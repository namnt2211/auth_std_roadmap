Module này giống công việc của kiến trúc sư an ninh tòa nhà: cửa chính dùng khóa gì, cửa kho dùng khóa gì, xe giao hàng (service) vào bằng thẻ gì, nhân viên nghỉ việc thì thu thẻ thế nào — và khi cửa không mở, kiểm tra theo thứ tự nào.

Input trước module

  • Có thể vẽ sequence diagram hoặc component diagram cơ bản.

Một số thuật ngữ dùng xuyên suốt:

  • Public client: ứng dụng không giữ được bí mật (SPA, desktop, mobile) vì code chạy trên máy người dùng. Confidential client: ứng dụng chạy trên server, giữ được client secret/khóa (web server, BFF, service).
  • Trust boundary (ranh giới tin cậy): đường phân chia giữa vùng bạn kiểm soát (server của bạn) và vùng không kiểm soát (browser, máy người dùng, mạng Internet). Mọi dữ liệu đi qua ranh giới này đều phải được kiểm tra.
  • Resource Server (RS): API giữ dữ liệu, kiểm tra access token. IdP (Identity Provider): hệ thống đăng nhập và phát hành token (Keycloak, Entra ID…).

B. Kiến trúc theo loại ứng dụng

B.1. Server-side Web Application Should

Nói đơn giản Web server giống quầy lễ tân có két sắt: lễ tân (backend) tự đi đổi “phiếu” (authorization code) lấy “chìa khóa” (token) ở IdP và cất trong két. Khách (browser) chỉ nhận một vé gửi đồ (session cookie) — không bao giờ cầm chìa thật.
  • Dùng OIDC Authorization Code Flow; backend đổi code lấy token, giữ client secret ở server (confidential client). Vẫn nên bật PKCE — OAuth 2.1 và RFC 9700 khuyến nghị PKCE cho cả confidential client.
  • Backend tạo application session riêng và bảo vệ bằng cookie (HttpOnly, Secure, SameSite).
  • Cần CSRF protection, cookie settings và session lifecycle (idle/absolute timeout, logout) — xem M06 — CSRF, M02 — session management.
  • Nếu gọi API downstream, dùng access token riêng cho API đó (đúng aud), không chuyển tiếp ID token.

Token chỉ nằm ở backend. Browser chỉ có cookie phiên của web app.
using Microsoft.AspNetCore.Authentication.Cookies;
using Microsoft.AspNetCore.Authentication.OpenIdConnect;
using Microsoft.IdentityModel.Protocols.OpenIdConnect;

builder.Services
    .AddAuthentication(o =>
    {
        o.DefaultScheme = CookieAuthenticationDefaults.AuthenticationScheme;          // đọc session
        o.DefaultChallengeScheme = OpenIdConnectDefaults.AuthenticationScheme;        // chưa login → IdP
    })
    .AddCookie(o =>
    {
        o.Cookie.Name = "__Host-orders";
        o.Cookie.HttpOnly = true;
        o.Cookie.SecurePolicy = CookieSecurePolicy.Always;
        o.Cookie.SameSite = SameSiteMode.Lax;
        o.ExpireTimeSpan = TimeSpan.FromHours(8);
        o.SlidingExpiration = true;
    })
    .AddOpenIdConnect(o =>
    {
        o.Authority = "https://idp.example.com/realms/demo";
        o.ClientId = "orders-web";
        o.ClientSecret = builder.Configuration["Oidc:ClientSecret"];   // từ secret store, KHÔNG commit
        o.ResponseType = OpenIdConnectResponseType.Code;               // Authorization Code flow
        o.UsePkce = true;
        o.SaveTokens = true;              // lưu token vào authentication ticket (cookie đã mã hóa)
        o.MapInboundClaims = false;
        o.GetClaimsFromUserInfoEndpoint = true;
        o.Scope.Add("orders.read");
        o.TokenValidationParameters.NameClaimType = "preferred_username";
    });

builder.Services.AddAuthorization(o =>
    o.FallbackPolicy = new Microsoft.AspNetCore.Authorization.AuthorizationPolicyBuilder()
        .RequireAuthenticatedUser().Build());
ℹ️ Lưu ý về SaveTokens SaveTokens = true lưu token trong authentication ticket — mặc định nằm trong cookie (được Data Protection mã hóa). Cookie sẽ to ra; khi có nhiều token hoặc nhiều claim, cân nhắc lưu ticket phía server (ITicketStore) hoặc token cache phân tán. Nếu chạy nhiều instance, cấu hình Data Protection key ring dùng chung.

Checklist server-side web

  • Code flow (+ PKCE), client secret/khóa trong secret store.
  • Cookie __Host-, HttpOnly, Secure, SameSite; idle + absolute timeout.
  • Antiforgery cho form/POST; GET không đổi trạng thái.
  • Callback path (/signin-oidc) đăng ký đúng redirect URI.
  • Logout: xóa cookie app + RP-initiated logout ở IdP (M03).
  • Data Protection key ring dùng chung khi scale-out.

B.2. SPA (Single-Page Application) Must

Nói đơn giản SPA là JavaScript chạy hoàn toàn trong browser — giống một quầy hàng đặt ngoài vỉa hè: ai đi qua cũng nhìn thấy mọi thứ trên quầy. Không thể giấu “mật khẩu của ứng dụng” (client secret) ở đó. Vì vậy SPA hoặc dùng PKCE và giữ token thật cẩn thận, hoặc gửi chìa khóa vào trong cửa hàng (BFF) và chỉ cầm vé.
  • Authorization Code + PKCE (M03). Không có client secret nào giữ bí mật được.
  • Cân nhắc BFF để token không vào browser, browser chỉ có cookie phiên.
  • Nếu SPA gọi API trực tiếp: phải thiết kế cẩn thận token storage (M06), CORS, chống XSS, và refresh token policy (rotation, lifetime ngắn).
  • CORS không phải cơ chế authentication hay authorization (xem bên dưới).

RFC 10017 — OAuth 2.0 for Browser-Based Applications (BCP 212, phát hành 8/2026, trước đây là draft-ietf-oauth-browser-based-apps) mô tả ba pattern, xếp theo mức an toàn giảm dần:

B.3. BFF — Backend for Frontend

Nói đơn giản BFF giống quầy gửi đồ của siêu thị: chìa khóa thật (token) nằm trong tủ của quầy, bạn (browser) chỉ cầm phiếu gửi đồ (session cookie). Mất phiếu ở ngoài thì kẻ gian khó dùng lâu dài — nhưng nếu kẻ gian đứng ngay cạnh bạn (XSS), hắn vẫn có thể bắt bạn đưa phiếu ra quầy lấy đồ hộ.

BFF là một backend nhỏ, đi cùng SPA (thường cùng domain), đóng vai confidential client: thực hiện OIDC code flow, giữ access/refresh token ở server, cấp cho browser một session cookie, và proxy các lời gọi API (gắn access token vào).

👍 Được gì

XSS không đánh cắp được token để dùng lâu dài; refresh token an toàn ở server; có thể dùng client secret/khóa; logout và revoke tập trung.

👎 Phải trả gì

Thêm một thành phần phải vận hành; cookie → phải chống CSRF; XSS vẫn gọi API qua BFF khi tab đang mở; thêm độ trễ do proxy.

Trong .NET có thể tự dựng BFF (ASP.NET Core + AddOpenIdConnect + reverse proxy như YARP) hoặc dùng thư viện chuyên dụng (vd Duende BFF — kiểm tra điều khoản license). Theo RFC 10017, cookie của BFF phải có HttpOnly + Secure, nên dùng tiền tố __Host-Http- (báo hiệu cookie chỉ được đặt qua HTTP và không chia sẻ với subdomain; trình duyệt/framework chưa hỗ trợ thì tối thiểu dùng __Host-), nên đặt SameSite=Strict, và BFF phải có biện pháp chống CSRF (vd yêu cầu custom header để buộc CORS preflight).

CORS không phải authentication/authorization

Nói đơn giản CORS (Cross-Origin Resource Sharing) là luật của trình duyệt: “trang web A có được đọc câu trả lời từ server B không?”. Nó giống người gác cổng của browser, không phải bảo vệ của server. curl, Postman, một server khác… chẳng hề quan tâm CORS.
  • CORS nới lỏng Same-Origin Policy cho browser; nó không xác minh người gọi là ai.
  • Request “đơn giản” (form POST) vẫn được gửi tới server kể cả khi CORS chặn đọc response → CORS không chống được CSRF một mình.
  • Access-Control-Allow-Origin: * kết hợp credentials là cấu hình sai (browser không cho phép); phản chiếu mọi Origin kèm Allow-Credentials: true là lỗ hổng.
  • API vẫn phải xác minh token và phân quyền cho mọi request, bất kể CORS.

Checklist SPA / BFF

  • Code + PKCE (S256); không client secret trong bundle JS.
  • Dữ liệu nhạy cảm → BFF; nếu không, access token trong memory, refresh token rotation + lifetime ngắn.
  • Không lưu refresh token trong localStorage.
  • CSP chặt; không innerHTML với dữ liệu người dùng.
  • CORS allowlist origin cụ thể; không coi CORS là bảo mật.
  • BFF: cookie __Host- HttpOnly Secure SameSite + chống CSRF (custom header/antiforgery).

B.4. Desktop / Native Application Must

Nói đơn giản App desktop giống một chiếc xe bán cho mọi người: ai mua cũng tháo ra xem được từng con ốc, nên giấu “mật khẩu ứng dụng” trong xe là vô nghĩa. Khi cần đăng nhập, app mở trình duyệt thật (như dẫn khách tới quầy chính thức) thay vì tự vẽ ô nhập mật khẩu, và lắng nghe kết quả ở một cổng tạm trên chính máy (loopback 127.0.0.1).
  • Dùng external/system browser. RFC 8252 (OAuth for Native Apps) §8.12: native app MUST NOT dùng embedded user-agent (WebView nhúng) cho authorization request — vì app nhúng có thể đọc mật khẩu người dùng gõ, và người dùng không thấy thanh địa chỉ/không dùng lại được phiên SSO của browser.
  • Authorization Code + PKCE; không nhúng client secret như thể nó là bí mật.
  • Redirect URI theo platform: loopback http://127.0.0.1:{port}/ (RFC 8252 §7.3 — AS phải chấp nhận port bất kỳ tại thời điểm request; §8.3: localhost là NOT RECOMMENDED, dùng IP literal), private-use URI scheme (com.example.app:/callback), hoặc HTTPS claimed URL. Một số IdP (vd Entra ID với MSAL) có quy ước riêng như http://localhost — theo hướng dẫn của nhà cung cấp.
  • Lưu token bằng secure OS storage; hạn chế lifetime và scope.
  • API vẫn xác minh access token và thực hiện authorization — app desktop không phải nơi quyết định quyền.

Checklist desktop

  • System browser (hoặc broker của OS như WAM trên Windows), không WebView nhúng.
  • Code + PKCE; client đăng ký là public client.
  • Redirect loopback IP / custom scheme đăng ký đúng.
  • Token cache mã hóa (DPAPI/MSAL cache); không file plaintext.
  • Access token ngắn, refresh token rotation; logout xóa cache + revoke.
  • Không log token; không gửi role/permission từ app lên API.

B.5. Mobile Application Should

Nói đơn giản Giống desktop: app mobile là “xe bán cho mọi người”, không giấu được bí mật. Khác biệt là trên điện thoại, app mở một tab trình duyệt an toàn của hệ điều hành để đăng nhập (app không nhìn được vào trong), và cất token vào két sắt của điện thoại (Keychain/Keystore).
  • Authorization Code + PKCE, không hardcode secret.
  • Dùng system browser hoặc secure browser session của platform: iOS ASWebAuthenticationSession (kế nhiệm SFAuthenticationSession), Android Custom Tabs. Đây là “in-app browser tab” mà RFC 8252 (Phụ lục B) mô tả: chạy trong process browser, app không đọc được nội dung, có chia sẻ cookie SSO. Thư viện tham khảo: AppAuth (iOS/Android), MSAL.
  • Redirect: claimed HTTPS link (iOS Universal Links, Android App Links) an toàn hơn custom scheme vì app khác khó chiếm.
  • Secure storage: iOS Keychain, Android Keystore (khóa trong phần cứng khi có) để mã hóa token.
  • Có quy trình revoke và mất thiết bị: user/IT thu hồi refresh token, phiên trên thiết bị đó.

B.6. Service-to-Service / Microservices Must

Nói đơn giản Không có người dùng nào bấm nút — đây là xe giao hàng tự động ra vào kho. Mỗi xe cần thẻ riêng ghi rõ được vào kho nào (client credentials + scope). Đừng phát một thẻ chung cho cả đội xe: mất một thẻ là mất hết, và không biết xe nào đã vào.
  • Client Credentials (M03) hoặc workload identity phù hợp.
  • Mỗi service có identity riêng; least privilege (chỉ scope cần thiết).
  • Quản lý secret/certificate bằng secret manager (Azure Key Vault, AWS Secrets Manager, HashiCorp Vault…) hoặc tốt hơn là workload identity — không có secret dài hạn để lộ.
  • Resource server xác minh audience và scope.
  • mTLS có thể bổ sung xác thực ở tầng kết nối; không tự động thay thế authorization nghiệp vụ.
  • Tránh dùng chung một client credential cho toàn bộ hệ thống.

Checklist service-to-service

  • Mỗi service một client/identity; không chia sẻ credential.
  • Ưu tiên workload identity / private_key_jwt / mTLS hơn shared secret.
  • Secret trong secret manager, có lịch rotation; không trong appsettings/git.
  • Scope tối thiểu; API kiểm tra aud + scope.
  • Cache access token; không xin token cho mỗi request.

B.7. Windows Domain / Enterprise Network Nice

  • AD + Kerberos (M05) cho xác thực trong Windows domain (đăng nhập máy, file share, IIS với Windows Authentication).
  • LDAP/LDAPS (M05) để truy vấn directory; dùng LDAPS (TLS, thường port 636) thay vì LDAP rõ, và tránh dùng LDAP bind làm “cơ chế đăng nhập” cho app web mới.
  • RADIUS/TACACS+ (M05) cho network access (Wi-Fi 802.1X, VPN) và quản trị thiết bị mạng.
  • SAML/OIDC cho federation tới ứng dụng (IdP như AD FS hoặc Entra ID dùng AD làm nguồn danh tính).
  • FIDO2/passkey/MFA (Windows Hello for Business, security key) để tăng cường đăng nhập.

D.3. Code tham khảo phía WPF

Với Keycloak (như Lab 3): thư viện Duende.IdentityModel.OidcClient (trước đây là IdentityModel.OidcClient). Lớp SystemBrowser dưới đây không có sẵn trong thư viện — lấy từ sample của dự án (mở browser + HttpListener trên loopback).

using Duende.IdentityModel.OidcClient;
using System.Security.Cryptography;

public sealed class LoginService
{
    private readonly OidcClient _client;

    public LoginService()
    {
        var port = GetFreeTcpPort();
        _client = new OidcClient(new OidcClientOptions
        {
            Authority   = "http://localhost:8080/realms/demo",
            ClientId    = "wpf-client",                       // public client, KHÔNG có secret
            Scope       = "openid profile orders.read offline_access",
            RedirectUri = $"http://127.0.0.1:{port}/",
            Browser     = new SystemBrowser(port)             // từ sample: mở system browser + loopback
        });
    }

    public async Task<LoginResult> LoginAsync()
    {
        var result = await _client.LoginAsync(new LoginRequest());   // PKCE, state, nonce tự động
        if (result.IsError) throw new InvalidOperationException(result.Error);

        // Lưu refresh token đã mã hóa theo user Windows (DPAPI)
        var protectedBytes = ProtectedData.Protect(
            System.Text.Encoding.UTF8.GetBytes(result.RefreshToken),
            optionalEntropy: null,
            scope: DataProtectionScope.CurrentUser);
        await File.WriteAllBytesAsync(TokenFilePath, protectedBytes);

        return result;   // result.AccessToken dùng để gọi API; result.IdentityToken cho client
    }
    // GetFreeTcpPort(), TokenFilePath ... bỏ qua cho gọn
}

Phân tích sâu 3 case

Case 1 — B2C social login: “email trùng thì gộp tài khoản” có ổn không?

Bối cảnh: shop online cho đăng nhập bằng Google, Microsoft và mật khẩu riêng.

  • Lưu bảng ExternalLogins(Issuer, Subject, UserId). Khóa định danh là iss + sub; email chỉ là thuộc tính.
  • Không tự gộp chỉ vì email trùng: một IdP có thể cho phép email chưa xác minh; kẻ tấn công tạo account ở IdP B với email của nạn nhân → chiếm tài khoản (account takeover qua account linking).
  • Gộp chỉ khi user đã đăng nhập bằng phương thức hiện có rồi chủ động “liên kết thêm”, hoặc email đã xác minh và IdP được tin cậy về email đó, kèm xác nhận.
  • Flow: OIDC code + PKCE từ backend (confidential) hoặc BFF; session cookie cho shop.
Case 2 — Đối tác gọi API: API key hay Client Credentials?
  • API key: đơn giản, phù hợp dữ liệu ít nhạy cảm, cần quota/metering. Nhược: thường dài hạn, không có scope chuẩn, không hết hạn tự động, dễ lộ qua log/repo. Bắt buộc: gửi qua header (không query string), hash khi lưu, có rotation và revoke, gắn với một đối tác.
  • Client Credentials: token ngắn hạn, có scope/aud, IdP quản lý vòng đời, có thể nâng cấp lên private_key_jwt/mTLS. Phù hợp khi dữ liệu nhạy cảm hoặc cần phân quyền theo scope.
  • Cả hai đều định danh ứng dụng, không định danh người dùng. Nếu đối tác truy cập dữ liệu thay mặt user của bạn → cần Authorization Code (delegated) thay vì Client Credentials.
Case 3 — Nhân viên nghỉ việc lúc 17:00, phải mất quyền ngay
  1. HR vô hiệu hóa ở nguồn (HRIS/AD) → IdP vô hiệu hóa user và thu hồi refresh token/phiên SSO.
  2. IdP gửi SCIM PATCH active=false tới các app hỗ trợ SCIM → app khóa account, xóa session.
  3. App/API không hỗ trợ SCIM: dựa vào access token ngắn hạn (5–15 phút) và refresh token đã bị thu hồi.
  4. Nếu có CAE/introspection: API từ chối token ngay khi nhận sự kiện.
  5. Thu hồi credential khác: thiết bị (mất thiết bị → wipe), API key cá nhân, SSH key, chứng thư, passkey đăng ký; rotate shared secret mà người đó biết.
  6. Kiểm tra audit log các hoạt động gần thời điểm nghỉ.

G.4. Checklist kiến trúc — bổ sung vào security checklist master (deliverable 4)

Bổ sung vào checklist master ở M06:

BFF

  • Token chỉ ở server; cookie __Host-, HttpOnly, Secure, SameSite.
  • Chống CSRF (custom header bắt buộc / antiforgery) cho mọi endpoint của BFF.
  • Proxy chỉ chuyển tiếp tới API trong allowlist; không thành open proxy.
  • Logout xóa session server + revoke refresh token.

CORS

  • Allowlist origin cụ thể; không phản chiếu mọi Origin khi Allow-Credentials: true.
  • Không xem CORS là authentication/authorization; API vẫn xác minh token.
  • UseCors đặt trước authentication/authorization để preflight không bị 401.

mTLS / service identity

  • Mỗi service một identity/certificate; certificate ngắn hạn, tự động gia hạn.
  • mTLS chỉ xác thực kết nối; API vẫn kiểm tra scope/permission.
  • Cân nhắc certificate-bound token (RFC 8705) hoặc DPoP cho token nhạy cảm.

Key rotation

  • IdP rotate signing key theo lịch; JWKS công bố key mới trước khi dùng, giữ key cũ đến khi token cũ hết hạn.
  • API lấy JWKS tự động theo kid (không hardcode public key).
  • Theo dõi ngày hết hạn certificate SAML/TLS; có runbook rollover.
  • Runbook khi lộ khóa: rotate ngay, thu hồi token/phiên liên quan.

Secret management

  • Secret trong secret manager (Key Vault, Vault…), không trong git/appsettings/image.
  • Ưu tiên workload identity / managed identity để không có secret dài hạn.
  • Secret có chủ sở hữu, hạn dùng, lịch rotation; quét secret trong repo (secret scanning).
  • Không nhúng secret trong SPA/desktop/mobile.

Tóm tắt nhanh

  • Thiết kế bắt đầu từ 10 câu hỏi: subject, client, resource, federation, MFA, delegated access, lưu token, nơi phân quyền, vòng đời account, sự cố.
  • Server-side web: OIDC code flow, confidential client, cookie session + CSRF.
  • SPA: code + PKCE; dữ liệu nhạy cảm → BFF (RFC 10017). CORS không phải authN/authZ.
  • Desktop/mobile: public client, code + PKCE, system browser (RFC 8252), token trong secure OS storage (DPAPI/Keychain/Keystore).
  • Service-to-service: Client Credentials hoặc workload identity, mỗi service một identity; mTLS bổ sung, không thay authorization.
  • Enterprise network: AD + Kerberos, LDAPS, RADIUS, SAML/OIDC federation, FIDO2.
  • Offboarding = vô hiệu hóa ở IdP + SCIM + revoke session/refresh token + access token ngắn hạn (+ CAE).
  • WPF + API: WPF lấy token qua browser; API tự xác minh token và tự phân quyền; không tin role từ UI.
  • Troubleshooting: đọc WWW-Authenticate + log; 401 → kiểm tra token (exp, aud, iss, chữ ký); 403 → kiểm tra scope, claim type, policy.
  • Không có giao thức tốt nhất — chọn theo use case bằng decision matrix.

Knowledge Check (tự luận)

Chọn flow nào cho WPF desktop app? Vì sao?

Authorization Code + PKCE qua system browser với redirect loopback (RFC 8252). WPF là public client nên không giữ được secret; PKCE bảo vệ authorization code khỏi bị chặn và dùng lại. System browser giúp app không chạm vào mật khẩu, hỗ trợ MFA/passkey và SSO sẵn có.

Có nên nhúng client secret vào WPF không?

Không. Assembly .NET dịch ngược rất dễ; secret nhúng là “bí mật” chung của mọi bản cài, không chứng minh được gì và một khi lộ thì phải đổi cho tất cả. Đăng ký WPF là public client, dùng PKCE.

Vì sao API không nên nhận ID token làm access token?

ID token dành cho client (aud = client_id), mô tả sự kiện đăng nhập, không mang scope cho API. Nhận ID token nghĩa là API chấp nhận token phát hành cho bên khác — bất kỳ client nào có ID token của user đều gọi được API. API phải nhận access token có aud là chính nó.

Khi nào dùng SAML thay vì OIDC?

Khi ứng dụng/SaaS chỉ hỗ trợ SAML, khi IdP hoặc đối tác federation yêu cầu SAML, hoặc khi tổ chức đã có hạ tầng SAML ổn định. Với app mới, mobile, SPA hoặc cần gọi API, OIDC/OAuth phù hợp hơn.

Khi nào Kerberos phù hợp hơn OIDC?

Trong mạng nội bộ Windows domain: máy domain-joined, file share, app nội bộ dùng Windows Integrated Authentication — người dùng đã có TGT khi đăng nhập máy nên SSO trong suốt, không cần browser redirect. Kerberos không phù hợp cho client ngoài domain/Internet hoặc mobile.

mTLS có thay thế authorization không?

Không. mTLS xác thực hai đầu kết nối (service nào đang gọi). Authorization vẫn phải quyết định service đó được làm gì (scope/permission) và, nếu thay mặt user, user đó có quyền gì.

Nếu token hợp lệ nhưng user không có quyền xem resource thì API trả gì?

403 Forbidden — hoặc 404 Not Found nếu chính sách là không lộ sự tồn tại của resource. Không trả 401 (token hợp lệ, xác thực lại không giải quyết được gì).

Làm thế nào để thu hồi quyền khi nhân viên nghỉ việc?

Vô hiệu hóa ở nguồn danh tính/IdP; thu hồi refresh token và phiên SSO; SCIM đẩy active=false tới các app; access token ngắn hạn để token còn lại hết hạn nhanh; dùng CAE/introspection nếu có; thu hồi thiết bị, API key, certificate, passkey; rotate shared secret; kiểm tra audit log.
