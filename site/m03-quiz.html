Các hiểu lầm cần tránh

Bản tóm tắt để ôn nhanh. Chi tiết và ví dụ nằm ngay dưới từng phần trong bài — bấm “xem bài” để đọc. Thử che vế “Thực tế” và tự giải thích vì sao vế “Hiểu lầm” sai.

  • Hiểu lầm: Có access token nghĩa là người dùng đã đăng nhập vào app. → Thực tế: Access token để gọi API; đăng nhập cần ID token đã validate (xem bài).
  • Hiểu lầm: OAuth đã đủ để làm đăng nhập. → Thực tế: OAuth là ủy quyền; xác thực chuẩn hóa nằm ở OIDC (xem bài).
  • Hiểu lầm: Obfuscate thì giấu được client_secret trong WPF/SPA. → Thực tế: Public client không giữ được bí mật; dùng PKCE, không secret (xem bài).
  • Hiểu lầm: PKCE chỉ dành cho mobile/SPA. → Thực tế: RFC 9700 khuyến nghị cả confidential client; OAuth 2.1 đưa PKCE vào mặc định (xem bài).
  • Hiểu lầm: OAuth 2.1 là chuẩn mới với nhiều cơ chế mới. → Thực tế: Là bản hợp nhất best practice đã có, tại 11/2026 vẫn là Internet-Draft (xem bài).
  • Hiểu lầm: state và nonce là một, dùng cái nào cũng được. → Thực tế: state bảo vệ authorization response (CSRF), nonce bảo vệ ID token (replay) (xem bài).
  • Hiểu lầm: Gửi ID token lên API cho tiện, vì nó cũng là JWT có chữ ký. → Thực tế: aud = client, không có scope; API đúng sẽ trả 401 (xem bài).
  • Hiểu lầm: Web gửi kèm ID token ở mỗi request để “giữ đăng nhập”. → Thực tế: Validate xong thì tạo session cookie riêng (xem bài).
  • Hiểu lầm: Chữ ký ID token hợp lệ là đủ. → Thực tế: Còn phải kiểm tra iss, aud, exp, nonce (xem bài).
  • Hiểu lầm: Copy public key vào config là xong, khỏi cần JWKS. → Thực tế: Ngày xoay khóa, toàn hệ thống 401; để thư viện đọc Discovery/JWKS (xem bài).
  • Hiểu lầm: Gặp kid lạ thì tải lại JWKS mỗi lần. → Thực tế: Refresh có giới hạn tần suất, nếu không sẽ bị spam (xem bài).
  • Hiểu lầm: Bấm Logout trong app là đã đăng xuất khỏi mọi nơi. → Thực tế: Local session, OP session, token là ba thứ khác nhau; chỉ local logout thì SSO cho vào lại ngay (xem bài).
  • Hiểu lầm: Đăng xuất ở OP thì access token JWT hết hiệu lực ngay. → Thực tế: API validate cục bộ vẫn nhận tới exp (xem bài).
  • Hiểu lầm: sub không bao giờ cấp lại nên chỉ cần lưu sub. → Thực tế: Chỉ duy nhất trong phạm vi iss; khóa là (iss, sub) (xem bài).
  • Hiểu lầm: Email trùng (kể cả email_verified = true) thì cứ tự gộp tài khoản. → Thực tế: Cần provider có thẩm quyền với domain; an toàn nhất là người dùng đang đăng nhập chủ động liên kết (xem bài).
  • Hiểu lầm: Dùng /organizations thì Microsoft đã lọc tenant giúp. → Thực tế: App phải tự kiểm tra tid theo danh sách cho phép (xem bài).

So sánh cần nắm vững

Các cặp dưới đây là nơi người mới hay nhầm nhất. Với mỗi dòng, hãy che cột “Câu chốt” và thử tự nói ra trong một câu. Link dẫn về bài có bảng so sánh chi tiết và ví dụ.

#Cặp so sánhĐiểm khác cốt lõiCâu “chốt”
1OAuth 2.0 vs OIDCOAuth: ủy quyền, sản phẩm là access token cho API. OIDC: xác thực trên nền OAuth, thêm scope openid, ID token, UserInfo, Discovery.OAuth = “được làm gì”, OIDC = “là ai”.
2Authentication vs delegated authorizationAuthN xác minh danh tính người đang dùng app. Delegated authorization: người dùng cho phép app truy cập tài nguyên của mình ở nơi khác.Đăng nhập ≠ cấp quyền cho app.
3Authorization Code vs Client CredentialsCode: có người dùng, qua browser, token đại diện người dùng. Client Credentials: không có người dùng, token đại diện service.Có user → Code + PKCE. Không user → Client Credentials.
4Public vs Confidential clientConfidential chạy trên server, giữ được secret/key. Public chạy trên thiết bị người dùng, không giữ được.Code trên máy người dùng = public.
5Access vs ID vs Refresh tokenAccess → API. ID → client (kết quả đăng nhập). Refresh → AS (xin token mới).Mỗi token một người nhận (bảng).
6JWT vs opaque tokenJWT tự chứa claims, API validate cục bộ bằng JWKS, khó thu hồi tức thì. Opaque là chuỗi tham chiếu, API phải introspect, thu hồi tức thì được.JWT: nhanh, độc lập. Opaque: kiểm soát tập trung (M02).
7PKCE vs client_secretSecret: tĩnh, xác thực client, chỉ confidential client giữ được. PKCE: động mỗi lần đăng nhập, ràng buộc code với client instance, dùng được cho public client.Không thay nhau — confidential client nên dùng cả hai.
8state vs noncestate: client kiểm tra ở callback, chống CSRF/response injection. nonce: nằm trong ID token, chống replay ID token.state bảo vệ redirect, nonce bảo vệ ID token.
9Local logout vs federated logoutLocal: xóa session của app. Federated: kết thúc phiên ở OP và (tùy) thông báo các RP khác.Chỉ local logout → SSO đăng nhập lại ngay.
10OAuth 2.0 vs OAuth 2.12.1 hợp nhất 2.0 + PKCE + RFC 9700: PKCE bắt buộc, bỏ Implicit/ROPC/plain, exact redirect URI, không token trong query, ràng buộc refresh token public client.2.1 = 2.0 “đã dọn dẹp”, vẫn là draft.
11iss+sub vs email(iss, sub) ổn định, duy nhất, không cấp lại. Email đổi được, tái sử dụng được, có thể chưa xác minh.Khóa = (iss, sub). Email = thuộc tính.
12Scope vs claimScope: client xin trong request (openid profile email). Claim: giá trị OP trả trong token/UserInfo ("email": "an.nv@example.com").Scope = “tôi xin”, claim = “bạn nhận” (Bài 3.5).
13ID token vs UserInfoID token: JWT có chữ ký, nhận ở token endpoint, kể về sự kiện đăng nhập. UserInfo: gọi thêm bằng access token để lấy hồ sơ; sub phải trùng ID token.ID token = biên bản đăng nhập; UserInfo = hỏi thêm hồ sơ.
14Discovery vs JWKSDiscovery (/.well-known/openid-configuration): danh sách endpoint, tính năng. JWKS (jwks_uri): public key để kiểm tra chữ ký, đổi khi xoay khóa.Discovery là danh bạ, JWKS là bảng mẫu con dấu (Bài 3.6).
15kid vs algkid: ký bằng key nào → chọn JWK. alg: ký bằng thuật toán nào → chỉ chấp nhận thuật toán trong danh sách cho phép.kid = dấu nào, alg = cách đóng dấu.
16RP-initiated vs front-channel vs back-channel logoutRP-initiated: app báo OP kết thúc phiên OP (qua trình duyệt). Front-channel: OP báo các app khác qua iframe trong trình duyệt. Back-channel: OP POST logout token thẳng tới server từng app.App báo OP; OP báo các app còn lại (Bài 3.6).
17Social login vs account linking vs federationSocial login: đăng nhập bằng Google/GitHub. Account linking: gắn nhiều external login vào một user nội bộ. Federation: một IdP (vd. Keycloak) tin kết quả đăng nhập của IdP khác.Cửa vào / nhiều chìa một nhà / hai tổ chức tin nhau (Bài 3.7).
18Single-tenant vs multi-tenantSingle: chỉ người dùng một tổ chức, iss cố định. Multi: nhiều tổ chức, mỗi tenant một iss/tid → app tự kiểm tra danh sách tenant cho phép.Multi-tenant = phải tự giữ danh sách “ai được vào”.
19On-Behalf-Of vs Client Credentials vs chuyển tiếp tokenOBO: đổi token của user lấy token mới đúng aud, vẫn là user. Client Credentials: token của chính service, mất danh tính user. Chuyển tiếp nguyên xi: sai aud, quyền quá rộng.Có user → OBO; không user → Client Credentials (Bài 3.7).

Tóm tắt nhanh

  • OAuth 2.0 là khung ủy quyền: cấp access token có scope, có hạn, thu hồi được — thay cho việc đưa mật khẩu cho app khác.
  • 4 vai trò: Resource Owner (người dùng), Client (app), Authorization Server (cấp token), Resource Server (API kiểm tra token).
  • Có người dùng → Authorization Code + PKCE (mọi loại client). Không có người dùng → Client Credentials. Thiết bị không có trình duyệt → Device flow.
  • ROPC và Implicit đã bị loại bỏ: không dùng cho thiết kế mới.
  • PKCE: verifier ngẫu nhiên 43–128 ký tự, challenge = BASE64URL(SHA256(verifier)), method S256 → kẻ trộm code không đổi được token.
  • state chống CSRF ở callback, nonce chống replay ID token, redirect URI chính xác chống trộm code qua URI giả — không cái nào thay cái nào.
  • OIDC = OAuth + scope openid + ID token (JWT, aud = client_id) + UserInfo + Discovery/JWKS.
  • ID token cho client, access token cho API — không bao giờ dùng thay nhau.
  • Discovery cho biết endpoint; JWKS cho public key, chọn theo kid. Cache có thời hạn và tải lại khi gặp kid lạ — đừng hardcode key.
  • Logout có 3 lớp: session của app, session ở OP, token. Single Logout không bao giờ hoàn hảo.
  • Định danh người dùng bằng (iss, sub), không bằng email; chỉ liên kết tài khoản khi người dùng chủ động hoặc email đã xác minh bởi provider có thẩm quyền.
  • API gọi tiếp API khác thay mặt người dùng → Token Exchange / On-Behalf-Of, không chuyển tiếp nguyên token và không dùng Client Credentials.

Output / Deliverables

  • Sơ đồ sequence Authorization Code + PKCE có đủ Client, Browser, Authorization Server và Resource Server (tham khảo sơ đồ mẫu). Core
  • Sơ đồ Client Credentials cho service-to-service (mẫu). Core
  • Bảng so sánh OAuth 2.0 và OIDC, kèm một đoạn ngắn: OAuth 2.1 bắt buộc/loại bỏ gì và vì sao không dùng ROPC/Implicit cho thiết kế mới (OAuth 2.1, ROPC/Implicit). Core
  • Bổ sung bảng token và checklist validation từ Module 02 với phần ID token: nonce, aud = client_id, azp, issuer, thời hạn (bảng, checklist). Core
  • Bảng giải thích state, nonce, PKCE và redirect URI validation: mỗi cơ chế chống lại tấn công nào (mẫu). Core
  • Thiết kế bảng lưu user/external login dựa trên iss + sub, kèm quy tắc account linking (schema, quy tắc).

Knowledge Check (tự luận)

Tự trả lời trước, sau đó mở đáp án gợi ý để so sánh.

OAuth có xác thực người dùng không?

Bản thân OAuth 2.0 là authorization framework: Authorization Server có xác thực người dùng (để hỏi consent), nhưng OAuth không chuẩn hóa cách truyền kết quả xác thực cho client. Access token dành cho API, có thể không chứa thông tin người dùng, và client không có cách chuẩn để chắc token được cấp cho chính mình. Muốn “đăng nhập” chuẩn → dùng OIDC (ID token).

OIDC thêm những gì vào OAuth?

Scope openid; ID token (JWT có chữ ký với iss, sub, aud, exp, iat, nonce, auth_time, acr, amr…); tham số nonce; UserInfo endpoint; bộ claim và scope chuẩn (profile, email…); Discovery và JWKS; các đặc tả logout (RP-initiated, front/back-channel).

Vì sao SPA/native app cần PKCE?

Chúng là public client: không có client_secret để chứng minh với token endpoint “tôi là client thật”. Nếu authorization code bị chặn (app độc trùng custom scheme, log, Referer, extension), kẻ tấn công đổi code lấy token ngay. PKCE gắn code với một bí mật động chỉ instance thật biết (code_verifier), nên code bị trộm là vô dụng.

client_secret có thể giữ bí mật trong desktop app không?

Không. Mọi người dùng đều có file thực thi; secret nhúng trong đó (kể cả obfuscate, mã hóa với key cũng nằm trong app) có thể bị trích xuất bằng decompiler hoặc đọc bộ nhớ. Desktop app là public client → dùng Authorization Code + PKCE với system browser và loopback redirect, không có secret (M07 — Desktop).

API cần nhận ID token hay access token?

Access token. ID token có aud = client_id của RP, mô tả sự kiện đăng nhập cho client, không mang scope/quyền cho API. API phải validate access token: chữ ký, iss, aud = chính API, exp, scope/role.

aud của ID token và access token có thể khác nhau không?

Có, và thường là khác. ID token: aud = client_id của RP (vd. demo-client). Access token: aud = API đích (vd. demo-api). Cùng một lần đăng nhập sinh ra hai token với hai “người nhận” khác nhau; azp cho biết client nào đã xin token.

Client Credentials có đại diện cho user đang đăng nhập không?

Không. Token Client Credentials đại diện cho chính ứng dụng/service (sub là service account). Nếu cần gọi API downstream thay mặt user → Token Exchange/On-Behalf-Of, không phải Client Credentials.

Nếu chữ ký JWT hợp lệ nhưng aud sai, API có nên chấp nhận không?

Không. Chữ ký hợp lệ chỉ chứng minh token do AS phát hành và không bị sửa. aud sai nghĩa là token được cấp cho người nhận khác (API khác, hoặc là ID token cho client). Chấp nhận nó cho phép “token substitution”: token lấy ở dịch vụ kém quan trọng được dùng để vào dịch vụ quan trọng. Trả 401.

Vì sao không dùng email làm khóa định danh người dùng?

Email có thể thay đổi, được cấp lại cho người khác, chưa được xác minh (email_verified = false), và ở một số provider người dùng tự đặt được. Dùng email làm khóa (hoặc tự liên kết theo email) có thể dẫn đến chiếm tài khoản. Khóa đúng: cặp (iss, sub); email chỉ là thuộc tính liên lạc.

Khi người dùng bấm “Đăng xuất”, một web dùng OIDC nên làm những gì?

(1) Xóa session cookie của chính app (local logout). (2) Revoke refresh token nếu có. (3) Chuyển trình duyệt tới end_session_endpoint kèm id_token_hint và post_logout_redirect_uri đã đăng ký (RP-initiated logout) để kết thúc phiên OP. Các app khác chỉ bị đăng xuất nếu OP gửi front-channel/back-channel logout cho chúng. Access token JWT đã phát vẫn dùng được tới exp → giữ thời hạn ngắn (Bài 3.6).

App nhận JWT có kid chưa từng thấy. Xử lý thế nào?

Tải lại Discovery/JWKS từ jwks_uri đã cấu hình (có giới hạn tần suất để không bị spam). Nếu có key với kid đó → kiểm tra chữ ký bình thường; nếu vẫn không có → 401. Không tải key từ URL do chính token khai (jku/x5u) và không bỏ qua kiểm tra chữ ký (key rotation).

OAuth 2.1 bắt buộc và loại bỏ những gì?

Bắt buộc: PKCE cho mọi Authorization Code (chỉ S256; ngoại lệ hẹp cho confidential client dùng OIDC nonce), redirect URI so khớp chính xác (trừ port loopback), refresh token của public client phải sender-constrained hoặc dùng một lần. Loại bỏ: Implicit grant, ROPC, PKCE plain, bearer token trong query string. Tại 11/2026 OAuth 2.1 vẫn là Internet-Draft (-17); các yêu cầu tương ứng đã có hiệu lực qua RFC 9700 (BCP).

✅ Tiêu chí hoàn thành Có thể vẽ và giải thích Authorization Code + PKCE và Client Credentials, và mô tả cách client xác minh ID token và API xác minh access token mà không nhầm vai trò của từng token. Kiểm chứng bằng tay ở Lab 1–Lab 3.
