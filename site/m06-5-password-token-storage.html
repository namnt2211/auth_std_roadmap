D. Mật khẩu theo NIST SP 800-63B-4 Should

Nói đơn giản NIST (Viện Tiêu chuẩn và Công nghệ Hoa Kỳ) nói: một câu dài dễ nhớ (“com-ga-xoi-mo-buoi-sang-thu-hai”) mạnh hơn một từ ngắn rắc rối (“P@ss1!”). Đừng ép đổi mật khẩu định kỳ — người ta chỉ đổi “Mua1” thành “Mua2”. Thay vào đó: chặn mật khẩu phổ biến/đã lộ, giới hạn số lần đoán, và thêm MFA.

SHALL = bắt buộc, SHOULD = nên (khuyến nghị mạnh), MAY = được phép. Đây là cách viết chuẩn trong tài liệu NIST/RFC.

Bản hiện hành là NIST SP 800-63B-4 (Digital Identity Guidelines: Authentication and Authenticator Management), bản final phát hành tháng 7/2025, thay thế SP 800-63B (2017). Nguồn: pages.nist.gov/800-63-4/sp800-63b.html và csrc.nist.gov. Các yêu cầu cho “password verifier” (mục 3.1.1.2) và rate limiting (mục 3.2.2):

ℹ️ Vì sao NIST bỏ “đổi mật khẩu định kỳ” và “quy tắc phức tạp”? Bị ép đổi mỗi 90 ngày, người dùng chọn mẫu dễ đoán (Spring2026! → Summer2026!) hoặc ghi ra giấy. Quy tắc phức tạp tạo ra P@ssw0rd1 — đủ “phức tạp” nhưng nằm đầu mọi danh sách đoán. Độ dài + blocklist + MFA + rate limiting + lưu trữ bằng password hashing đúng cách hiệu quả hơn nhiều. Đổi mật khẩu chỉ khi có dấu hiệu bị lộ.

⚠️ Hiểu lầm hay gặp

Hiểu lầmMật khẩu phải có chữ hoa, số, ký tự đặc biệt và đổi mỗi 90 ngày.Thực tếNIST SP 800-63B-4: SHALL NOT composition rules, SHALL NOT đổi định kỳ; ưu tiên độ dài + blocklist. Chỉ bắt đổi khi có bằng chứng mật khẩu bị lộ.
Hiểu lầmNIST giới hạn mật khẩu tối đa 64 ký tự.Thực tếNgược lại: hệ thống SHOULD cho phép ít nhất 64 ký tự. 64 là mức sàn của giới hạn tối đa, không phải trần.
Hiểu lầmNIST yêu cầu khóa tài khoản sau 3–5 lần nhập sai.Thực tếNIST chỉ yêu cầu giới hạn số lần thất bại liên tiếp không quá 100 (MAY thấp hơn). Khóa cứng quá sớm còn giúp kẻ gian cố tình khóa tài khoản người khác; có thể dùng độ trễ tăng dần, CAPTCHA, đánh giá rủi ro.

E. Token storage trong browser Must

Nói đơn giản Cất chìa khóa ở đâu? localStorage = treo chìa ngoài cửa (ai lọt vào sân là cầm đi được). Memory = cầm chìa trong tay (mất khi bạn ngủ/reload, kẻ lọt vào nhà vẫn sai bạn mở cửa được). Cookie HttpOnly = chìa trong két, chỉ người giữ két dùng. BFF (Backend for Frontend — một server nhỏ đứng sau SPA) = chìa gửi ở bảo vệ tòa nhà, bạn chỉ cầm vé gửi đồ. Nhưng nếu kẻ gian đã ở trong nhà (XSS), hắn vẫn có thể nhờ bạn đi lấy đồ hộ.
Nơi lưuRủi ro XSSRủi ro CSRFGhi chú
localStorage / sessionStorage🔴 Cao: script đọc và gửi token ra ngoài được🟢 ThấpĐơn giản nhưng mất token nếu có XSS; token còn dùng được sau khi nạn nhân đóng tab.
Memory (biến JavaScript)🟠 Trung bình: XSS vẫn gọi API khi trang đang mở, khó lấy token dùng lâu dài🟢 ThấpMất khi reload → cần cơ chế lấy lại token (silent renew/refresh).

Ví dụ (Kaopiz HR): hr-web để access token trong localStorage. Một bình luận chứa XSS gửi token của Bình ra ngoài; kẻ gian xem bảng lương cả phòng từ máy của hắn cho đến khi token hết hạn. Nếu hr-web dùng BFF, cùng lỗi XSS đó chỉ gọi được API trong lúc Bình mở trang — và kẻ gian không có token nào để mang đi.

Càng ít chỗ JS chạm được vào token thì XSS càng ít thiệt hại. Cookie/BFF đổi rủi ro XSS lấy rủi ro CSRF — và CSRF dễ chặn hơn.
⛔ Không có nơi lưu nào miễn nhiễm hoàn toàn với XSS Khi script độc đã chạy trong origin của bạn, nó có thể gọi API như chính người dùng — dù token nằm ở đâu. Cách lưu token chỉ quyết định mức thiệt hại: token bị mang đi dùng lâu dài (localStorage) hay chỉ bị lạm dụng khi tab đang mở (cookie HttpOnly/BFF). XSS phải được ngăn chặn từ gốc.

Hiểu lầmLưu token trong memory là an toàn tuyệt đối.Thực tếMemory chỉ khiến token khó bị mang đi dùng lâu dài. Trong lúc trang đang chạy, script XSS vẫn gọi API như người dùng, hoặc ghi đè fetch để bắt token khi app gắn vào header.
Hiểu lầmDùng BFF thì không cần chống CSRF nữa.Thực tếBFF dựa vào cookie session mà browser tự gửi, nên chính nó cần chống CSRF: SameSite + anti-CSRF token hoặc custom header (vd X-CSRF: 1).

F. Security best practices Must

🔐

Xác thực

Bật MFA; ưu tiên phishing-resistant MFA/passkey. Chính sách mật khẩu theo NIST. SMS OTP chỉ là dự phòng. Recovery mạnh ngang login.

🔁

Flow & client

Authorization Code + PKCE cho public client (M03). Không nhúng client secret trong desktop/mobile/SPA. Bảo vệ redirect_uri, state, nonce (M03).

🎫

Token

Xác minh issuer, audience, signature, expiration và token type. Access token ngắn hạn; refresh token rotation + reuse detection (M02). Không đưa token vào URL, log, source control, error message.

🍪

Session & browser

HTTPS/TLS; cookie Secure, HttpOnly, SameSite phù hợp. Chống CSRF/XSS; hiểu token storage trade-off.

🛂

Authorization

Least privilege, deny by default, kiểm tra quyền ở server và ở mức object (chống BOLA).

📒

Audit & vận hành

Audit log không ghi credential, access/refresh token, dữ liệu nhạy cảm. Có quy trình account recovery, revoke session/token, mất thiết bị, offboarding. Quản lý signing key/certificate, rotation, expiration, secret storage.

⚠️ Hiểu lầm hay gặp

Hiểu lầmLog toàn bộ request (kể cả header Authorization) để debug là chấp nhận được vì log chỉ nội bộ.Thực tếLog được nhiều người, công cụ và bản sao lưu đọc, giữ lâu hơn token. Bearer token trong log = token bị lộ. Hãy log sub, client_id, jti và lý do lỗi thay vì token.
