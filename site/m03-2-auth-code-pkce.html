Bài 3.2 — Authorization Code + PKCE

Đây là flow bạn sẽ dùng cho hầu hết ứng dụng có người dùng đăng nhập (web, SPA, desktop, mobile). Bài đi chậm từng bước: trình duyệt được chuyển đi đâu, mang theo gì, client đổi code lấy token ra sao — và vì sao phải thêm PKCE để kẻ trộm được code cũng không dùng được.

⏱ ~30 phút 📘 Module 03 · OAuth 2.0 / 2.1 & OpenID Connect

Bài này dùng lại các khái niệm ở Bài 3.1 — Năm ý nền tảng (redirect, consent, scope, authorization code, front/back-channel). Nếu chưa chắc, đọc lại đoạn đó trước.

D. Các flow / grant quan trọng

Trước khi đi sâu một flow, hãy nhìn toàn cảnh: OAuth có nhiều “grant” (cách lấy token) cho các tình huống khác nhau. Bảng và cây quyết định dưới đây giúp bạn biết khi nào dùng cái nào; bài này tập trung vào dòng đầu tiên.

1. Authorization Code Flow Must

Nói đơn giảnGiống gửi đồ ở siêu thị: quầy đưa bạn một phiếu số (authorization code). Phiếu tự nó không phải đồ; nhân viên cửa hàng (backend) phải mang phiếu ra quầy riêng phía sau (token endpoint) và trình thẻ nhân viên (client_secret) mới nhận được đồ (token). Phiếu chỉ dùng một lần và hết hạn nhanh.

Đây là flow nền tảng. Ý tưởng chính gói trong hai câu:

  • Trình duyệt chỉ mang về một authorization code (ngắn hạn, dùng một lần) — không bao giờ mang token.
  • Client đổi code lấy token qua back-channel (gọi thẳng AS); confidential client còn kèm xác thực client (secret).

Ví dụ dưới là PrintNow — confidential web app có backend. Tóm tắt bằng lời trước khi xem sơ đồ:

  1. Đi (front-channel): An bấm “Kết nối PhotoCloud” → PrintNow redirect trình duyệt sang trang đăng nhập của PhotoCloud, kèm “đơn xin” (ai xin, xin quyền gì, trả kết quả về đâu).
  2. Đăng nhập + consent: An đăng nhập trên trang PhotoCloud và bấm “Cho phép”.
  3. Về (front-channel): PhotoCloud redirect trình duyệt về PrintNow kèm code.
  4. Đổi code (back-channel): backend PrintNow gọi thẳng PhotoCloud, nộp code + secret, nhận access token.
  5. Dùng token: PrintNow gọi Photos API kèm access token.

Authorization Code Flow (RFC 6749 §4.1). Token không bao giờ đi qua trình duyệt.

Bước 4–5: Authorization request (browser bị redirect tới AS; xuống dòng chỉ để dễ đọc):

GET https://auth.photocloud.example/authorize
    ?response_type=code
    &client_id=printnow-web
    &redirect_uri=https%3A%2F%2Fprintnow.example%2Fcallback
    &scope=photos.read
    &state=xyzABC123
  • response_type=code — “tôi muốn nhận về một authorization code”.
  • client_id=printnow-web — ai đang xin (định danh công khai, không bí mật).
  • redirect_uri — trả kết quả về đâu; phải khớp chính xác URI đã đăng ký (được URL-encode nên trông rối).
  • scope=photos.read — xin quyền gì; AS hiện quyền này trên màn hình consent.
  • state — giá trị ngẫu nhiên PrintNow lưu trong session, sẽ so lại ở bước 10 (Bài 3.4).

Bước 8: Authorization response — AS redirect về client:

HTTP/1.1 302 Found
Location: https://printnow.example/callback?code=SplxlOBeZQQYbYS6WxSbIA&state=xyzABC123
  • code — authorization code: dùng một lần, sống ngắn, chưa gọi API được.
  • state — phải giống hệt giá trị đã gửi đi; khác → client từ chối.

Bước 11: Token request — backend gọi thẳng token endpoint, xác thực client bằng HTTP Basic (client_id:client_secret base64):

POST /token HTTP/1.1
Host: auth.photocloud.example
Authorization: Basic cHJpbnRub3ctd2ViOnMzY3IzdA==
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&code=SplxlOBeZQQYbYS6WxSbIA&redirect_uri=https%3A%2F%2Fprintnow.example%2Fcallback
  • Authorization: Basic … — base64 của printnow-web:s3cr3t; đây là bước xác thực client (chỉ confidential client làm được). Base64 không phải mã hóa — chỉ an toàn vì đi trên HTTPS.
  • grant_type=authorization_code — “tôi đổi một code”.
  • code — code vừa nhận ở bước 8.
  • redirect_uri — gửi lại đúng giá trị đã dùng ở bước 4; AS kiểm tra khớp (yêu cầu của OAuth 2.0).

Bước 12: Token response:

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store

{
  "access_token": "2YotnFZFEjr1zCsicMWpAA",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "tGzv3JOkF0XG5Qx2TlKWIA",
  "scope": "photos.read"
}
  • access_token — vé gọi API. token_type: Bearer — gửi bằng header Authorization: Bearer ….
  • expires_in: 3600 — vé hết hạn sau 3600 giây (1 giờ).
  • refresh_token — dùng để xin access token mới khi hết hạn (Bài 3.3); chỉ gửi tới AS.
  • scope — quyền thực sự được cấp (có thể ít hơn đã xin). Cache-Control: no-store — cấm cache vì response chứa token.

Bước 13: Gọi API: GET /photos với header Authorization: Bearer 2YotnFZFEjr1zCsicMWpAA (RFC 6750).

⚠️ Authorization Code “trần” (không PKCE) ngày nay chưa đủ Nếu code bị lộ (log, Referer, app độc chiếm custom URI scheme) thì với public client kẻ tấn công đổi code lấy token ngay vì không cần secret; với confidential client vẫn còn nguy cơ code injection. Vì vậy RFC 9700 yêu cầu public client phải dùng PKCE và khuyến nghị cả confidential client cũng dùng; OAuth 2.1 đưa PKCE vào mặc định. → Phần tiếp theo.

⚠️ Hiểu lầm hay gặp

Hiểu lầmCode chỉ sống vài phút và dùng một lần, nên lộ code cũng chẳng sao.Thực tếKẻ tấn công chỉ cần vài giây để đổi code trước app thật. Với public client không PKCE, code lộ = token lộ. “Dùng một lần” chỉ có nghĩa là ai đổi trước người đó thắng.

2. Authorization Code + PKCE Must

Nói đơn giảnNhư xé đôi tấm vé: lúc xin code, app gửi trước cho AS “dấu vân” của nửa vé (code_challenge); nửa vé thật (code_verifier) app giữ trong túi. Lúc đổi code, ai trình được nửa vé khớp dấu vân mới nhận token. Kẻ nhặt được phiếu code nhưng không có nửa vé thì bị từ chối. Giới hạn: “dấu vân” là bản băm SHA-256 — không thể từ nó dựng lại nửa vé.

PKCE (Proof Key for Code Exchange — “bằng chứng khóa khi đổi code”, RFC 7636, đọc là “pixy”) thêm một bí mật dùng-một-lần do chính client instance tạo ra cho mỗi lần đăng nhập (client instance = đúng bản app đang chạy trên máy An lúc đó).

  • Lúc xin code: client gửi bản băm của bí mật.
  • Lúc đổi code: client phải trình bí mật gốc.

Ai trộm được code nhưng không có bí mật gốc thì đổi code thất bại.

Phân biệt dễ nhầm: code_verifier vs code_challenge

Authorization Code + PKCE cho public client (desktop). Không có client_secret. Đây cũng là nội dung Lab 3.

Authorization request thật (gửi tới Keycloak, có cả tham số OIDC nonce vì scope có openid):

GET http://localhost:8080/realms/demo/protocol/openid-connect/auth
    ?response_type=code
    &client_id=demo-client
    &redirect_uri=http%3A%2F%2F127.0.0.1%3A7890%2F
    &scope=openid%20profile%20email%20orders.read
    &state=af0ifjsldkj
    &nonce=n-0S6_WzA2Mj
    &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
    &code_challenge_method=S256

So với request của PrintNow ở trên, phần mới là:

  • scope=openid profile email orders.read — openid bật OIDC (sẽ có ID token); orders.read là quyền gọi demo-api. %20 là dấu cách đã URL-encode.
  • nonce — (OIDC) giá trị ngẫu nhiên, sẽ được chép vào ID token để client kiểm tra.
  • code_challenge — bản băm của verifier (verifier vẫn nằm trong RAM của app).
  • code_challenge_method=S256 — cách băm là SHA-256. Luôn gửi tường minh.
  • redirect_uri=http://127.0.0.1:7890/ — địa chỉ loopback: app WPF tự mở một listener HTTP nhỏ trên máy An để “hứng” callback.

Callback (AS → browser → listener loopback của app). Một số AS (gồm Keycloak bản mới) gửi thêm iss theo RFC 9207 để chống mix-up attack:

HTTP/1.1 302 Found
Location: http://127.0.0.1:7890/?state=af0ifjsldkj&iss=http%3A%2F%2Flocalhost%3A8080%2Frealms%2Fdemo&code=3f1c2a0e-7d.b41e...

Token request — public client: không có client_secret, thay vào đó là code_verifier:

POST /realms/demo/protocol/openid-connect/token HTTP/1.1

(Body thật nằm trên một dòng; tách dòng ở đây cho dễ đọc.)

  • Không có header Authorization: Basic — public client không có secret, chỉ gửi client_id trong body.
  • code_verifier — bí mật gốc. AS tính SHA256 của nó, so với code_challenge đã lưu ở bước xin code; khác → invalid_grant.
  • Callback ở trên có thêm iss — client kiểm tra nó bằng đúng địa chỉ Keycloak mình đã gọi.

PKCE chi tiết (RFC 7636) Must

Thành phầnQuy định (RFC 7636)
code_verifierChuỗi ngẫu nhiên mật mã, độ dài 43–128 ký tự, chỉ gồm ký tự “unreserved”: A-Z a-z 0-9 - . _ ~. Khuyến nghị: sinh 32 byte ngẫu nhiên rồi base64url → đúng 43 ký tự.
code_challenge (S256)BASE64URL-ENCODE(SHA256(ASCII(code_verifier))) — base64url không padding =.
code_challenge (plain)code_challenge = code_verifier. Chỉ được dùng khi client không thể hỗ trợ S256 vì lý do kỹ thuật. OAuth 2.1 (draft) bỏ plain.
code_challenge_methodS256 hoặc plain (mặc định plain nếu không gửi — nên luôn gửi S256 tường minh).
Khi verifier saiToken endpoint trả lỗi invalid_grant.
Vector kiểm thử (Appendix B)verifier dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk → challenge E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM

Vì sao S256 tốt hơn plain?

Với plain, giá trị đi trên front-channel chính là verifier — ai đọc được authorization request (log, proxy, malware) cũng có luôn verifier. Với S256, front-channel chỉ chứa bản băm; SHA-256 một chiều nên không suy ngược ra verifier.

PKCE khác client_secret thế nào?

client_secret là bí mật tĩnh, dùng chung cho mọi bản cài → không giấu được trong public client. PKCE verifier là bí mật động, sinh mới cho mỗi lần đăng nhập, chỉ nằm trong RAM của đúng instance đó → không cần “giấu” trong binary.

Tấn công authorization code interception mà PKCE chặn

Kịch bản kinh điển trên desktop/mobile: app độc cài trên cùng máy đăng ký cùng custom URI scheme (vd. com.demo.app:/callback) hoặc đọc được URL callback (log, Referer, extension). Nó lấy được code — nhưng không có code_verifier nằm trong RAM của app thật.

sequenceDiagram
  autonumber
  participant C as App thật (demo-client)
  participant B as Browser
  participant AZ as Authorization Server
  participant M as 😈 App độc / kẻ nghe lén
  C->>C: verifier V (chỉ ở RAM), challenge = SHA256(V)
  C->>B: Authorization request + code_challenge
  B->>AZ: Đăng nhập thành công
  AZ-->>B: Redirect kèm code
  B-->>M: Code bị chặn (custom scheme trùng, log, Referer)
  M->>AZ: POST /token (code, client_id=demo-client, KHÔNG có V)
  alt Không dùng PKCE
    AZ-->>M: ❌ Cấp token cho kẻ tấn công (public client không có secret)
  else Có PKCE
    AZ-->>M: ✅ 400 invalid_grant - thiếu hoặc sai code_verifier
  end
PKCE ràng buộc code với đúng client instance đã tạo request. Biến thể “code injection” (kẻ tấn công nhét code trộm được vào phiên của chính nó) cũng thất bại vì verifier trong phiên của kẻ tấn công không khớp challenge.
Phân biệt dễ nhầm: Authorization Code vs Authorization Code + PKCE
Tiêu chíAuthorization Code (không PKCE)Authorization Code + PKCE
Tham số thêm—code_challenge + code_challenge_method (xin code), code_verifier (đổi code)
Ai đổi được codeAi có code (+ secret nếu là confidential client)Chỉ instance đang giữ verifier (+ secret nếu có)
Public client❌ Không an toàn: lộ code = lộ token✅ Cách đúng duy nhất
Confidential clientVẫn còn nguy cơ code injection✅ Khuyến nghị (RFC 9700), mặc định trong OAuth 2.1
Chi phíGần như bằng 0: thư viện tự sinh verifier/challenge.

Ví dụ: app độc trên máy An chiếm được callback ?code=3f1c2a0e…. Không PKCE → nó POST code này với client_id=demo-client và nhận token. Có PKCE → nó không có code_verifier → 400 invalid_grant.

PKCE không phải flow mới — chỉ là 3 tham số thêm vào Authorization Code. Luôn bật.
