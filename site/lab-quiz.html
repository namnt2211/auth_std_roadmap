Công cụ: decode JWT ngay trong trang (không gửi đi đâu)

🧪 Decode header & payload của JWT (chạy 100% trong trình duyệt)

Dán access token hoặc ID token từ lab. Công cụ không kiểm tra chữ ký — chỉ để đọc. Thời gian exp/iat được đổi sang giờ địa phương.

🔎 Decode xong thì nhìn vào đâu?
  1. iss — có đúng http://localhost:8080/realms/demo (không phải 127.0.0.1)?
  2. aud — có demo-api không? Nếu là demo-client thì đó là ID token.
  3. azp — client nào xin: worker hay demo-client?
  4. scope — có orders.read không?
  5. exp và claim typ (của Keycloak) — công cụ đã ghi chú sẵn ở phần “Ghi chú”.
Năm điểm này khớp với phần lớn các dòng trong bảng lỗi bên dưới (xem thêm aud vs azp vs scope).

Bảng lỗi mẫu: kịch bản → status → header/log → nguyên nhân → cách sửa

Đây là mẫu cho Deliverable 2 Core. Khi nộp, thay cột “Header/log” bằng giá trị thật bạn bắt được. Bảng này cũng là nguồn cho troubleshooting guide ở M07.

Cách đọc nhanh: nhìn cột Status trước. 401 → vấn đề ở token (thiếu, sai, hết hạn) — đọc error_description và mã IDX. 403 → token ổn, thiếu quyền — đọc log Authorization failed. 500 → API không tải được cấu hình từ Keycloak. Xem lại so sánh 401 vs 403.

Các hiểu lầm cần tránh khi làm lab

Chi tiết và ví dụ nằm ngay dưới từng phần trong bài. Bản tóm tắt:

  • Hiểu lầm: Lỗi audience thì tắt ValidateAudience cho nhanh. → Thực tế: API sẽ nhận cả token dành cho API khác (kể cả ID token); sửa Audience mapper ở IdP. (xem bài)
  • Hiểu lầm: Token hợp lệ nhưng thiếu quyền thì trả 401. → Thực tế: thiếu scope/quyền là 403; 401 là không xác thực được. (xem bài)
  • Hiểu lầm: Revoke token là API lập tức từ chối. → Thực tế: API xác minh JWT cục bộ chấp nhận tới exp (+ ClockSkew). (xem bài)
  • Hiểu lầm: Desktop app nên dùng client secret cho “an toàn hơn”. → Thực tế: secret trong app cài trên máy người dùng không còn bí mật; dùng public client + PKCE. (xem bài)
  • Hiểu lầm: Cứ bật Direct access grants để lấy token cho tiện. → Thực tế: đó là ROPC, bị loại khỏi OAuth 2.1; chỉ dùng client test riêng, xóa sau lab. (xem bài)
  • Hiểu lầm: localhost và 127.0.0.1 như nhau nên redirect URI ghi kiểu nào cũng được. → Thực tế: Keycloak so chuỗi chính xác; hai chuỗi khác nhau bị từ chối. (xem bài)
  • Hiểu lầm: Lỗi “token expired” chỉ xảy ra với token cũ. → Thực tế: đồng hồ máy API lệch quá ClockSkew cũng làm token mới bị báo hết hạn. (xem bài)
  • Hiểu lầm: Bật MapInboundClaims làm hỏng cả policy scope. → Thực tế: claim scope không bị đổi tên; sub và scp (Entra) thì có. (xem bài)
  • Hiểu lầm: Token client credentials không có sub. → Thực tế: có sub của service account; chỉ là không đại diện người thật. (xem bài)
  • Hiểu lầm: code_challenge lộ trên URL là lỗ hổng. → Thực tế: challenge là hash một chiều, được thiết kế để công khai; bí mật là code_verifier. (xem bài)
  • Hiểu lầm: Response SAML đến từ IdP nên SP chỉ cần đọc NameID. → Thực tế: Response đi qua trình duyệt; SP phải kiểm chữ ký, Audience, Destination, Conditions, InResponseTo. (xem bài)

Tóm tắt nhanh

  • Keycloak: realm = không gian riêng có issuer riêng; client public (desktop, PKCE) vs confidential (server, secret).
  • Audience không tự có: Keycloak cần Audience mapper (gắn vào client scope) để aud chứa demo-api.
  • Default client scope luôn áp dụng; Optional chỉ khi client xin trong tham số scope.
  • AddJwtBearer + Authority = tự tải discovery + JWKS, kiểm tra chữ ký, iss, aud, exp cục bộ.
  • Token sai (thiếu, sai aud/iss/chữ ký, hết hạn) → 401 + WWW-Authenticate; token đúng nhưng thiếu quyền → 403.
  • ID token có aud = client → API từ chối. API chỉ nhận access token.
  • MapInboundClaims = false giữ nguyên tên claim; mặc định sub → nameidentifier, scp → .../identity/claims/scope.
  • PKCE: code_challenge đi qua browser, code_verifier chỉ đi back channel. state kiểm callback, nonce kiểm ID token.
  • Client Credentials: token của ứng dụng, không có user, thường không có refresh token.
  • Rotation làm refresh token cũ bị từ chối (invalid_grant); revoke không làm API JWT từ chối access token ngay.

Knowledge Check (tự luận)

Tự trả lời trước, sau đó mở đáp án gợi ý để so sánh.

Vì sao MapInboundClaims = false giúp tránh lỗi policy?

Mặc định handler đổi tên một số claim theo bảng ánh xạ cũ của Microsoft: sub → http://schemas.xmlsoap.org/ws/2005/05/identity/claims/nameidentifier, scp → http://schemas.microsoft.com/identity/claims/scope, email → ClaimTypes.Email… Policy viết theo tên trong token (RequireClaim("sub"), đọc scp) sẽ không tìm thấy claim → 403 dù token đúng. Tắt mapping để tên claim trong ClaimsPrincipal giống hệt trong JWT — điều bạn thấy khi decode là điều code nhận được.

API trả 401 hay 403 khi token hợp lệ nhưng thiếu scope?

403 Forbidden. Authentication đã thành công (biết caller là ai); thất bại ở authorization. Response 403 không mang error="invalid_token". (RFC 6750 có mã insufficient_scope cho trường hợp này; ASP.NET Core mặc định không tự thêm nó vào header — có thể tùy biến nếu muốn.)

API lấy public key để xác minh chữ ký ở đâu, khi nào làm mới?

Từ jwks_uri trong discovery document ({Authority}/.well-known/openid-configuration), ở đây là /realms/demo/protocol/openid-connect/certs. JwtBearer tải lần đầu khi cần, cache lại, làm mới định kỳ (mặc định của ConfigurationManager là theo chu kỳ tính bằng giờ) và làm mới ngay khi gặp token có kid không có trong cache (RefreshOnIssuerKeyNotFound, mặc định bật) — để hỗ trợ xoay vòng khóa.

Vì sao ID token bị API từ chối dù chữ ký hợp lệ?

Vì ID token dành cho client: aud = demo-client, không phải demo-api. Chữ ký chỉ chứng minh “Keycloak đã phát hành token này”, không chứng minh “token này dành cho tôi”. Ngoài ra ID token không mang scope ủy quyền. API phải kiểm tra aud và chỉ nhận access token.
