Bài 3.4 — state, nonce & redirect URI

Flow OAuth đi vòng qua trình duyệt nên có nhiều chỗ kẻ tấn công chen vào được. Bài này giải thích bốn “ổ khóa” nhỏ — state, nonce, PKCE và kiểm tra redirect URI: mỗi cái khóa cửa nào, chặn tấn công gì, và vì sao không được bỏ cái nào.

⏱ ~10 phút 📘 Module 03 · OAuth 2.0 / 2.1 & OpenID Connect
📖 Thuật ngữ trong bài
state
Số ngẫu nhiên client gửi đi và nhận lại ở callback — để chắc callback là của chính phiên đăng nhập này.
nonce
(OIDC) Số ngẫu nhiên được AS chép vào ID token — để chắc ID token sinh ra cho chính request này.
PKCE
Cặp verifier/challenge — để chỉ client đã xin code mới đổi được code (Bài 3.2).
CSRF
Cross-Site Request Forgery: trang lạ khiến trình duyệt của nạn nhân gửi request mà nạn nhân không chủ ý.
Login CSRF
Biến thể CSRF ép nạn nhân bị đăng nhập vào tài khoản của kẻ tấn công.
Replay
Lấy một token/thông điệp hợp lệ cũ và “phát lại” ở nơi khác.
Open redirect
Trang nhận tham số URL rồi redirect tới bất kỳ đâu — kẻ tấn công lợi dụng để đẩy code ra ngoài.
Mix-up attack
Client làm việc với nhiều AS bị lừa gửi code của AS này sang AS khác.

E. PKCE, state, nonce và redirect URI Must

Nói đơn giảnBốn “ổ khóa” cho bốn cánh cửa khác nhau. state = số thứ tự bạn bấm ở quầy: kết quả trả về phải đúng số của bạn. nonce = mã đơn hàng in lên hóa đơn: hóa đơn (ID token) phải ghi đúng mã đơn bạn vừa đặt. PKCE = nửa vé xé đôi: chỉ người giữ nửa vé mới đổi được phiếu. Redirect URI chính xác = địa chỉ giao hàng cố định đã đăng ký: không ai đổi được nơi nhận.

Mỗi cơ chế bảo vệ một thứ khác nhau trong flow. Nói bằng một câu cho từng cái:

  • state bảo vệ callback: “callback này có đúng là kết quả của lần đăng nhập mà trình duyệt này vừa bắt đầu không?”
  • nonce bảo vệ ID token: “ID token này có được tạo cho đúng request của tôi không, hay là token cũ bị đem dùng lại?”
  • PKCE bảo vệ authorization code: “người đang đổi code có phải đúng app đã xin code không?”
  • Redirect URI validation bảo vệ đích đến: “AS có đang gửi code tới đúng địa chỉ đã đăng ký không?”

Bốn cơ chế này liên quan nhưng không thay thế nhau. Bảng chi tiết dưới đây là Deliverable 5:

⚠️ Hiểu lầm hay gặp

Hiểu lầmstate và nonce là một, dùng cái nào cũng được.Thực tếstate bảo vệ authorization response (CSRF), client so ở callback; nonce bảo vệ ID token (replay), client so khi validate ID token. Khác đối tượng, khác nơi kiểm tra. OAuth thuần không có ID token nên nonce không thay được state.

Ví dụ: login CSRF khi thiếu state

Tấn công này nghe ngược đời: kẻ tấn công không lấy tài khoản của nạn nhân, mà ép nạn nhân dùng tài khoản của kẻ tấn công — để mọi thứ nạn nhân tải lên rơi vào tay hắn. Đọc sơ đồ theo các bước:

  1. Kẻ tấn công tự đăng nhập PhotoCloud bằng tài khoản của chính hắn, lấy được một code hợp lệ nhưng không dùng.
  2. Hắn gửi cho nạn nhân một link (hoặc ảnh ẩn) trỏ tới callback của PrintNow kèm code đó.
  3. Nếu PrintNow không kiểm tra state, nó đổi code và liên kết phiên của nạn nhân với tài khoản PhotoCloud của kẻ tấn công.

⚠️ Hiểu lầm hay gặp

Hiểu lầmĐã có PKCE thì bỏ state, bỏ nonce.Thực tếPKCE bảo vệ code. nonce bảo vệ ID token. state vẫn hữu ích cho correlation và là lớp chống CSRF khi không chắc AS thực thi PKCE. Thư viện chuẩn (ASP.NET Core OIDC handler, OidcClient, MSAL) dùng cả ba — đừng tắt.
Hiểu lầmCó gửi tham số state là được, giá trị gì cũng xong (vd. state=printnow).Thực tếstate phải ngẫu nhiên, khó đoán, gắn với phiên trình duyệt và dùng một lần. Giá trị cố định thì kẻ tấn công cũng biết và tự gắn vào link callback giả — coi như không có state.
Hiểu lầmLogin CSRF vô hại vì kẻ tấn công không lấy được tài khoản của nạn nhân.Thực tếHắn không cần: nạn nhân làm việc trong tài khoản của hắn, nên ảnh tải lên, địa chỉ, thẻ thanh toán nạn nhân nhập đều rơi vào tay hắn.

Redirect URI validation

Authorization Server chỉ được gửi code tới URI đã đăng ký trước, so khớp chính xác từng ký tự (scheme, host, port, path, cả dấu / cuối).

🧪 Ví dụ: kẻ tấn công sửa redirect_uri Kẻ tấn công gửi cho An link đăng nhập PhotoCloud “thật”, nhưng sửa một tham số: 
https://auth.photocloud.example/authorize?response_type=code&client_id=printnow-web
    &redirect_uri=https%3A%2F%2Fevil.example%2Fsteal&scope=photos.read
An thấy trang đăng nhập PhotoCloud thật nên yên tâm đăng nhập. Nếu AS không kiểm tra redirect URI, nó sẽ gửi code tới evil.example. AS làm đúng sẽ thấy https://evil.example/steal không nằm trong danh sách đã đăng ký của printnow-web → hiện lỗi, không redirect.
✅ Nên
  • Đăng ký URI đầy đủ: https://printnow.example/signin-oidc.
  • Native/desktop: loopback IP http://127.0.0.1:{port}/ (port động được phép) hoặc claimed HTTPS scheme / private-use scheme dạng reverse-domain (RFC 8252).
  • Tách URI theo môi trường (dev/staging/prod), xóa URI không dùng.
  • Callback page không nhúng script/ảnh bên thứ ba, đặt Referrer-Policy chặt.
❌ Không nên
  • Wildcard: https://*.printnow.example/* — một subdomain bị chiếm (subdomain takeover) là mất code.
  • So khớp tiền tố: https://printnow.example/ cho phép …/open-redirect?to=evil.com.
  • Endpoint trên client nhận tham số returnUrl rồi redirect bừa (open redirect) — biến thành “cầu” đẩy code ra ngoài.
  • Dùng http:// cho domain thật (chỉ loopback mới được HTTP).

⚠️ Hiểu lầm hay gặp

Hiểu lầmCùng domain là đủ: đăng ký https://printnow.example/callback thì …/callback/ hay …/callback?next=/orders cũng phải được nhận.Thực tếOAuth 2.1 / RFC 9700 yêu cầu so khớp chuỗi chính xác — không prefix, không wildcard. Thêm dấu / hay query là một URI khác → AS báo lỗi. Muốn quay về trang cũ thì lưu trang đích trong session (gắn với state), đừng nhét vào redirect URI.
Hiểu lầmClient tự kiểm tra redirect URI ở callback là đủ.Thực tếLúc callback tới client thì đã muộn — code đã được gửi đi. Phải là AS kiểm tra redirect_uri với danh sách đăng ký trước khi hiện trang đăng nhập và trước khi gửi code.
✅ Tự kiểm tra nhanh
  • Client OAuth thuần (không dùng OIDC, không có ID token) có cần nonce không?
  • Ai kiểm tra PKCE: client hay Authorization Server? Còn state?
  • Vì sao đăng ký redirect URI dạng https://*.printnow.example/* là nguy hiểm?
