Lab 4 — Client Credentials, refresh, introspection

Bạn xem token của một ứng dụng (worker, không có người dùng) khác token của alice ra sao, rồi theo dõi vòng đời token: đổi refresh token (rotation), hỏi Keycloak “token này còn sống không?” (introspection) và hủy token (revocation) — và vì sao API vẫn nhận access token đã “hủy”.

⏱ ~20 phút 📘 Lab · Hands-on OAuth/OIDC với ASP.NET Core
📖 Thuật ngữ trong bài
Client Credentials
Grant để một ứng dụng tự xin token cho chính nó bằng client_id + client_secret, không có người dùng, không có trình duyệt.
Service account
User ảo Keycloak gắn với client worker (service-account-worker); token client credentials mang sub của user ảo này.
Refresh token
Token sống lâu hơn, chỉ gửi cho Keycloak để đổi lấy access token mới mà không cần đăng nhập lại. Không bao giờ gửi cho API.
Refresh token rotation
Mỗi lần refresh, Keycloak cấp refresh token mới và vô hiệu cái cũ; dùng lại cái cũ bị từ chối.
Introspection (RFC 7662)
Endpoint để bên có quyền hỏi Keycloak “token này còn hiệu lực không, chứa gì?”.
Revocation (RFC 7009)
Endpoint để client báo Keycloak “hủy token này”.
client_secret_basic / client_secret_post
Hai cách gửi secret: trong header HTTP Basic (curl -u) hoặc trong body form (-d client_secret=…).
Opaque token
Token là chuỗi ngẫu nhiên không đọc được nội dung; API buộc phải hỏi IdP (introspection) mới biết nó hợp lệ không.

Lab 4 — Client Credentials, refresh, introspection

Should⏱ 20 phút

(a) Mục tiêu

Quan sát token không có người dùng thật (Client Credentials), cơ chế refresh token rotation và phát hiện dùng lại, và hai endpoint quản lý vòng đời token: introspection (RFC 7662) và revocation (RFC 7009). Lý thuyết ở M02 — Token lifecycle và M02 — Introspection & Revocation.

Nói đơn giản Access token giống thẻ ra vào có hạn 5 phút. Refresh token giống giấy hẹn đổi thẻ mới ở quầy lễ tân. Với rotation, mỗi lần đổi, lễ tân thu giấy hẹn cũ và đưa giấy mới — ai cầm giấy cũ quay lại là bị phát hiện. Introspection là gọi điện hỏi lễ tân “thẻ này còn hiệu lực không?”. Revocation là báo lễ tân “hủy thẻ/giấy này”. Giới hạn: đầu đọc thẻ ở cửa (API JWT) không gọi điện hỏi lễ tân — thẻ đã hủy vẫn mở được cửa đến khi hết hạn, trừ khi API dùng introspection.

(b) Yêu cầu / đề bài

  1. Lấy token bằng grant_type=client_credentials cho worker, gọi API thành công; chỉ ra các claim cho thấy đây là token của ứng dụng, không phải của người.
  2. Bật refresh token rotation; dùng refresh token (từ Lab 3) để refresh; dùng lại refresh token cũ và ghi lại phản hồi.
  3. Gọi introspection cho access token và refresh token; revoke refresh token; introspect lại; thử gọi API bằng access token cũ.
  4. Nộp: log các lệnh + response (Deliverable 4 — lộ trình Full) và 3 câu kết luận.

(c) Hướng dẫn từng bước

Các lệnh dùng lại biến $KC, $API, $WORKER_SECRET và hàm jwt_payload từ Lab 2 bước 4; DemoApi cần đang chạy. Bước 2–5 cần đã làm Lab 3 (để có refresh token của alice).

  1. Client Credentials. 
    curl -s -X POST "$KC/protocol/openid-connect/token" \
  -u "worker:$WORKER_SECRET" \
  -d grant_type=client_credentials -d scope=orders.read | tee cc.json | jq .
TOK=$(jq -r .access_token cc.json)
jwt_payload "$TOK" | jq '{sub, azp, preferred_username, aud, scope}'
curl -i -H "Authorization: Bearer $TOK" $API/orders
    • Vì sao -u: gửi credential của client bằng HTTP Basic (client_secret_basic) — tương đương -d client_id -d client_secret (client_secret_post). Keycloak chấp nhận cả hai.
    • Kiểm tra: response không có refresh_token (Keycloak mặc định không cấp refresh token cho client credentials — client cứ xin token mới khi cần). Payload: azp = "worker", preferred_username = "service-account-worker", sub là ID của user “service account” gắn với client. API trả 200.
    Phân biệt dễ nhầm: token của worker (Client Credentials) vs token của alice (Auth Code + PKCE)

    Có người đăng nhập → Auth Code + PKCE. Máy gọi máy, không ai ngồi trước màn hình → Client Credentials.

    ⚠️ Hiểu lầm hay gặp

    Hiểu lầmToken client credentials “không có người dùng” nên không có sub và /me sẽ lỗi.Thực tếToken vẫn có sub — của user ảo service-account-worker. /me trả 200 nhưng không có thông tin về người thật nào (không có alice, email của alice…).
    Hiểu lầmWorker chạy job “thay mặt” người bấm nút, nên token của nó đại diện người đó.Thực tếToken chỉ đại diện ứng dụng. Phân quyền dựa trên “app nào”; muốn hành động thay người dùng thì cần token của người dùng (Auth Code), không dùng Client Credentials để giả user.
  2. Bật refresh token rotation. Realm settings → tab Tokens (hoặc Sessions/Tokens tùy phiên bản) → bật Revoke Refresh Token. Trường Refresh Token Max Reuse xuất hiện → để 0 → Save.
    • Vì sao: theo tài liệu Keycloak, khi bật, Keycloak thu hồi refresh token đã dùng và phát hành refresh token mới mà client phải dùng. Max Reuse = số lần một refresh token được dùng lại (0 = chỉ dùng đúng 1 lần).
    • Kiểm tra: chạy lại DemoClient (Lab 3) để có refresh token mới sau khi bật cấu hình (tokens/refresh_token.txt).
  3. Refresh lần 1 (hợp lệ) rồi dùng lại token cũ. 
    RT1=$(cat ../DemoClient/tokens/refresh_token.txt)
refresh() { curl -s -X POST "$KC/protocol/openid-connect/token" \
  -d grant_type=refresh_token -d client_id=demo-client -d refresh_token="$1"; }

refresh "$RT1" | tee r1.json | jq '{has_access: (.access_token != null), refresh_token: (.refresh_token[0:20])}'
RT2=$(jq -r .refresh_token r1.json)

refresh "$RT1" | jq .     # dùng lại RT1 -> bị từ chối
refresh "$RT2" | jq '{has_access: (.access_token != null)}'   # RT2 còn dùng được không? Ghi lại!
    • Vì sao không có secret: demo-client là public client.
    • Kiểm tra: lần dùng lại RT1 trả HTTP 400 với "error": "invalid_grant". error_description (theo mã nguồn Keycloak) là Maximum allowed refresh token reuse exceeded khi dùng lại token đã dùng, hoặc Stale token khi một token mới hơn đã được dùng. Nếu tắt Revoke Refresh Token, dùng lại RT1 sẽ thành công — thử để so sánh.
    ℹ️ “Reuse detection” ở Keycloak khác một số IdP Một số IdP (theo khuyến nghị OAuth Security BCP) khi phát hiện dùng lại sẽ thu hồi cả chuỗi refresh token (kể cả RT2) vì coi là dấu hiệu bị đánh cắp. Hành vi của Keycloak có thể chỉ từ chối token cũ. Hãy tự quan sát lời gọi cuối với RT2 và ghi vào báo cáo — đó chính là mục đích của lab.

    ⚠️ Hiểu lầm hay gặp

    Hiểu lầmRefresh token còn hạn thì dùng lại bao nhiêu lần cũng được.Thực tếĐúng khi tắt rotation. Bật Revoke Refresh Token + Max Reuse = 0 thì mỗi RT chỉ dùng được một lần; dùng lại → 400 invalid_grant dù chưa hết hạn.
  4. Introspection. 
    AT=$(jq -r .access_token r1.json)
curl -s -X POST "$KC/protocol/openid-connect/token/introspect" \
  -u "worker:$WORKER_SECRET" -d token="$AT" | jq '{active, client_id, username, scope, aud, exp, token_type}'
    • Vì sao dùng worker: introspection endpoint yêu cầu bên gọi xác thực (thường là resource server có credential). Public client không nên/không thể gọi.
    • Kiểm tra: "active": true cùng các claim của token. Token rác/hết hạn → chỉ {"active": false}.

    ⚠️ Hiểu lầm hay gặp

    Hiểu lầmAi có token cũng gọi introspection để kiểm tra được, kể cả demo-client.Thực tếIntrospection yêu cầu bên gọi xác thực (thường là resource server có credential). Không gửi credential → 401; vì vậy lab dùng -u worker:secret.
  5. Revocation rồi introspect lại. 
    curl -i -X POST "$KC/protocol/openid-connect/revoke" \
  -d client_id=demo-client -d token="$RT2" -d token_type_hint=refresh_token
# -> HTTP/1.1 200 OK, body rỗng

curl -s -X POST "$KC/protocol/openid-connect/token/introspect" -u "worker:$WORKER_SECRET" -d token="$RT2" | jq .active
refresh "$RT2" | jq .                                    # -> 400 invalid_grant
curl -s -X POST "$KC/protocol/openid-connect/token/introspect" -u "worker:$WORKER_SECRET" -d token="$AT" | jq .active
curl -i -H "Authorization: Bearer $AT" $API/orders      # API JWT vẫn 200 cho tới khi AT hết hạn!
    • Vì sao: RFC 7009 quy định server trả 200 kể cả khi token đã vô hiệu từ trước (để không lộ thông tin). Sau revoke, refresh token chết ngay. Access token có thể vẫn active hoặc không khi introspect (tùy việc Keycloak có đóng phiên client hay không — ghi lại kết quả thực tế), nhưng DemoApi vẫn chấp nhận vì nó xác minh JWT cục bộ, không hỏi Keycloak.
    • Kiểm tra: bạn rút ra được: “muốn thu hồi tức thì ở API → access token ngắn hạn, hoặc API dùng introspection/token tham chiếu (opaque)”.

(f) Câu hỏi tự kiểm tra

Token client_credentials có đại diện cho alice không?

Không. Nó đại diện cho ứng dụng worker (service account). Mọi quyết định phân quyền dựa trên “ứng dụng nào”, không phải “người nào”. Không dùng flow này để giả làm user.

Vì sao revoke xong mà API vẫn nhận access token?

API xác minh JWT cục bộ (chữ ký + exp), không hỏi IdP. Thu hồi chỉ có hiệu lực ở nơi có hỏi IdP (refresh, introspection). Giải pháp: access token ngắn hạn; với tài nguyên nhạy cảm, introspection hoặc token opaque.
