Bài 2.4 — Vòng đời token

Token không sống mãi: nó được cấp, được dùng, hết hạn, được làm mới và có thể bị thu hồi. Bài này giải thích từng giai đoạn đó, cách phát hiện refresh token bị trộm, cách AS thay khóa ký (key rotation), và hai endpoint “hỏi trạng thái token” (introspection) và “hủy token” (revocation).

F. Token lifecycle Must

📖 Thuật ngữ trong bài
Refresh token rotation
Mỗi lần dùng refresh token, AS đưa refresh token mới và vô hiệu cái cũ.
Reuse detection
AS phát hiện một refresh token “đã dùng rồi” bị gửi lại → nghi bị trộm → hủy cả chuỗi.
Grant
Một lần người dùng/ứng dụng được cấp quyền; các token sinh ra từ lần đó thuộc cùng một “họ”.
Signing key / key rotation
Khóa riêng AS dùng để ký token / việc định kỳ thay khóa đó bằng khóa mới.
Introspection
API hỏi AS: “token này còn hiệu lực không, của ai?”.
Revocation
Client báo AS: “hủy token này giúp tôi”.
Nói đơn giản Thẻ ra vào (access token) hết hạn sau 5 phút → mang giấy hẹn (refresh token) ra lễ tân đổi thẻ mới. Mỗi lần đổi, lễ tân thu giấy hẹn cũ, đưa giấy hẹn mới (rotation). Nếu ai đó mang tới một giấy hẹn đã bị thu, lễ tân biết có kẻ sao chép → hủy luôn cả chuỗi giấy hẹn (reuse detection).

Vòng đời: cấp → sử dụng → hết hạn → refresh → revoke.

  • Access token có thời hạn ngắn hơn refresh token. Lý do: access token được gửi đi rất nhiều lần (mỗi request tới API) nên dễ lộ hơn; hạn ngắn giới hạn thiệt hại nếu lộ.
  • Refresh token rotation: mỗi lần dùng refresh token, AS cấp refresh token mới và vô hiệu cái cũ. Mỗi refresh token chỉ dùng được một lần.
  • Reuse detection: nếu refresh token cũ (đã dùng) bị gửi lại → dấu hiệu có hai bên cùng giữ nó, tức là bị đánh cắp → AS thu hồi toàn bộ refresh token thuộc cùng grant/phiên.
  • RFC 9700 (OAuth 2.0 Security Best Current Practice — tài liệu “thực hành bảo mật tốt nhất” của OAuth) yêu cầu refresh token của public client (app không giữ được secret: SPA, mobile, desktop) phải được ràng buộc với bên gửi (sender-constrained) hoặc dùng rotation.

Sơ đồ dưới kể một câu chuyện: hr-web dùng token bình thường, rồi một kẻ tấn công thử dùng refresh token đã trộm. Hãy để ý dòng “phát hiện REUSE”.

Rotation + reuse detection biến việc trộm refresh token thành sự kiện phát hiện được. Cái giá: người dùng thật cũng bị đăng xuất.
ℹ️ Trong Keycloak Rotation được bật bằng tùy chọn Revoke Refresh Token trong cấu hình token của realm, kết hợp Refresh Token Max Reuse = 0 (mỗi refresh token chỉ dùng một lần). Hệ quả thực tế: nhiều tab/nhiều instance dùng chung một refresh token sẽ “giành” nhau — cần thiết kế để chỉ một nơi refresh. Vị trí menu có thể thay đổi theo phiên bản.

Logout có vô hiệu hóa token ngay không?

Không mặc định. Logout thường hủy phiên ở IdP và thu hồi refresh token. Nhưng một JWT access token đã phát hành vẫn verify được cho tới exp, vì API kiểm tra cục bộ và không hỏi ai.

Nếu cần token “chết” ngay, có các lựa chọn (tùy kiến trúc mà chọn):

  • Access token thật ngắn (vài phút) — chấp nhận độ trễ nhỏ.
  • Introspection (hoặc opaque token) cho API nhạy cảm.
  • Denylist (danh sách chặn) theo jti (mã token) hoặc sid (mã phiên).
  • Cơ chế đặc thù của IdP.

Hết hạn là “tự chết theo giờ”; thu hồi là “bị hủy theo yêu cầu”; logout là “kết thúc phiên” — chỉ hết hạn là chắc chắn có hiệu lực với JWT ở mọi API.

Key rotation (xoay vòng signing key) Should

  • Issuer định kỳ thay signing key (hoặc thay gấp khi lộ key). Public key được công bố ở JWKS (JSON Web Key Set) endpoint, mỗi key có kid — chi tiết ở M03 — Discovery/JWKS.
  • Quy trình an toàn (rollover — chuyển giao từ key cũ sang key mới):
    1. Công bố key mới trong JWKS trước.
    2. Bắt đầu ký token bằng key mới.
    3. Giữ key cũ trong JWKS tới khi mọi token ký bằng key cũ đã hết hạn.
    4. Gỡ key cũ.
  • API phải: cache JWKS, chọn key theo kid, và khi gặp kid lạ thì làm mới JWKS (có giới hạn tần suất) thay vì từ chối mãi. Không hard-code public key vào code. Middleware JwtBearer với Authority làm việc này tự động.

Ví dụ JWKS của realm kaopiz trong giai đoạn chuyển giao: có cả hai key, nên token ký bằng key cũ (hr-2026-08) lẫn key mới (hr-2026-11) đều verify được.

  "keys": [

Token Introspection (RFC 7662) và Revocation (RFC 7009) Should

Nói đơn giản Introspection: bảo vệ ở cửa gọi điện hỏi lễ tân “thẻ số này còn hiệu lực không, của ai?”. Revocation: khách (client) báo lễ tân hủy thẻ vì đã về hoặc làm mất.

Introspection: Resource Server (API) hỏi Authorization Server: token còn hiệu lực (active) không, và mang thông tin gì.

  • Dùng khi: token là opaque (API không tự đọc được), hoặc API cần biết ngay token đã bị thu hồi chưa.
  • Khi gọi, API phải tự xác thực với AS (vd. bằng client_id/client_secret của hr-api) — để người lạ không dùng endpoint này dò token.

  C->>API: GET /payroll/57 + Bearer token
  API->>AS: POST /introspect (token=..., xác thực bằng credential của hr-api)

Introspection = độ chính xác tức thời đổi lấy một lần gọi mạng (và phụ thuộc AS còn sống).

Request thực tế dưới đây do hr-api gửi lên Keycloak. Để ý: hr-api đăng nhập bằng header Basic (credential của chính hr-api), còn token cần hỏi nằm ở body.

Revocation: client báo AS thu hồi refresh token hoặc access token — ví dụ khi logout hoặc mất thiết bị. Request dưới do hr-web gửi khi An bấm Đăng xuất.

POST /realms/kaopiz/protocol/openid-connect/revoke HTTP/1.1
Host: sso.kaopiz.local
Content-Type: application/x-www-form-urlencoded
Authorization: Basic <base64(client_id:client_secret)>

token=<refresh_token>&token_type_hint=refresh_token
  • token_type_hint (tùy chọn): access_token hoặc refresh_token; AS có thể bỏ qua.
  • Thành công → HTTP 200. Token không hợp lệ/không tồn tại cũng trả 200 (mục đích “token không còn dùng được” đã đạt).
  • Thu hồi refresh token: nếu AS hỗ trợ thu hồi access token thì nên thu hồi luôn các access token cùng grant. Nhưng JWT access token đã nằm ở API vẫn verify được cục bộ cho tới khi hết hạn nếu API không introspect.

Revocation = client “báo mất thẻ”; introspection = bảo vệ “gọi hỏi thẻ còn dùng được không”.
