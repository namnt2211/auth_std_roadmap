Pipeline ASP.NET Core: UseAuthentication → UseAuthorization → endpoint

Nói đơn giản Hãy hình dung cổng một tòa nhà có hai trạm. Trạm 1 (UseAuthentication) đọc thẻ của bạn để biết bạn là ai. Trạm 2 (UseAuthorization) xem danh sách phòng bạn được vào. Nếu trạm 2 đứng trước trạm 1, nó sẽ thấy mọi người đều “không có thẻ” và chặn hết.

Thuật ngữ: middleware là các bước xử lý request nối tiếp nhau trong ASP.NET Core; scheme là một cách xác thực có tên (ví dụ “Cookies”, “Bearer”, “oidc”), mỗi scheme có một handler thực hiện.

UseAuthentication gọi handler của default authenticate scheme để dựng HttpContext.User (từ cookie hoặc header Authorization: Bearer). UseAuthorization đọc metadata của endpoint ([Authorize], policy) và quyết định: cho qua, Challenge (chưa xác thực) hay Forbid (đã xác thực nhưng thiếu quyền). Phản hồi cụ thể của Challenge/Forbid do handler của scheme tương ứng quyết định.

Default / challenge / forbid scheme

Nói đơn giản App có thể có nhiều “cửa đăng nhập” (cookie cho web, Bearer token cho API, OIDC để chuyển sang IdP). Các Default scheme là bảng chỉ dẫn: đọc thẻ bằng cửa nào, khi khách chưa có thẻ thì đưa họ đến cửa nào (challenge), và khi khách có thẻ nhưng sai phòng thì báo thế nào (forbid).
  • Challenge: phản hồi khi người dùng chưa đăng nhập → API trả 401, web app chuyển hướng sang trang login.
  • Forbid: phản hồi khi đã đăng nhập nhưng không đủ quyền → 403 hoặc trang “Access denied”.

builder.Services.AddAuthentication(options =>
{
    options.DefaultScheme = CookieAuthenticationDefaults.AuthenticationScheme;      // "Cookies"
    options.DefaultChallengeScheme = OpenIdConnectDefaults.AuthenticationScheme;    // "OpenIdConnect"
})
.AddCookie(o =>
{
    o.Cookie.SameSite = SameSiteMode.Lax;
    o.Cookie.SecurePolicy = CookieSecurePolicy.Always;
})
.AddOpenIdConnect(o =>
{
    o.Authority = builder.Configuration["Oidc:Authority"];   // vd. https://localhost:8443/realms/demo
    o.ClientId = "hr-web";
    o.ClientSecret = builder.Configuration["Oidc:ClientSecret"];   // confidential client: secret ở server
    o.ResponseType = OpenIdConnectResponseType.Code;            // Authorization Code
    o.UsePkce = true;
    o.SaveTokens = true;                                         // lưu access/refresh token trong ticket
    o.MapInboundClaims = false;                                  // giữ nguyên "sub", "name"...
    o.Scope.Add("orders.read");
});

var app = builder.Build();
app.UseRouting();
app.UseAuthentication();   // 1. dựng HttpContext.User
app.UseAuthorization();    // 2. kiểm tra policy
app.MapControllers();
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(o =>
    {
        o.Authority = builder.Configuration["Jwt:Authority"];   // tự tải discovery + JWKS
        o.Audience  = "orders-api";                              // kiểm tra "aud"
        o.MapInboundClaims = false;
        o.TokenValidationParameters.ClockSkew = TimeSpan.FromMinutes(1);
    });

builder.Services.AddAuthorization(o =>
{
    // "scope" (Keycloak) là MỘT chuỗi nhiều giá trị: "openid orders.read" → phải tách theo dấu cách
    o.AddPolicy("orders.read", p => p.RequireAuthenticatedUser()
        .RequireAssertion(ctx => ctx.User.FindAll("scope")
            .SelectMany(c => c.Value.Split(' '))
            .Contains("orders.read")));
});

app.MapGet("/orders", () => Results.Ok())
   .RequireAuthorization("orders.read");
ℹ️ Claim scope là chuỗi cách nhau bởi dấu cách Nhiều IdP (Keycloak, Duende) phát "scope": "openid orders.read" dạng một chuỗi. RequireClaim("scope", "orders.read") chỉ khớp khi giá trị claim bằng đúng chuỗi đó — nên với chuỗi nhiều scope cần RequireAssertion tách theo dấu cách (như code trên) hoặc dùng handler tùy biến. Entra ID dùng claim scp cho delegated permission và roles cho app permission. Kiểm tra token thật ở Lab 2.

1. Sai thứ tự hoặc thiếu UseAuthentication()

Triệu chứngGửi token hợp lệ nhưng mọi endpoint [Authorize] vẫn trả 401 / redirect login; User.Identity.IsAuthenticated == false trong controller.
Nguyên nhânUseAuthorization() chạy khi HttpContext.User chưa được dựng (vì UseAuthentication() đứng sau hoặc bị thiếu). Lưu ý: WebApplication chỉ tự chèn UseAuthentication khi bạn không tự gọi nó; một khi đã gọi tường minh thì thứ tự là trách nhiệm của bạn.
❌ Sai
app.UseRouting();
app.UseAuthorization();   // chạy trước → User rỗng
app.UseAuthentication();
app.MapControllers();
✅ Đúng
app.UseRouting();
app.UseCors();            // nếu dùng CORS
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

2. Policy kiểm tra sub/scp/roles nhưng claim đã bị đổi tên

Nói đơn giản Token ghi “sub = 57”, nhưng .NET mặc định “dịch” tên trường sang một cái tên dài kiểu cũ của Microsoft trước khi đưa cho bạn. Bạn tìm “sub” thì không thấy, dù dữ liệu vẫn ở đó — chỉ là bị đổi nhãn.
Triệu chứngToken chắc chắn có "sub" (đã xem trên jwt.io) nhưng User.FindFirst("sub") trả null; với token Entra ID, policy RequireClaim("scp", …) luôn 403. Debug thấy claim type kiểu http://schemas.xmlsoap.org/ws/2005/05/identity/claims/nameidentifier.
Nguyên nhânInbound claim mapping mặc định (MapInboundClaims = true) đổi tên các claim JWT theo bảng ClaimTypeMapping của Microsoft.IdentityModel: sub → ClaimTypes.NameIdentifier, roles/role → ClaimTypes.Role, scp → http://schemas.microsoft.com/identity/claims/scope. Claim scope (Keycloak) không nằm trong bảng nên giữ nguyên tên — nếu policy theo scope vẫn 403 thì nguyên nhân thường là chuỗi nhiều scope (xem callout ở trên), không phải mapping.
❌ Sai
.AddJwtBearer(o =>
{
    o.Authority = authority;
    o.Audience = "orders-api";
    // MapInboundClaims mặc định = true
});
// ...
var userId = User.FindFirst("sub")?.Value; // null!
✅ Đúng
.AddJwtBearer(o =>
{
    o.Authority = authority;
    o.Audience = "orders-api";
    o.MapInboundClaims = false;          // giữ tên claim gốc
    o.TokenValidationParameters.NameClaimType = "name";
    o.TokenValidationParameters.RoleClaimType = "roles";
});
var userId = User.FindFirst("sub")?.Value; // OK

3. Nhiều scheme nhưng không chỉ định default/challenge → API bị redirect login thay vì 401

Triệu chứngGọi GET /api/orders từ SPA/Postman không token nhận 302 Found → /Account/Login (hoặc trang login IdP, kèm lỗi CORS ở browser) thay vì 401. Hoặc ngược lại: gửi Bearer token hợp lệ vẫn 401 vì endpoint chỉ authenticate bằng cookie.
Nguyên nhânApp lai (MVC + API) đăng ký Cookie, OIDC và JwtBearer nhưng default scheme là Cookie/OIDC → Challenge cho API dùng handler cookie/OIDC (redirect). Bearer handler không bao giờ được gọi cho endpoint API.
❌ Sai
builder.Services.AddAuthentication(o =>
{
    o.DefaultScheme = "Cookies";
    o.DefaultChallengeScheme = "oidc";
})
.AddCookie().AddOpenIdConnect("oidc", ...)
.AddJwtBearer();

[Authorize]                // dùng default = Cookies/oidc
[ApiController]
public class OrdersController : ControllerBase { }
✅ Đúng
// Cách 1: chỉ định scheme cho API
[Authorize(AuthenticationSchemes =
    JwtBearerDefaults.AuthenticationScheme)]
public class OrdersController : ControllerBase { }

// Cách 2: policy scheme chọn theo request
.AddPolicyScheme("smart", "Cookie or Bearer", o =>
{
    o.ForwardDefaultSelector = ctx =>
        ctx.Request.Path.StartsWithSegments("/api")
            ? JwtBearerDefaults.AuthenticationScheme
            : CookieAuthenticationDefaults.AuthenticationScheme;
});
// và đặt DefaultScheme = "smart"

4. Data Protection key không được chia sẻ giữa các instance

Nói đơn giản Cookie đăng nhập giống một phong bì được niêm phong bằng con dấu riêng của server. Nếu có 3 server mà mỗi cái dùng một con dấu khác nhau, phong bì do server A niêm phong sẽ bị server B coi là giả → người dùng bị đá ra ngoài. Giải pháp: cả 3 dùng chung một bộ con dấu (key ring).
Triệu chứngNgười dùng bị đăng xuất ngẫu nhiên sau load balancing hoặc sau mỗi lần deploy/restart container; log có CryptographicException: The key {…} was not found in the key ring; OIDC callback lỗi “Correlation failed” / “Unable to unprotect the message.State”.
Nguyên nhânMỗi instance tự sinh key ring riêng (thường trong thư mục tạm của container, mất khi redeploy). Cookie do instance A ký/mã hóa thì instance B không giải được.
❌ Sai
// Không cấu hình gì: key lưu cục bộ từng instance
builder.Services.AddAuthentication().AddCookie();
// chạy 3 replica sau load balancer
✅ Đúng
builder.Services.AddDataProtection()
    .SetApplicationName("kaopiz-hr")          // giống nhau ở mọi instance
    .PersistKeysToFileSystem(new DirectoryInfo(@"\\fileshare\dp-keys"))
    .ProtectKeysWithCertificate(cert);        // mã hóa key at rest
// hoặc PersistKeysToDbContext / Azure Blob + Key Vault / Redis

5. RequireHttpsMetadata = false hoặc tắt validate aud/iss trong dev rồi lọt lên production

Triệu chứngKhông có lỗi nào — đó chính là vấn đề. API chấp nhận token phát cho API khác (sai aud) hoặc từ issuer khác; metadata/JWKS có thể bị tải qua HTTP không mã hóa. Thường chỉ lộ ra khi pentest hoặc review.
Nguyên nhânLúc dev dùng Keycloak HTTP / token test không có aud nên “tạm tắt” validation, cấu hình không phân biệt môi trường. Xem lại checklist JWT validation.
❌ Sai
.AddJwtBearer(o =>
{
    o.Authority = "http://keycloak:8080/realms/demo";
    o.RequireHttpsMetadata = false;
    o.TokenValidationParameters = new()
    {
        ValidateAudience = false,   // "tạm thời"
        ValidateIssuer = false
    };
});
✅ Đúng
.AddJwtBearer(o =>
{
    o.Authority = builder.Configuration["Jwt:Authority"]; // https ở prod
    o.Audience  = "orders-api";
    // chỉ nới lỏng khi đang chạy Development
    o.RequireHttpsMetadata = !builder.Environment.IsDevelopment();
    // KHÔNG tắt ValidateAudience / ValidateIssuer;
    // cấu hình IdP thêm audience mapper cho đúng
});
✅ Mẹo chống lọt cấu hình dev Viết một integration test gửi token có aud sai và kỳ vọng 401; chạy trong CI. Đây chính là kịch bản 2 trong Lab 2.

C. Nội dung nâng cao chưa đào sâu trong 15 giờ Nice

Nói đơn giản Phần lớn chủ đề dưới đây trả lời một trong ba câu hỏi: (1) làm sao để token bị trộm vẫn vô dụng (DPoP, mTLS), (2) làm sao để yêu cầu đăng nhập không bị sửa giữa đường (PAR, JAR, JARM), (3) làm sao để quản lý danh tính ở quy mô lớn (Federation, SCIM, IGA, CAE). Chỉ cần nhớ câu hỏi, chi tiết tra spec khi cần.

Để giữ đúng giới hạn thời lượng, các chủ đề sau chỉ cần biết tên, biết nó giải quyết vấn đề gì. Đây không phải các chủ đề không quan trọng; chúng được tách ra vì cần thời gian riêng để học đúng chiều sâu.

Gợi ý kịch bản demo (30 phút, buổi 2)

Tóm tắt nhanh

  • Trong ASP.NET Core: UseAuthentication() phải chạy trước UseAuthorization(); CORS đặt trước cả hai.
  • Web app thường dùng Cookie + OIDC; Web API dùng JwtBearer với Authority + Audience.
  • Challenge = “chưa đăng nhập” (401/redirect login); Forbid = “thiếu quyền” (403). Phản hồi cụ thể do scheme quyết định.
  • Đặt MapInboundClaims = false để giữ nguyên tên claim gốc (sub, scp, roles…); claim scope của Keycloak vốn không bị đổi tên nhưng là chuỗi nhiều scope cách nhau dấu cách.
  • Chạy nhiều instance → chia sẻ Data Protection key ring; không bao giờ tắt kiểm tra aud/iss ở production.
  • ASP.NET Core Identity băm mật khẩu bằng PBKDF2-HMAC-SHA512 (100.000 vòng mặc định) và hỗ trợ passkey từ .NET 10.
  • Chủ đề nâng cao (DPoP, PAR, RAR, Token Exchange, FAPI 2.0…) chỉ cần biết tên và vấn đề chúng giải quyết.

Adversary-in-the-Middle — kẻ tấn công đứng giữa		Trang phishing đứng giữa người dùng và trang login thật, chuyển tiếp mọi thứ rồi cướp session cookie sau khi bạn đăng nhập xong. Vượt qua được cả mã OTP và push. Passkey chống được.
Ví dụ: link giả micros0ft-login.com hiển thị đúng trang Microsoft.		M06
API key
khóa API		Một chuỗi bí mật cố định để nhận diện ứng dụng gọi API. Thường không gắn với người dùng và không tự hết hạn, nên cần đổi định kỳ.
Ví dụ: header X-Api-Key: sk_live_... khi gọi dịch vụ gửi email.		M02
Assertion (SAML)
bản xác nhận		“Giấy xác nhận” có chữ ký của IdP, nói rằng người này là ai, đã đăng nhập lúc nào, giấy dành cho ứng dụng nào, có hiệu lực đến khi nào.
Ví dụ: phần <saml:Assertion> trong SAML Response.		M04
Audience (aud)
người nhận dự kiến		Ghi trong token: token này được phát cho ai dùng. API phải từ chối token không ghi tên mình.
Ví dụ: token có "aud": "payroll-api" gửi tới orders-api → 401.		M02
Authentication (AuthN)
xác thực		Trả lời câu hỏi “Bạn có đúng là người bạn khai không?” bằng cách kiểm tra bằng chứng. Thất bại thường trả HTTP 401.
Ví dụ: nhập mật khẩu + bấm xác nhận trên điện thoại.		M01
Authorization (AuthZ)
phân quyền / ủy quyền		Trả lời câu hỏi “Bạn được làm gì?” sau khi đã biết bạn là ai. Thiếu quyền trả HTTP 403.
Ví dụ: An xem được bảng lương của mình, không xem được của đồng nghiệp.		M01
Authorization Code Flow
luồng mã ủy quyền		Cách đăng nhập chuẩn của OAuth/OIDC: browser chỉ mang về một mã dùng một lần, rồi ứng dụng đổi mã đó lấy token qua kênh riêng. Luôn đi kèm PKCE.
Ví dụ: bấm “Đăng nhập bằng Microsoft” → về /callback?code=....		M03
Authorization Server (AS)
máy chủ cấp quyền		Nơi người dùng đăng nhập và nơi phát hành token theo OAuth.
Ví dụ: Keycloak, Microsoft Entra ID.		M03
Bearer token
token “người mang”		Token mà ai cầm được cũng dùng được, giống tiền mặt. Vì vậy phải giữ kỹ và chỉ gửi qua HTTPS.
Ví dụ: lộ access token trong log → kẻ khác gọi được API đến khi token hết hạn.		M02
BFF
Backend for Frontend		Một backend nhỏ đứng sau SPA, giữ token thay cho browser. Browser chỉ giữ một cookie an toàn, nên JavaScript độc không lấy được token.
Ví dụ: React gọi /bff/api/orders, BFF gắn token rồi gọi API thật.		M07
Claim
thông tin khai báo		Một mẩu thông tin dạng “tên = giá trị” về người dùng, nằm trong token.
Ví dụ: "sub": "57", "email": "an@company.com", "roles": ["manager"].		M02
ClaimsPrincipal
người dùng hiện tại trong .NET		Đối tượng .NET chứa người dùng đang gọi request và các claim của họ, đọc qua HttpContext.User.
Ví dụ: User.FindFirst("sub")?.Value.		Phụ lục
Client (confidential / public)
ứng dụng khách		Ứng dụng xin token. Confidential chạy trên server nên giữ được bí mật (secret). Public chạy trên máy người dùng nên không giữ được bí mật.
Ví dụ: web MVC = confidential; SPA, app WPF, app mobile = public.		M03
Client Credentials
luồng thông tin xác thực của client		Cách một dịch vụ tự xin token cho chính nó, không có người dùng tham gia.
Ví dụ: job đồng bộ dữ liệu ban đêm gọi API báo cáo.		M03
Cookie attributes
thuộc tính cookie		Các “nhãn an toàn” trên cookie. HttpOnly: JavaScript không đọc được. Secure: chỉ gửi qua HTTPS. SameSite: hạn chế gửi kèm khi request đến từ trang khác.
Ví dụ: Set-Cookie: sid=abc; HttpOnly; Secure; SameSite=Lax.		M02
CORS
Cross-Origin Resource Sharing		Quy tắc của browser cho phép trang ở domain khác gọi API của bạn. CORS không xác thực ai và không phân quyền gì.
Ví dụ: cho https://spa.example.com gọi https://api.example.com.		Phụ lục
Credential
bằng chứng xác thực		Thứ bạn đưa ra để chứng minh mình là ai.
Ví dụ: mật khẩu, passkey, smart card, chứng thư số.		M01
CSRF
Cross-Site Request Forgery — giả mạo request từ trang khác		Trang độc lừa browser gửi request tới app của bạn, browser tự gửi kèm cookie nên app tưởng chính bạn bấm.
Ví dụ: mở trang lạ, nó âm thầm submit form “chuyển tiền” tới ngân hàng bạn đang đăng nhập. Chống bằng antiforgery token, SameSite.		M06
Data Protection (.NET)
bộ mã hóa dữ liệu của ASP.NET Core		Cơ chế ASP.NET Core dùng để mã hóa và ký cookie đăng nhập. Mọi server chạy cùng app phải dùng chung bộ khóa.
Ví dụ: 3 server không chung khóa → người dùng bị đăng xuất ngẫu nhiên.		Phụ lục
Device Authorization Grant
luồng đăng nhập cho thiết bị		Đăng nhập cho thiết bị khó gõ phím: thiết bị hiện một mã ngắn, bạn nhập mã đó trên điện thoại để xác nhận.
Ví dụ: đăng nhập YouTube trên Smart TV, hoặc az login --use-device-code.		M03
Discovery & JWKS
tài liệu khám phá & bộ khóa công khai		Discovery là “danh thiếp” của IdP (các địa chỉ endpoint). JWKS là danh sách public key để kiểm chữ ký token.
Ví dụ: /.well-known/openid-configuration chứa jwks_uri.		M03
DPoP
Demonstrating Proof of Possession — chứng minh sở hữu khóa		Gắn token với một khóa bí mật của client. Kẻ trộm có token mà không có khóa thì vẫn không dùng được.
Ví dụ: mỗi request gửi kèm header DPoP ký bằng khóa của app.		Phụ lục
Federation
liên kết danh tính		Hai tổ chức tin nhau, chấp nhận việc đăng nhập do bên kia thực hiện.
Ví dụ: nhân viên đối tác đăng nhập vào hệ thống của bạn bằng tài khoản công ty họ.		M01
Hash vs Encryption
băm vs mã hóa		Hash là “xay nhuyễn” một chiều, không đảo ngược được. Encryption là “khóa két”, có chìa thì mở lại được. Mật khẩu phải hash, không mã hóa.
Ví dụ: DB lưu AQAAAAIAAYag... (hash), không lưu mật khẩu gốc.		M02
HMAC
Hash-based Message Authentication Code		“Con dấu” tạo từ một khóa bí mật dùng chung. Bên nhận có cùng khóa sẽ biết dữ liệu không bị sửa và do bên kia gửi.
Ví dụ: JWT ký HS256; webhook kèm header chữ ký HMAC.		M02
ID token
token danh tính		“Giấy báo kết quả đăng nhập” mà OIDC gửi cho ứng dụng: ai vừa đăng nhập, lúc nào, bằng cách nào. Không dùng để gọi API.
Ví dụ: app đọc name trong ID token để hiện “Xin chào An”.		M03
Identity
danh tính		Tập thông tin mô tả một người/thực thể trong một bối cảnh.
Ví dụ: “An — kỹ sư R&D, mã NV 1024” trong công ty.		M01
Identity Provider (IdP)
nhà cung cấp danh tính		Hệ thống lo việc đăng nhập thay cho các ứng dụng, rồi báo kết quả cho chúng.
Ví dụ: Entra ID, Google, Okta, Keycloak.		M01
Introspection / Revocation
tra cứu / thu hồi token		Introspection: API hỏi lại IdP “token này còn dùng được không?”. Revocation: yêu cầu IdP hủy token.
Ví dụ: người dùng bấm “Đăng xuất mọi thiết bị” → refresh token bị thu hồi.		M02
Issuer (iss) + Subject (sub)
bên phát hành + mã người dùng		iss cho biết IdP nào phát token; sub là mã cố định của người dùng tại IdP đó. Cặp này mới là khóa nhận diện người dùng đáng tin, không phải email.
Ví dụ: iss = https://login.example.com, sub = 8f2c....		M03
JWT
JSON Web Token		Định dạng token gồm 3 phần header.payload.signature. Ai cũng đọc được nội dung; chữ ký chỉ chứng minh không bị sửa, không giữ bí mật.
Ví dụ: dán token vào jwt.io là đọc được sub, exp.		M02
Kerberos
giao thức xác thực bằng vé		Đăng nhập một lần vào domain, sau đó hệ thống cấp “vé” để vào từng dịch vụ mà không phải gõ lại mật khẩu.
Ví dụ: mở thư mục chia sẻ \\fileserver trong công ty không bị hỏi mật khẩu.		M05
LDAP
Lightweight Directory Access Protocol		Giao thức để tra cứu danh bạ (user, group, phòng ban). Có thể dùng để kiểm mật khẩu nhưng không phải giao thức SSO như OIDC.
Ví dụ: app tìm “các thành viên group HR” trong AD qua LDAP.		M05
MFA
Multi-Factor Authentication — xác thực đa yếu tố		Đăng nhập bằng ít nhất 2 loại bằng chứng khác nhóm: thứ bạn biết, thứ bạn có, thứ thuộc về bạn.
Ví dụ: mật khẩu + mã trên app điện thoại. Hai mật khẩu thì không phải MFA.		M01
mTLS
mutual TLS — TLS hai chiều		Kết nối HTTPS mà cả hai bên đều trình chứng thư, không chỉ server. Dùng để các dịch vụ nhận diện nhau. Nó chứng minh “ai đang gọi”, không quyết định “được làm gì”.
Ví dụ: service A gọi service B trong mạng nội bộ bằng chứng thư riêng.		M07
Nonce
số dùng một lần		Giá trị ngẫu nhiên app tạo khi bắt đầu đăng nhập và kiểm lại trong ID token, để không ai dùng lại ID token cũ.
Ví dụ: request có nonce=x7k2 → ID token phải có "nonce": "x7k2".		M03
NTLM
NT LAN Manager		Cách đăng nhập cũ của Windows dựa trên thách đố–trả lời. Yếu hơn Kerberos, chỉ dùng khi không có lựa chọn khác.
Ví dụ: truy cập máy chủ bằng địa chỉ IP thay vì tên thường rơi về NTLM.		M05
OAuth 2.0
khung ủy quyền mở		Chuẩn để một ứng dụng xin quyền truy cập API thay mặt người dùng mà không cần biết mật khẩu của họ. Bản thân OAuth không phải chuẩn đăng nhập.
Ví dụ: cho app lịch quyền đọc Google Calendar của bạn.		M03
OAuth 2.1
phiên bản hợp nhất (đang là draft)		Bản “dọn dẹp” OAuth 2.0: bắt buộc PKCE, bỏ các luồng không an toàn (Implicit, ROPC), redirect URI phải khớp chính xác.
Ví dụ: thiết kế mới nên tuân theo các quy tắc này ngay cả khi 2.1 chưa thành RFC.		M03
OpenID Connect (OIDC)
lớp đăng nhập trên OAuth		Chuẩn đăng nhập xây trên OAuth 2.0: thêm ID token để ứng dụng biết ai vừa đăng nhập.
Ví dụ: nút “Sign in with Google/Microsoft” trên hầu hết website.		M03
Passkey
khóa truy cập thay mật khẩu		Đăng nhập không mật khẩu: thiết bị giữ một khóa bí mật, mở bằng vân tay/khuôn mặt/PIN. Khóa chỉ hoạt động với đúng website đã đăng ký nên trang giả không lừa được.
Ví dụ: đăng nhập GitHub bằng Face ID.		M05
Password hashing
băm mật khẩu		Lưu mật khẩu bằng thuật toán cố tình chậm và có salt, để kẻ trộm DB khó đoán ngược.
Ví dụ: Argon2id, bcrypt, PBKDF2 (ASP.NET Core Identity). Không dùng SHA-256 đơn thuần.		M02
PKCE
Proof Key for Code Exchange, đọc là “pixy”		App tạo một bí mật ngẫu nhiên, gửi trước bản băm của nó, rồi trình bí mật gốc khi đổi code. Kẻ trộm được code cũng không đổi được token.
Ví dụ: code_challenge trong URL đăng nhập, code_verifier khi đổi token.		M03
PKI
Public Key Infrastructure — hạ tầng khóa công khai		Hệ thống CA cấp và thu hồi chứng thư số, tạo chuỗi tin cậy để biết một public key thuộc về ai.
Ví dụ: ổ khóa HTTPS trên trình duyệt dựa vào PKI.		M02
Principal
chủ thể bảo mật		“Ai đó” mà hệ thống gắn quyền vào: có thể là người, dịch vụ hay thiết bị.
Ví dụ: trong .NET là ClaimsPrincipal; trong Kerberos là an@CORP.LOCAL.		M01
RADIUS
Remote Authentication Dial-In User Service		Giao thức kiểm tra đăng nhập cho thiết bị mạng như VPN, Wi-Fi doanh nghiệp.
Ví dụ: kết nối Wi-Fi công ty bằng tài khoản domain.		M05
RBAC
Role-Based Access Control — phân quyền theo vai trò		Gán quyền cho vai trò, rồi gán vai trò cho người dùng.
Ví dụ: role Manager được duyệt nghỉ phép; An là Manager nên duyệt được.		M06
ReBAC
Relationship-Based Access Control — phân quyền theo quan hệ		Quyền suy ra từ quan hệ giữa người dùng và tài nguyên.
Ví dụ: Google Docs: bạn sửa được tài liệu vì bạn là chủ sở hữu hoặc được chia sẻ.		M06
Redirect URI
địa chỉ trả về		Địa chỉ IdP gửi người dùng (kèm code) quay về sau đăng nhập. Phải đăng ký trước và khớp chính xác, nếu không code có thể bị gửi tới kẻ gian.
Ví dụ: https://hr.example.com/signin-oidc.		M03
Refresh token
token làm mới		Token sống lâu hơn, dùng để lấy access token mới khi cái cũ hết hạn mà không bắt người dùng đăng nhập lại. Cần giữ rất kỹ.
Ví dụ: app mobile vẫn đăng nhập sau nhiều ngày nhờ refresh token.		M02
Relying Party (RP)
bên tin cậy		Ứng dụng dựa vào kết quả đăng nhập do bên khác cung cấp, thay vì tự kiểm mật khẩu.
Ví dụ: app HR dùng Entra ID để đăng nhập là RP.		M01
Resource Server (RS)
máy chủ tài nguyên		API giữ dữ liệu, kiểm tra access token trước khi trả dữ liệu.
Ví dụ: orders-api của bạn viết bằng ASP.NET Core.		M03
ROPC / Implicit
hai luồng OAuth cũ		ROPC: app tự cầm mật khẩu của người dùng. Implicit: token trả thẳng trên URL. Cả hai đều kém an toàn và bị loại khỏi OAuth 2.1.
Ví dụ: SPA đời cũ nhận #access_token=... trên URL — không làm vậy nữa.		M03
SAML 2.0
Security Assertion Markup Language		Chuẩn SSO doanh nghiệp dựa trên XML: IdP gửi “giấy xác nhận” có chữ ký cho ứng dụng.
Ví dụ: đăng nhập Salesforce bằng tài khoản công ty qua ADFS.		M04
Scope
phạm vi quyền		Quyền mà ứng dụng xin được làm thay người dùng. Khác role: role mô tả người dùng, scope giới hạn ứng dụng.
Ví dụ: orders.read cho phép đọc nhưng không cho sửa đơn hàng.		M06
SCIM
System for Cross-domain Identity Management		Chuẩn để IdP tự động tạo, sửa, khóa tài khoản trong các ứng dụng.
Ví dụ: nhân viên nghỉ việc, HR khóa ở Entra ID → tài khoản ở Slack tự bị vô hiệu.		M07
Service Provider (SP)
nhà cung cấp dịch vụ		Tên gọi ứng dụng trong SAML: bên nhận assertion từ IdP.
Ví dụ: Salesforce là SP khi đăng nhập qua ADFS.		M04
Session
phiên đăng nhập		Trạng thái “đã đăng nhập” mà server ghi nhớ giữa các request. Cookie chỉ là phương tiện mang mã phiên.
Ví dụ: cookie .AspNetCore.Cookies giúp bạn không phải đăng nhập lại ở mỗi trang.		M02
Signature
chữ ký số		Ký bằng private key, ai có public key cũng kiểm được. Chứng minh nguồn gốc và không bị sửa, nhưng không che giấu nội dung.
Ví dụ: JWT ký RS256, API kiểm bằng public key trong JWKS.		M02
SSO
Single Sign-On — đăng nhập một lần		Đăng nhập một lần rồi dùng nhiều ứng dụng mà không phải gõ lại mật khẩu. Mỗi app vẫn có phiên riêng.
Ví dụ: đăng nhập Outlook xong mở Teams không bị hỏi lại.		M01
State
tham số trạng thái		Giá trị ngẫu nhiên app gửi đi khi bắt đầu đăng nhập và kiểm lại khi IdP trả về, để chắc rằng phản hồi thuộc đúng lần đăng nhập của chính người dùng này.
Ví dụ: gửi state=a91f → callback phải có state=a91f.		M03
TLS
Transport Layer Security		Lớp mã hóa đường truyền (chữ “S” trong HTTPS) và chứng minh server là thật. Mọi luồng đăng nhập đều phải chạy trên TLS.
Ví dụ: https:// và biểu tượng ổ khóa.		M02
Token Exchange
đổi token		Một API đổi token đang có lấy token mới để gọi tiếp API khác thay mặt người dùng.
Ví dụ: API đơn hàng đổi token của An để gọi API kho hàng (Entra ID gọi là On-Behalf-Of).		Phụ lục
UP / UV
User Presence / User Verification		UP: xác nhận có người đang ở đó (chạm vào khóa). UV: xác nhận đúng người (PIN, vân tay).
Ví dụ: chạm YubiKey = UP; quét vân tay mở passkey = UV.		M05
WebAuthn
Web Authentication		API của trình duyệt cho phép website đăng ký và đăng nhập bằng khóa công khai thay mật khẩu; là nền tảng của passkey.
