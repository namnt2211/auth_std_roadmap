A. Cryptography essentials Must

Bạn không cần biết toán học bên trong AES hay RSA. Bạn cần biết mỗi công cụ giải quyết bài toán gì, vì hầu hết lỗi bảo mật trong authentication đến từ việc dùng sai công cụ (ví dụ “mã hóa” mật khẩu thay vì hash, hoặc tưởng JWT đã ký là bí mật).

Symmetric vs Asymmetric

Nói đơn giản Symmetric giống chiếc két sắt có một chìa: ai có chìa thì vừa khóa vừa mở được — nên phải trao chìa cho người kia một cách bí mật. Asymmetric giống hộp thư có khe: ai cũng nhét thư vào được (public key), nhưng chỉ chủ hộp có chìa mở (private key).
  • Symmetric encryption (mã hóa đối xứng): cùng một secret key để mã hóa và giải mã. Nhanh, dùng cho dữ liệu lớn. Ví dụ: AES (Advanced Encryption Standard). Khó khăn: làm sao chia sẻ key an toàn cho bên kia?
  • Asymmetric cryptography (mật mã bất đối xứng / mật mã khóa công khai): mỗi bên có cặp khóa — public key (công khai, phát cho ai cũng được) và private key (giữ tuyệt mật). Dữ liệu mã hóa bằng public key chỉ giải được bằng private key tương ứng. Ví dụ: RSA, ECC (Elliptic-Curve Cryptography — ví dụ ECDSA, ECDH). Chậm hơn nhiều so với symmetric.
  • Thực tế (ví dụ TLS) dùng cả hai: asymmetric để xác thực và thỏa thuận key, rồi symmetric (AES) để mã hóa dữ liệu thật.

Hashing (hàm băm)

Nói đơn giản Hash giống dấu vân tay của dữ liệu: cùng một người luôn cho cùng một vân tay, vân tay rất ngắn, nhưng từ vân tay không dựng lại được cả con người. Giới hạn của phép so sánh: “vân tay” của dữ liệu ngắn (như mật khẩu) có thể bị đoán thử — xem phần password hashing.
  • Hash function là hàm một chiều: nhận dữ liệu bất kỳ độ dài → trả về digest (giá trị băm) độ dài cố định. Ví dụ SHA-256 luôn trả về 256 bit (64 ký tự hex).
  • Cùng input → luôn cùng digest. Đổi 1 ký tự → digest thay đổi hoàn toàn (thử ở widget bên dưới).
  • Không có key, không “giải mã” được. Vì vậy hash không phải encryption.
  • Dùng để: kiểm tra toàn vẹn file (checksum), làm thành phần trong chữ ký số/HMAC, lưu dấu của dữ liệu bí mật có entropy cao (ví dụ API key).

Password hashing và Salt Must

Nói đơn giản SHA-256 được thiết kế để nhanh — GPU có thể thử hàng tỷ mật khẩu mỗi giây. Password hashing cố tình làm việc băm chậm và tốn RAM, như một ổ khóa phải xoay 2 giây mới mở: người dùng thật không thấy phiền (chỉ mở một lần), còn kẻ đoán mò thử hàng tỷ lần thì kiệt sức. Salt giống việc mỗi người dùng có một “gia vị” riêng trộn vào trước khi băm, nên hai người cùng mật khẩu vẫn ra hai kết quả khác nhau.

Vì sao SHA-256(password) không đủ?

  1. Quá nhanh → brute-force/dictionary attack (thử lần lượt các mật khẩu phổ biến) rất rẻ khi DB bị lộ.
  2. Không có salt → cùng mật khẩu cho cùng hash: kẻ tấn công thấy ngay ai dùng chung mật khẩu, và dùng được bảng tính sẵn (precomputed table / rainbow table) cho các mật khẩu phổ biến.
  3. Mật khẩu người dùng có entropy thấp (dễ đoán) — khác với API key ngẫu nhiên 256 bit.

Password hashing dùng thuật toán chuyên dụng — chậm có chủ đích, có tham số chi phí (work factor) điều chỉnh được, và tích hợp salt:

Trong ASP.NET Core, đừng tự viết — dùng PasswordHasher<TUser> của ASP.NET Core Identity. Định dạng V3 hiện tại dùng PBKDF2 với HMAC-SHA512, salt 128 bit, subkey 256 bit, và IterationCount mặc định 100.000. Mức này thấp hơn khuyến nghị OWASP hiện hành cho PBKDF2-HMAC-SHA512 (220.000), nên hãy cấu hình lại:

using Microsoft.AspNetCore.Identity;

// Tăng số vòng PBKDF2 (V3 dùng HMAC-SHA512) theo OWASP: >= 220.000
builder.Services.Configure<PasswordHasherOptions>(o =>
{
    o.IterationCount = 220_000;   // đo thời gian đăng nhập trên server thật rồi điều chỉnh
});

// --- Dùng trực tiếp (ví dụ trong một app không dùng full Identity) ---
var hasher = new PasswordHasher<AppUser>();
string stored = hasher.HashPassword(user, "Kaopiz2026");
// stored = chuỗi Base64 chứa: version marker, PRF, iteration count, salt, subkey

var result = hasher.VerifyHashedPassword(user, stored, inputPassword);
switch (result)
{
    case PasswordVerificationResult.Success:
        break;                                   // đăng nhập OK
    case PasswordVerificationResult.SuccessRehashNeeded:
        // Hash cũ dùng tham số yếu hơn (ít vòng hơn, PRF cũ...) → băm lại và lưu
        user.PasswordHash = hasher.HashPassword(user, inputPassword);
        await db.SaveChangesAsync();
        break;
    default:
        return Results.Unauthorized();
}
✅ Nâng cấp tham số không cần bắt user đổi mật khẩu Vì hash lưu kèm tham số, khi bạn tăng IterationCount, các hash cũ vẫn verify được và trả về SuccessRehashNeeded → băm lại ngay lúc user đăng nhập thành công. Digital signature (chữ ký số) Must

Nói đơn giản Giống con dấu niêm phong của công ty trên văn bản: ai cũng đọc được văn bản và kiểm tra con dấu có thật không (bằng public key), nhưng chỉ người giữ con dấu (private key) mới đóng được. Chữ ký không che nội dung — nó chỉ chứng minh “ai tạo ra” và “không bị sửa”.
  • Ký: người gửi băm dữ liệu rồi dùng private key tạo chữ ký.
  • Verify: người nhận dùng public key của người gửi kiểm tra chữ ký khớp với dữ liệu.
  • Đảm bảo integrity (sửa 1 byte → verify thất bại) và authenticity theo mô hình khóa (chỉ người giữ private key ký được). Không đảm bảo confidentiality.
  • Ứng dụng trong auth: JWT ký RS256/ES256 (mục E), SAML assertion (M04), certificate (PKI), passkey (M05).

HMAC Nice

Nói đơn giản HMAC giống mật khẩu chung giữa hai người bạn gắn vào cuối thư: người nhận kiểm tra được thư từ bạn mình và không bị sửa. Nhưng vì cả hai cùng biết secret, người nhận cũng có thể tự tạo “thư hợp lệ” — nên HMAC không chứng minh được với bên thứ ba ai là người viết.
  • HMAC (Hash-based Message Authentication Code, RFC 2104): HMAC(secret key, message) → tag. Bên nhận có cùng key tính lại và so sánh.
  • Đảm bảo integrity + authenticity giữa hai bên cùng giữ secret. Khác chữ ký bất đối xứng: không có non-repudiation (chống chối bỏ) và mọi bên verify được cũng ký được.
  • Ví dụ: JWT HS256 = HMAC-SHA256; webhook signature (GitHub, Stripe…); một số cơ chế ký request API.
  • Hệ quả quan trọng: nếu dùng HS256 cho access token, mọi API cần secret để verify → API nào cũng có thể tự phát hành token. Với nhiều API, dùng chữ ký bất đối xứng (RS256/ES256) an toàn hơn.
byte[] expected = HMACSHA256.HashData(webhookSecret, requestBodyBytes);
byte[] received = Convert.FromHexString(signatureHeaderValue);
// So sánh constant-time để không lộ thông tin qua thời gian phản hồi
bool valid = CryptographicOperations.FixedTimeEquals(expected, received);

Certificate, X.509, CA và PKI Should

Nói đơn giản Public key chỉ là một dãy số — làm sao biết nó thật sự thuộc về sso.kaopiz.local? Certificate giống căn cước công dân: ghi “public key này thuộc về tên miền này”, và được cơ quan cấp (CA) đóng dấu. Bạn tin căn cước vì bạn tin cơ quan cấp.
  • Certificate / X.509: chứng thư theo định dạng X.509, gắn public key với danh tính/thuộc tính (subject, tên miền trong SAN — Subject Alternative Name), có thời hạn (notBefore/notAfter), và được CA ký.
  • CA (Certificate Authority — tổ chức cấp chứng thư): ký certificate cho người khác. Có Root CA (tự ký, được cài sẵn trong trust store của OS/trình duyệt) và Intermediate CA.
  • PKI (Public Key Infrastructure — hạ tầng khóa công khai): toàn bộ CA, chính sách, quy trình cấp phát, gia hạn, thu hồi certificate.
  • Trust chain (chuỗi tin cậy): leaf certificate ← ký bởi Intermediate ← ký bởi Root có trong trust store.
  • Khi kiểm tra certificate: chữ ký chuỗi hợp lệ tới một root tin cậy; còn hạn; tên miền khớp; mục đích sử dụng phù hợp; chưa bị thu hồi (revocation — qua CRL hoặc OCSP; mức hỗ trợ khác nhau tùy CA/trình duyệt).

TLS/HTTPS và mTLS Should

Nói đơn giản TLS giống xe chở tiền bọc thép giữa trình duyệt và server: kiểm tra giấy tờ tài xế (certificate của server) trước khi lên xe, và không ai nhìn trộm hay tráo hàng trên đường. Nhưng tới nơi rồi thì hàng (token, mật khẩu) vẫn là hàng thật — TLS không bảo vệ dữ liệu sau khi đến server hay trong log.
  • TLS (Transport Layer Security) bảo vệ kênh truyền: xác thực server bằng certificate, bảo vệ bí mật và toàn vẹn dữ liệu khi truyền. HTTPS = HTTP chạy trên TLS.
  • mTLS (mutual TLS): client cũng trình certificate → server xác thực được client. Hay dùng cho service-to-service, và trong OAuth để ràng buộc token với certificate của client (RFC 8705).
  • Mọi cơ chế ở trang này (cookie, Basic, Bearer, API key) đều giả định có TLS. Không có TLS, ai nghe lén được mạng là lấy được credential.

C. Session, Cookie và Stateful/Stateless Must

Nói đơn giản HTTP “mất trí nhớ”: mỗi request là một lần gặp mới. Session giống việc gửi áo khoác ở quầy giữ đồ: quầy giữ áo (trạng thái ở server), bạn cầm tấm thẻ số (session ID). Cookie là cái túi áo trình duyệt dùng để cất tấm thẻ đó và tự động đưa ra mỗi lần quay lại quầy.

Stateful vs Stateless

  • Stateful: server lưu trạng thái phiên. Request chỉ mang session ID; server tra cứu. Ưu: thu hồi tức thì (xóa session). Nhược: cần store dùng chung khi scale nhiều instance.

  • “Stateless” không có nghĩa là không có state nào: vẫn cần trạng thái cho refresh token, revocation list, risk, audit, policy.

C.1. Session management Should

Có session rồi, cần quản lý nó an toàn suốt vòng đời: tạo → dùng → nâng quyền → hết hạn → hủy.

Session ID phải ngẫu nhiên và do framework sinh

  • Session ID phải không đoán được: sinh bằng bộ sinh số ngẫu nhiên an toàn mật mã (CSPRNG), đủ dài (OWASP khuyến nghị tối thiểu 64 bit entropy).
  • Không tự chế (ví dụ userId + timestamp, GUID tăng dần, MD5(username)) — dùng cơ chế của framework.
  • Không đưa session ID lên URL (lộ qua log, lịch sử, header Referer).

Session fixation

Nói đơn giản Kẻ gian đưa cho bạn một tấm thẻ giữ đồ mà hắn đã chụp ảnh số thẻ. Bạn dùng thẻ đó để gửi áo (đăng nhập). Hắn mang ảnh số thẻ ra quầy và lấy áo của bạn. Cách chống: đổi thẻ mới ngay khi bạn gửi đồ quý (đăng nhập/nâng quyền).

Idle timeout và absolute timeout

💤

Idle timeout

Session hết hạn khi không hoạt động trong X phút. Giảm rủi ro máy bỏ quên không khóa. Trong ASP.NET Core: ExpireTimeSpan + SlidingExpiration = true.

⏳

Absolute timeout

Session hết hạn sau thời gian tối đa (ví dụ 8 giờ) dù vẫn hoạt động. Giới hạn thời gian kẻ trộm dùng được session bị đánh cắp. Nên có cả hai.

// Lúc đăng nhập: ghi lại thời điểm login vào AuthenticationProperties
var props = new AuthenticationProperties();
props.Items["login_at"] = DateTimeOffset.UtcNow.ToUnixTimeSeconds().ToString();
await HttpContext.SignInAsync(CookieAuthenticationDefaults.AuthenticationScheme, principal, props);

// Mỗi request: từ chối nếu quá 8 giờ kể từ lúc login (dù sliding vẫn đang gia hạn)
o.Events.OnValidatePrincipal = async ctx =>
{
    if (ctx.Properties.Items.TryGetValue("login_at", out var s) &&
        DateTimeOffset.UtcNow.ToUnixTimeSeconds() - long.Parse(s!) > 8 * 3600)
    {
        ctx.RejectPrincipal();
        await ctx.HttpContext.SignOutAsync(CookieAuthenticationDefaults.AuthenticationScheme);
    }
};

Re-authentication / step-up authentication

Trước thao tác nhạy cảm (đổi mật khẩu, đổi email, chuyển tiền, xem dữ liệu bí mật), yêu cầu xác thực lại hoặc dùng yếu tố mạnh hơn (ví dụ passkey/MFA) — kể cả khi session vẫn còn hạn. Lý do: session có thể đã bị đánh cắp, hoặc máy đang bị người khác dùng. Với OIDC, app có thể yêu cầu IdP xác thực lại (ví dụ tham số max_age, prompt=login, acr_values — xem M03).

Remember me

  • Dùng persistent token riêng (ngẫu nhiên, lưu hash ở server), có thời hạn, có thể thu hồi từng thiết bị, xoay vòng sau mỗi lần dùng.
  • Không phải chỉ kéo dài session vô thời hạn hay lưu username/password trong cookie.
  • Khi đăng nhập bằng remember-me, nên coi là mức tin cậy thấp hơn: thao tác nhạy cảm vẫn cần step-up.

Logout phải hủy session phía server

  • Chỉ xóa cookie ở trình duyệt là chưa đủ: nếu ai đó đã chép được cookie/session ID, họ vẫn dùng được nếu server chưa hủy.
  • Session stateful: xóa bản ghi session. Cookie stateless (ticket mã hóa): cần server-side store (ITicketStore) hoặc đánh dấu thu hồi (security stamp, “session version”).
  • Logout trong SSO còn liên quan phiên ở IdP và các app khác — xem M03 — Logout.

D. Token concepts Must

Nói đơn giản Access token giống thẻ ra vào tòa nhà có hạn dùng: quẹt ở cửa (API) là vào, ai nhặt được cũng quẹt được, nên hạn dùng ngắn. Refresh token giống giấy hẹn đổi thẻ mới ở quầy lễ tân (Authorization Server) — không quẹt được ở cửa. ID token giống biên nhận “đã kiểm tra căn cước” lễ tân đưa cho công ty mời bạn đến (client) — chứ không phải đưa cho bảo vệ ở cửa.
  • Token: vật mang thông tin/quyền, hoặc tham chiếu tới thông tin/quyền lưu ở server.
  • Access Token: dùng để truy cập Resource Server/API. Audience (người nhận) là API.
  • ID Token: trong OIDC (OpenID Connect), mang thông tin về kết quả xác thực và subject, dành cho client/RP. Luôn là JWT.
  • Refresh Token: dùng để xin access token mới theo chính sách của Authorization Server; chỉ gửi tới AS, không dùng gọi API.

Opaque token vs JWT

🎫

Opaque token (by reference)

Chuỗi ngẫu nhiên không mang cấu trúc đọc được, vd. 2YotnFZFEjr1zCsicMWpAA. API phải hỏi AS (introspection) hoặc tra server-side. Ưu: thu hồi tức thì, không lộ claims. Nhược: thêm một lần gọi mạng.

📜

JWT (by value)

Tự mang claims đã ký. API verify cục bộ bằng public key. Ưu: nhanh, không phụ thuộc AS mỗi request. Nhược: khó thu hồi trước hạn, payload đọc được.

JWT, JWS và JWE Should (JWE)

  • JWT (JSON Web Token, RFC 7519): định dạng biểu diễn claims (các cặp thông tin dạng JSON). JWT có thể được ký (dùng JWS) hoặc mã hóa (dùng JWE).
  • JWS (JSON Web Signature, RFC 7515): bảo vệ toàn vẹn + nguồn gốc. Dạng compact gồm 3 phần: header.payload.signature. Đây là loại bạn gặp 99% thời gian.
  • JWE (JSON Web Encryption, RFC 7516): bảo vệ bí mật nội dung. Dạng compact gồm 5 phần: header.encrypted_key.iv.ciphertext.tag.
🚫 JWT ký ≠ payload bí mật Payload của JWS chỉ được Base64url-encode — ai cầm token cũng đọc được (thử với widget bên dưới). Đừng bao giờ đặt mật khẩu, số CMND, lương… vào payload của JWT ký. Cần giấu → dùng JWE, hoặc dùng opaque token.

E.1. JWT validation — checklist cho access token Must

Nói đơn giản Bảo vệ ở cửa tòa nhà kiểm tra thẻ theo thứ tự: tem chống giả thật không (chữ ký) → do đúng công ty phát hành không (iss) → thẻ dành cho tòa nhà này không (aud) → còn hạn không (exp/nbf) → đúng loại thẻ ra vào không, không phải biên nhận (token type) → có quyền vào tầng này không (scope/role).

Deliverable 5. Checklist cho API khi nhận access token JWT. M03 sẽ bổ sung phần validation ID token (nonce, aud = client_id…).

  • Định dạng: đúng 3 phần (JWS); token lấy từ header Authorization: Bearer, không từ query string.
  • Thuật toán: alg nằm trong allowlist do API cấu hình (vd. chỉ RS256). Từ chối none; không để token tự chọn thuật toán (chặn tấn công “alg confusion” RS256 → HS256).
  • Chữ ký: verify bằng key đáng tin cậy — public key lấy từ JWKS của issuer đã cấu hình (qua HTTPS), chọn theo kid. Không lấy key từ chính token (vd. header jku/jwk do token tự khai).
  • iss khớp chính xác issuer mong đợi (kể cả dấu / cuối).
  • aud chứa định danh của chính API này (vd. hr-api).
  • Thời hạn: exp chưa qua, nbf (nếu có) đã tới; clock skew nhỏ (vài chục giây đến vài phút).
  • Đúng loại token/ngữ cảnh: là access token, không phải ID token hay refresh token (kiểm tra typ header nếu IdP dùng at+jwt, hoặc claim/audience đặc trưng).
  • Quyền: có scope/role cần thiết cho endpoint (thiếu → 403 + insufficient_scope), sau đó còn kiểm tra quyền trên dữ liệu cụ thể (An chỉ xem payroll của An — M06).
  • Tùy yêu cầu: kiểm tra thu hồi (introspection/denylist jti), ràng buộc sender (DPoP/mTLS), client được phép (azp/client_id).
  • Không tự viết: dùng thư viện đã kiểm chứng (Microsoft.IdentityModel / JwtBearer); log lý do từ chối ở server, không lộ chi tiết cho client.

F. Token lifecycle Must

Nói đơn giản Thẻ ra vào (access token) hết hạn sau 5 phút → mang giấy hẹn (refresh token) ra lễ tân đổi thẻ mới. Mỗi lần đổi, lễ tân thu giấy hẹn cũ, đưa giấy hẹn mới (rotation). Nếu ai đó mang tới một giấy hẹn đã bị thu, lễ tân biết có kẻ sao chép → hủy luôn cả chuỗi giấy hẹn (reuse detection).

Vòng đời: cấp → sử dụng → hết hạn → refresh → revoke.

  • Access token có thời hạn ngắn hơn refresh token: lộ access token thì thiệt hại bị giới hạn bởi thời hạn ngắn.
  • Refresh token rotation: mỗi lần dùng refresh token, AS cấp refresh token mới và vô hiệu cái cũ.
  • Reuse detection: nếu refresh token cũ (đã dùng) bị dùng lại → dấu hiệu bị đánh cắp → AS thu hồi toàn bộ refresh token thuộc cùng grant/phiên. RFC 9700 (OAuth 2.0 Security Best Current Practice) yêu cầu refresh token của public client phải được ràng buộc với sender hoặc dùng rotation.

Logout có vô hiệu hóa token ngay không?

Không mặc định. Logout thường hủy phiên ở IdP và thu hồi refresh token, nhưng một JWT access token đã phát hành vẫn verify được cho tới exp, vì API kiểm tra cục bộ và không hỏi ai. Các lựa chọn: access token thật ngắn; introspection (hoặc opaque token) cho API nhạy cảm; denylist theo jti/sid; cơ chế đặc thù của IdP. Tùy kiến trúc mà chọn.

Key rotation (xoay vòng signing key) Should

  • Issuer định kỳ thay signing key (hoặc thay gấp khi lộ key). Public key được công bố ở JWKS (JSON Web Key Set) endpoint, mỗi key có kid — chi tiết ở M03 — Discovery/JWKS.
  • Quy trình an toàn: công bố key mới trong JWKS trước → bắt đầu ký bằng key mới → giữ key cũ trong JWKS tới khi mọi token ký bằng key cũ đã hết hạn → gỡ key cũ.
  • API phải: cache JWKS, chọn key theo kid, và khi gặp kid lạ thì làm mới JWKS (có giới hạn tần suất) thay vì từ chối mãi. Không hard-code public key vào code. Middleware JwtBearer với Authority làm việc này tự động.

Basic authentication

  • RFC 7617: Authorization: Basic base64(username:password).
  • Base64 chỉ là encoding (đổi cách biểu diễn), không phải mã hóa: ai bắt được header là có mật khẩu → chỉ dùng qua TLS.
  • Gửi mật khẩu thật trong mọi request; không có hạn dùng, scope hay cách thu hồi riêng. Hạn chế dùng cho API mới; vẫn gặp ở hệ thống cũ, công cụ nội bộ, và xác thực client tại token endpoint (client_secret_basic).

Bearer token (RFC 6750)

Nói đơn giản “Bearer” nghĩa là người cầm: giống tiền mặt — ai cầm tờ tiền là tiêu được, cửa hàng không hỏi bạn là ai. Vì vậy phải giữ token như giữ mật khẩu.
  • Authorization: Bearer <access_token>. Ai cầm token là dùng được → bảo vệ token như mật khẩu.
  • Không gửi qua query string/URL (?access_token=…): URL bị ghi vào log server/proxy, lịch sử trình duyệt, header Referer.
  • Luôn qua TLS; access token ngắn hạn; không log token. Muốn chống dùng lại token bị trộm → sender-constrained token (DPoP RFC 9449, mTLS RFC 8705) — xem M06.

G.1. API key Must

Nói đơn giản API key giống chìa khóa nhà kho cấp cho một công ty đối tác: nó cho biết công ty nào (ứng dụng/dự án) đang vào, không biết nhân viên nào (người dùng). Chìa thường dùng rất lâu và mở được mọi cửa được gán — nên mất chìa là chuyện lớn.
  • Chuỗi bí mật định danh ứng dụng/dự án gọi API, không định danh người dùng.
  • Thường sống lâu, không có scope/consent/audience chuẩn hóa; không có chuẩn chung về cách gửi (thường header tùy chỉnh như X-API-Key).
✅ Phù hợp
  • Public API đơn giản (dữ liệu thời tiết, bản đồ…).
  • Quota, rate limit, metering, tính phí theo dự án.
  • Tích hợp server-to-server quy mô nhỏ, key nằm an toàn ở backend.
❌ Không phù hợp
  • Hành động thay mặt người dùng (không biết user nào, không có consent).
  • Nhúng trong public client: SPA, mobile, desktop (WPF) — key sẽ bị lộ khi người dùng mở DevTools/decompile.
  • Quyền chi tiết, ngắn hạn, cần audit theo người dùng.

Thực hành tốt

  • Gửi qua header, không qua URL.
  • Sinh bằng CSPRNG (≥ 128 bit, thường 256 bit), có prefix nhận diện để công cụ secret scanning phát hiện khi lỡ commit.
  • Chỉ lưu hash phía server; hiển thị key cho người dùng một lần lúc tạo.
  • Hỗ trợ rotation/revoke (cho phép 2 key song song khi xoay), có expiration, gắn quyền tối thiểu (theo API/hành động/IP), theo dõi usage và cảnh báo bất thường.
using System.Security.Cryptography;
using System.Text;

// 1) Sinh key: 32 byte ngẫu nhiên (256 bit) từ CSPRNG + prefix nhận diện
string secret = Convert.ToHexString(RandomNumberGenerator.GetBytes(32)).ToLowerInvariant();
string apiKey = $"kz_live_{secret}";          // hiển thị cho khách hàng ĐÚNG MỘT LẦN

// 2) Lưu: chỉ lưu hash + vài ký tự đầu để nhận diện trên UI
byte[] hash = SHA256.HashData(Encoding.UTF8.GetBytes(apiKey));
db.ApiKeys.Add(new ApiKeyRecord
{
    ClientId  = "payroll-batch",
    Prefix    = apiKey[..12],                   // "kz_live_7d1f" để hiển thị/tra cứu
    KeyHash   = hash,
    Scopes    = "payroll:export",
    ExpiresAt = DateTimeOffset.UtcNow.AddDays(90)
});

// 3) Kiểm tra khi có request: băm key nhận được, so sánh constant-time
static bool Matches(string presented, byte[] storedHash) =>
    CryptographicOperations.FixedTimeEquals(
        SHA256.HashData(Encoding.UTF8.GetBytes(presented)), storedHash);
🤔 Vừa nói SHA-256 không đủ cho mật khẩu, sao lại dùng cho API key? Vì API key là 256 bit ngẫu nhiên — không có “danh sách key phổ biến” để đoán, brute-force 2256 là bất khả thi dù hash nhanh. Mật khẩu người dùng thì entropy thấp, nên mới cần thuật toán chậm. Điểm mấu chốt là entropy của input, không phải bản thân SHA-256.

Tóm tắt nhanh

  • Encryption để giấu (đảo ngược được bằng key); hash một chiều không key; signature = private key ký, public key verify, không che nội dung; HMAC = toàn vẹn bằng secret dùng chung.
  • Mật khẩu: Argon2id (19 MiB, t=2, p=1) hoặc PBKDF2-HMAC-SHA512 ≥ 220.000 vòng, có salt riêng. Không bao giờ SHA-256(password). ASP.NET Core Identity mặc định 100.000 vòng → nên tăng.
  • Certificate gắn public key với danh tính, được CA ký; tin cậy đi theo chain tới root trong trust store. TLS bảo vệ kênh; mTLS xác thực cả client.
  • Cookie ≠ session. Cookie đăng nhập: HttpOnly; Secure; SameSite=Lax/Strict, không đặt Domain, cân nhắc prefix __Host-.
  • Session: ID ngẫu nhiên do framework sinh, đổi ID sau login, có idle + absolute timeout, step-up cho thao tác nhạy cảm, logout hủy phía server.
  • Access token → API; ID token → client; refresh token → AS. Không dùng ID token gọi API.
  • API phải verify JWT: alg allowlist, chữ ký bằng key tin cậy (JWKS theo kid), iss, aud, exp/nbf, loại token, scope. Decode ≠ verify.
  • Refresh token rotation + reuse detection; JWT khó thu hồi trước hạn → token ngắn, introspection (RFC 7662), revocation (RFC 7009).
  • 401 kèm WWW-Authenticate cho biết lý do (invalid_token…); 403 insufficient_scope khi thiếu quyền.
  • API key định danh ứng dụng, sống lâu; với service-to-service cần kiểm soát tốt hơn, dùng Client Credentials.

Knowledge Check (tự luận)

Tự trả lời trước, sau đó mở đáp án gợi ý để so sánh.

Vì sao không nên lưu password bằng SHA-256 đơn thuần?

SHA-256 được thiết kế để nhanh — GPU thử được hàng tỷ ứng viên mỗi giây, nên khi DB lộ, mật khẩu phổ biến bị đoán ra rất rẻ. Không có salt thì cùng mật khẩu cho cùng hash, dùng được bảng tính sẵn và lộ ai dùng chung mật khẩu. Cần thuật toán password hashing chậm có chủ đích, có salt, có work factor: Argon2id, scrypt, PBKDF2 (đủ vòng), bcrypt.

Khác nhau giữa cookie và session?

Session là trạng thái đăng nhập/hoạt động do ứng dụng quản lý (thường lưu ở server). Cookie là cơ chế của trình duyệt để lưu và tự động gửi dữ liệu theo domain/path. Cookie thường mang session ID để tham chiếu session, nhưng cookie còn dùng cho việc khác, và session có thể truyền bằng cách khác.

API có thể chỉ decode JWT rồi tin payload không?

Không. Decode chỉ là Base64url — ai cũng tạo được JWT với payload tùy ý (thử nút “Giả mạo” trong widget). API phải verify chữ ký bằng key tin cậy với thuật toán trong allowlist, rồi kiểm tra iss, aud, exp/nbf, loại token, scope — bằng thư viện đã kiểm chứng.

aud giúp bảo vệ điều gì?

aud cho biết token được cấp cho API nào. Kiểm tra aud ngăn việc một token cấp cho API A (hoặc ID token cấp cho client) bị đem sang dùng ở API B — ví dụ một API ít quan trọng bị lộ token, kẻ tấn công không thể dùng token đó gọi hr-api. Đây là phòng chống “token substitution / confused deputy”.

Vì sao ID token không nên gửi cho API thay access token?

ID token dành cho client (aud = client_id) để biết ai đã đăng nhập; nó không đại diện cho việc ủy quyền gọi API, không mang scope cho API, và API không phải audience của nó. Nếu API chấp nhận ID token, bất kỳ client nào có ID token của user (kể cả client khác) có thể gọi API; đồng thời mất khả năng kiểm soát scope/audience. Chi tiết ở M03.

Logout có luôn vô hiệu hóa token ngay lập tức không?

Không. Logout thường hủy session ở app/IdP và có thể thu hồi refresh token, nhưng JWT access token đã phát hành vẫn verify được cục bộ cho tới exp. Muốn hiệu lực tức thì cần: access token ngắn, introspection/opaque token, denylist, hoặc cơ chế đặc thù của IdP — phụ thuộc kiến trúc.

API key khác OAuth access token thế nào?

API key: secret dài hạn, định danh ứng dụng, không có scope/audience/consent chuẩn hóa, vòng đời và thu hồi tự xây. Access token: do Authorization Server cấp, ngắn hạn, có scope, aud, có thể đại diện user + client, xoay vòng/thu hồi theo chuẩn. Với service-to-service cần kiểm soát tốt, dùng Client Credentials thay API key.

Vì sao phải cấp session ID mới sau khi login?

Để chống session fixation: nếu giữ nguyên session ID từ trước khi đăng nhập, kẻ tấn công có thể “cài” sẵn một session ID mà hắn biết cho nạn nhân; sau khi nạn nhân đăng nhập, session ID đó trở thành phiên đã xác thực và kẻ tấn công dùng được. Cũng phải đổi ID khi thay đổi mức quyền.

Header WWW-Authenticate cho biết điều gì khi API trả 401?

Cho biết scheme server yêu cầu (vd. Bearer, Basic), realm, và với Bearer có thể kèm error (invalid_request/invalid_token/insufficient_scope), error_description và scope cần. Từ đó biết nên refresh token, sửa audience/issuer, hay xin thêm scope.
