Bài 2.5 — HTTP auth schemes & API key

Khi gọi API, “giấy tờ” được gửi trong header Authorization, và khi bị từ chối, server giải thích lý do trong header WWW-Authenticate. Bài này giúp bạn đọc hai header đó, phân biệt Basic, Bearer, API key, và chọn đúng cách cho từng tình huống.

G. HTTP authentication schemes Must

Nói đơn giản HTTP có một “ô” chuẩn để trình giấy tờ: header Authorization. Phần đầu nói loại giấy tờ (Basic, Bearer…), phần sau là giấy tờ. Khi bị từ chối, server trả lời bằng header WWW-Authenticate: “ở đây cần loại giấy tờ X, và giấy của bạn bị lỗi Y”.

Header Authorization

Định dạng chung (RFC 9110): Authorization: <scheme> <credentials> — tức là “loại giấy tờ” + dấu cách + “giấy tờ”. Ba dòng dưới là ba cách hr-api có thể nhận credential:

Authorization: Basic YW4ubnY6UEBzc3cwcmQh
Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCIsImtpZCI6ImhyLTIwMjYtMTEifQ.eyJleHAi…
X-API-Key: kz_7d1f…        ← API key thường dùng header riêng, không phải scheme chuẩn

Header WWW-Authenticate — đọc lỗi 401 như đọc log

Server trả kèm 401 để báo scheme yêu cầu và (với Bearer) lý do lỗi. Đây là nguồn thông tin troubleshooting (gỡ lỗi) số 1 — mở DevTools tab Network hoặc xem response header trong Postman.

Bốn response mẫu dưới đây từ hr-api: hãy so sánh status code và giá trị error trong từng trường hợp.

HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="hr-api"
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="hr-api", error="invalid_token", error_description="The access token expired"
HTTP/1.1 403 Forbidden
WWW-Authenticate: Bearer realm="hr-api", error="insufficient_scope", scope="hr.write"
HTTP/1.1 400 Bad Request
WWW-Authenticate: Bearer realm="hr-api", error="invalid_request"

Ý nghĩa“Đây là giấy tờ của tôi”“Tôi cần loại giấy tờ này / giấy của bạn lỗi thế này”

Ví dụ: hr-web gửi Authorization: Bearer <token có aud=account> → hr-api trả 401 + WWW-Authenticate: Bearer error="invalid_token", error_description="…audience…". Dev đọc header thứ hai là biết phải sửa audience ở Keycloak, không cần đoán.

Tên dễ gây hiểu lầm: header tên “Authorization” nhưng thực ra mang thông tin xác thực (authentication). Client “trình” bằng Authorization, server “đòi” bằng WWW-Authenticate.
ℹ️ Nhắc lại 401 vs 403 401 = server không biết/không tin bạn là ai (thiếu token, token hết hạn, sai chữ ký, sai aud) → cần token hợp lệ (refresh, đăng nhập lại, hoặc sửa cấu hình). 403 = server biết bạn là ai nhưng bạn không được phép → thử lại với cùng token cũng vô ích. Chi tiết ở M01 và M06.

⚠️ Hiểu lầm hay gặp

Hiểu lầm401 và 403 giống nhau, đều là “không có quyền”.Thực tế401 = không tin token (thiếu, hết hạn, sai chữ ký/aud) → cần token hợp lệ. 403 = tin token nhưng không đủ quyền → refresh cũng vô ích, phải xin thêm scope/quyền.
Hiểu lầmGặp 401 thì cứ refresh token rồi gọi lại là xong.Thực tếRefresh chỉ chữa được token hết hạn. Nếu error_description nói sai audience/issuer, token mới vẫn được cấp với cùng cấu hình → vẫn 401. Đọc WWW-Authenticate trước, rồi sửa cấu hình (vd. audience mapper ở Keycloak).

Basic authentication

  • RFC 7617: Authorization: Basic base64(username:password).
  • Base64 chỉ là encoding (đổi cách biểu diễn), không phải mã hóa: ai bắt được header là có mật khẩu → chỉ dùng qua TLS.
  • Gửi mật khẩu thật trong mọi request; không có hạn dùng, scope hay cách thu hồi riêng.
  • Hạn chế dùng cho API mới. Vẫn gặp ở hệ thống cũ, công cụ nội bộ, và khi client tự xác thực với token endpoint của AS — gọi là client_secret_basic: client gửi base64(client_id:client_secret) (bạn đã thấy ở request introspection của bài 2.4).

Widget dưới cho bạn tự thấy: chỉ một cú bấm là đọc ra mật khẩu, không cần key nào.

⚠️ Hiểu lầm hay gặp

Hiểu lầmĐã chạy qua HTTPS thì Basic auth dùng cho API mới cũng ổn như Bearer token.Thực tếTLS chỉ bảo vệ trên đường truyền. Basic vẫn gửi mật khẩu thật trong mọi request, không có hạn dùng, scope hay cách thu hồi riêng; lộ ở log hoặc ở một server trung gian là lộ mật khẩu. Bearer token ngắn hạn, có scope thì lộ ít hại hơn.

Bearer token (RFC 6750)

Nói đơn giản “Bearer” nghĩa là người cầm: giống tiền mặt — ai cầm tờ tiền là tiêu được, cửa hàng không hỏi bạn là ai. Vì vậy phải giữ token như giữ mật khẩu.
  • Authorization: Bearer <access_token>. Ai cầm token là dùng được → bảo vệ token như mật khẩu.
  • Không gửi qua query string/URL (?access_token=…): URL bị ghi vào log server/proxy, lịch sử trình duyệt, header Referer.
  • Luôn qua TLS; access token ngắn hạn; không log token.
  • Muốn token bị trộm cũng không dùng được → sender-constrained token (token “gắn chủ”: chỉ bên giữ một key riêng mới dùng được) — DPoP RFC 9449, mTLS RFC 8705, xem M06.
🧪 Ví dụ: vì sao không đặt token trong URL hr-web gọi GET https://hr-api/payroll/57?access_token=eyJhbGci…. Nginx trước hr-api ghi nguyên URL vào access log; log được đẩy sang hệ thống giám sát mà cả team xem được → ai đọc log cũng có token của An tới khi hết hạn. Đặt token trong header Authorization: Bearer thì thường không bị ghi vào access log (định dạng log mặc định không chứa header này) — nhưng vẫn phải cẩn thận với log ứng dụng.

⚠️ Hiểu lầm hay gặp

Hiểu lầmĐã dùng HTTPS thì đặt token trong query string cũng an toàn.Thực tếTLS mã hóa URL trên đường truyền, nhưng ở hai đầu URL vẫn là văn bản rõ: access log của server/proxy, lịch sử trình duyệt, header Referer. Token phải nằm trong header Authorization.
Hiểu lầmBearer token có chữ ký nên kẻ trộm không dùng được.Thực tếChữ ký chống sửa, không chống dùng lại. “Bearer” = ai cầm cũng dùng được nguyên vẹn tới khi hết hạn. Muốn token bị trộm vô dụng cần sender-constrained token (DPoP, mTLS).

G.1. API key Must

Nói đơn giản API key giống chìa khóa nhà kho cấp cho một công ty đối tác: nó cho biết công ty nào (ứng dụng/dự án) đang vào, không biết nhân viên nào (người dùng). Chìa thường dùng rất lâu và mở được mọi cửa được gán — nên mất chìa là chuyện lớn.
  • Chuỗi bí mật định danh ứng dụng/dự án gọi API, không định danh người dùng.
  • Thường sống lâu, không có scope/consent/audience chuẩn hóa; không có chuẩn chung về cách gửi (thường header tùy chỉnh như X-API-Key).
✅ Phù hợp
  • Public API đơn giản (dữ liệu thời tiết, bản đồ…).
  • Quota, rate limit, metering, tính phí theo dự án.
  • Tích hợp server-to-server quy mô nhỏ, key nằm an toàn ở backend.
❌ Không phù hợp
  • Hành động thay mặt người dùng (không biết user nào, không có consent).
  • Nhúng trong public client: SPA, mobile, desktop (WPF) — key sẽ bị lộ khi người dùng mở DevTools/decompile.
  • Quyền chi tiết, ngắn hạn, cần audit theo người dùng.

⚠️ Hiểu lầm hay gặp

Hiểu lầmAPI key là cách xác thực người dùng.Thực tếAPI key định danh ứng dụng/dự án, không phải người dùng: mọi nhân viên dùng chung app đều gửi cùng một key, API không biết ai là An.
Hiểu lầmLàm rối (obfuscate) hoặc mã hóa API key trong app WPF/SPA là đủ giấu.Thực tếApp phải tự giải mã được key để gửi đi, nên người dùng cũng lấy được (DevTools, decompile, bắt request). Public client không giữ được secret — dùng Authorization Code + PKCE.

Thực hành tốt

  • Gửi qua header, không qua URL.
  • Sinh bằng CSPRNG (bộ sinh số ngẫu nhiên an toàn cho mật mã, vd. RandomNumberGenerator trong .NET — không phải Random), ≥ 128 bit, thường 256 bit. Thêm prefix nhận diện (vd. kz_live_) để công cụ secret scanning (quét bí mật trong code) phát hiện khi lỡ commit.
  • Chỉ lưu hash phía server; hiển thị key cho người dùng một lần lúc tạo.
  • Hỗ trợ rotation/revoke (cho phép 2 key song song khi xoay), có expiration, gắn quyền tối thiểu (theo API/hành động/IP), theo dõi usage và cảnh báo bất thường.

Code dưới gói các thực hành trên thành 3 bước: sinh key → chỉ lưu hash → so sánh khi có request. “So sánh constant-time” nghĩa là thời gian so sánh không phụ thuộc vào việc sai ở ký tự thứ mấy, để kẻ gian không đo thời gian mà đoán dần key.

using System.Security.Cryptography;
using System.Text;

// 1) Sinh key: 32 byte ngẫu nhiên (256 bit) từ CSPRNG + prefix nhận diện
string secret = Convert.ToHexString(RandomNumberGenerator.GetBytes(32)).ToLowerInvariant();
string apiKey = $"kz_live_{secret}";          // hiển thị cho khách hàng ĐÚNG MỘT LẦN

// 2) Lưu: chỉ lưu hash + vài ký tự đầu để nhận diện trên UI
byte[] hash = SHA256.HashData(Encoding.UTF8.GetBytes(apiKey));
db.ApiKeys.Add(new ApiKeyRecord
{
    ClientId  = "payroll-batch",
    Prefix    = apiKey[..12],                   // "kz_live_7d1f" để hiển thị/tra cứu
    KeyHash   = hash,
    Scopes    = "payroll:export",
    ExpiresAt = DateTimeOffset.UtcNow.AddDays(90)
});

// 3) Kiểm tra khi có request: băm key nhận được, so sánh constant-time
static bool Matches(string presented, byte[] storedHash) =>
    CryptographicOperations.FixedTimeEquals(
        SHA256.HashData(Encoding.UTF8.GetBytes(presented)), storedHash);
🤔 Vừa nói SHA-256 không đủ cho mật khẩu, sao lại dùng cho API key? Vì API key là 256 bit ngẫu nhiên — không có “danh sách key phổ biến” để đoán, brute-force 2256 là bất khả thi dù hash nhanh. Mật khẩu người dùng thì entropy thấp, nên mới cần thuật toán chậm. Điểm mấu chốt là entropy của input, không phải bản thân SHA-256.

Ví dụ — chọn cái nào?

  • hr-web gọi hr-api thay mặt An → Bearer access token lấy qua đăng nhập OAuth/OIDC (Authorization Code + PKCE). Có user, có scope, hạn ngắn.
  • payroll-batch chạy đêm, xuất bảng lương từ hr-api → Client Credentials: không có người dùng, nhưng cần token ngắn hạn có aud/scope và audit được.
  • Kaopiz mở API tra ngày nghỉ lễ công khai cho đối tác, cần đếm quota → API key là đủ: chỉ cần biết “đối tác nào” và giới hạn số lần gọi.
  • Tool nội bộ cũ chỉ hỗ trợ username/password → Basic qua HTTPS, dùng tài khoản kỹ thuật riêng, lên kế hoạch chuyển dần.
  • App WPF trên máy nhân viên → không nhúng API key hay client secret; dùng Bearer token qua Authorization Code + PKCE (M07).
