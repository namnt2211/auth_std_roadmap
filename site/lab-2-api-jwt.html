Lab 2 — Web API xác minh JWT

Bạn viết một Web API ASP.NET Core chỉ chấp nhận access token do Keycloak cấp cho đúng nó, rồi cố tình gửi token sai theo 6 cách để tự tay thấy khi nào API trả 401, khi nào trả 403, và đọc lý do ở đâu.

⏱ ~30 phút 📘 Lab · Hands-on OAuth/OIDC với ASP.NET Core
📖 Thuật ngữ trong bài
Resource Server (RS)
Server giữ dữ liệu cần bảo vệ và kiểm tra token trước khi trả dữ liệu — ở đây là DemoApi.
JWT Bearer handler
Phần của ASP.NET Core (AddJwtBearer) đọc header Authorization: Bearer … và kiểm tra JWT.
Authority
Địa chỉ realm Keycloak. Từ đây handler tự tải discovery + JWKS và biết iss hợp lệ là gì.
Audience (cấu hình API)
Tên mà token phải ghi trong aud thì API mới nhận (demo-api).
Policy
Luật phân quyền đặt tên, ví dụ orders.read = “claim scope phải chứa orders.read”.
ClaimsPrincipal
Đối tượng .NET mô tả “người gọi” sau khi token hợp lệ: danh sách claim (type + value).
WWW-Authenticate
Header API gửi kèm 401 để nói “cần token kiểu gì / token sai ở đâu” (RFC 6750).
Mã IDX…
Mã lỗi của thư viện Microsoft.IdentityModel trong log, ví dụ IDX10214 = sai audience.
ClockSkew
Khoảng “du di” thời gian khi kiểm tra exp/nbf để bù lệch đồng hồ giữa các máy (mặc định 5 phút).
MapInboundClaims
Tùy chọn đổi tên claim JWT sang tên kiểu Microsoft (vd. sub → …/nameidentifier). Lab tắt nó.

Lab 2 — ASP.NET Core Web API xác minh JWT

Must⏱ 30 phút

(a) Mục tiêu

Viết DemoApi bảo vệ endpoint bằng JWT Bearer, rồi cố tình gửi token sai theo 6 kịch bản để thấy API phản ứng thế nào ở tầng authentication (401) và authorization (403) — xem lại 401 vs 403.

Nói đơn giản Đầu đọc thẻ ở cửa phòng Orders kiểm tra theo thứ tự: (1) có thẻ không, (2) con dấu thật không (chữ ký), (3) do đúng lễ tân của tòa nhà này cấp không (iss), (4) thẻ có ghi “dùng cho phòng Orders” không (aud), (5) còn hạn không (exp). Hỏng bất kỳ bước nào → “Tôi không biết bạn là ai” = 401. Qua hết rồi mới hỏi: “thẻ của bạn có quyền đọc đơn hàng không?” — không có → “Tôi biết bạn là ai nhưng bạn không được vào” = 403.

(b) Yêu cầu / đề bài

  1. API chạy ở http://localhost:5005 với 4 endpoint: /public (ai cũng gọi được), /me (chỉ cần token hợp lệ), /orders (cần scope orders.read), /profile (policy yêu cầu claim sub — dùng cho kịch bản 6).
  2. Tái hiện 6 kịch bản bên dưới. Với mỗi kịch bản ghi lại: status code, header WWW-Authenticate, dòng log quan trọng (mã IDX), và giải thích nguyên nhân.
  3. Nộp: bảng lỗi theo mẫu ở mục #error-table (tối thiểu 5 kịch bản — Deliverable 2, Core) + source code API trong repo.

(c) Hướng dẫn từng bước

    Đọc lướt trước khi dán — file chia làm 4 phần, mỗi phần trả lời một câu hỏi:

    1. AddJwtBearer: “token thế nào thì được coi là hợp lệ?” (chữ ký, iss, aud, hạn dùng) → sai thì 401.
    2. Events: in lý do từ chối ra console để bạn đọc được.
    3. AddAuthorization: “token hợp lệ rồi, có đủ quyền không?” (policy) → thiếu thì 403.

    using System.Security.Claims;
using Microsoft.AspNetCore.Authentication.JwtBearer;
using Microsoft.IdentityModel.Logging;

var builder = WebApplication.CreateBuilder(args);

// [LAB] Công tắc cho kịch bản 6:  dotnet run -- --Lab:MapInboundClaims=true
var mapInboundClaims = builder.Configuration.GetValue("Lab:MapInboundClaims", false);

// [LAB] Hiện giá trị thật (aud, iss...) trong thông báo IDX thay vì "[PII ... is hidden]".
// CHỈ dùng khi dev. Production: KHÔNG bật (log sẽ chứa dữ liệu nhạy cảm).
if (builder.Environment.IsDevelopment())
{
    IdentityModelEventSource.ShowPII = true;
}

builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(o =>
    {
        o.Authority = "http://localhost:8080/realms/demo"; // -> tải discovery + JWKS, kiểm tra iss
        o.Audience = "demo-api";                           // -> token phải có aud chứa demo-api
        o.RequireHttpsMetadata = false;   // CHỈ dùng cho lab localhost
        o.MapInboundClaims = mapInboundClaims; // lab mặc định false: giữ nguyên tên claim sub, scope...
        o.IncludeErrorDetails = true;     // mặc định đã là true: đưa error_description vào WWW-Authenticate
        // Mặc định ClockSkew = 5 phút (token hết hạn vẫn được chấp nhận thêm 5 phút).
        // Lab giảm xuống 30 giây để kịch bản "token hết hạn" không phải chờ lâu.
        o.TokenValidationParameters.ClockSkew = TimeSpan.FromSeconds(30);

        o.Events = new JwtBearerEvents
        {
            OnAuthenticationFailed = ctx =>
            {
                LabLog(ctx.HttpContext).LogWarning("[LAB] Token bị từ chối: {Message}", ctx.Exception.Message);
                return Task.CompletedTask;
            },
            OnChallenge = ctx =>
            {
                LabLog(ctx.HttpContext).LogWarning("[LAB] 401 challenge. error={Error} description={Description}",
                    ctx.Error ?? "(none)", ctx.ErrorDescription ?? "(none)");
                return Task.CompletedTask;
            },
            OnForbidden = ctx =>
            {
                LabLog(ctx.HttpContext).LogWarning("[LAB] 403 forbidden. Claims: {Claims}",
                    string.Join(", ", ctx.HttpContext.User.Claims.Select(c => c.Type)));
                return Task.CompletedTask;
            }
        };
    });

builder.Services.AddAuthorization(o =>
{
    // Keycloak đặt scope trong MỘT claim "scope", các giá trị cách nhau bởi dấu cách.
    o.AddPolicy("orders.read", p => p.RequireAssertion(ctx =>
        ctx.User.FindFirst("scope")?.Value
            .Split(' ').Contains("orders.read") == true));

    // [LAB] Policy cho kịch bản 6: phụ thuộc vào TÊN claim "sub".
    o.AddPolicy("has-sub", p => p.RequireClaim("sub"));
});

var app = builder.Build();

app.UseAuthentication();   // 1. đọc token -> HttpContext.User
app.UseAuthorization();    // 2. kiểm tra policy

app.MapGet("/public", () => "ok");

app.MapGet("/me", (ClaimsPrincipal u) =>
        u.Claims.Select(c => new { c.Type, c.Value }))
   .RequireAuthorization();

app.MapGet("/orders", () => new[] { "order-1" })
   .RequireAuthorization("orders.read");

app.MapGet("/profile", (ClaimsPrincipal u) => new { sub = u.FindFirst("sub")?.Value })
   .RequireAuthorization("has-sub");

app.Run("http://localhost:5005");

static ILogger LabLog(HttpContext http) =>
    http.RequestServices.GetRequiredService<ILoggerFactory>().CreateLogger("Lab.Auth");
    • Vì sao app.Run("http://localhost:5005"): cố định cổng, không phụ thuộc launchSettings.json.
    • Vì sao ShowPII: mặc định thư viện Microsoft.IdentityModel che giá trị trong log (thông báo kiểu [PII of type 'System.String' is hidden]) — tốt cho production nhưng khó học.
    • Vì sao Events: để thấy rõ trên console lý do từ chối; trong dự án thật, dùng logging chuẩn là đủ.

    export KC=http://localhost:8080/realms/demo
export API=http://localhost:5005
# Lấy token worker; tham số 1 = scope (có thể rỗng)
worker_token() {
  curl -s -X POST "$KC/protocol/openid-connect/token" \
    -d grant_type=client_credentials -d client_id=worker \
    -d client_secret="$WORKER_SECRET" ${1:+-d scope="$1"} | jq -r .access_token
}
# Decode phần payload của JWT (không kiểm tra chữ ký - chỉ để đọc)
jwt_payload() {
  local p=$(echo -n "$1" | cut -d. -f2 | tr '_-' '/+')
  while [ $(( ${#p} % 4 )) -ne 0 ]; do p="$p="; done
  echo "$p" | base64 -d | jq .
}
    function Get-WorkerToken([string]$Scope) {
  $body = @{ grant_type="client_credentials"; client_id="worker"; client_secret=$env:WORKER_SECRET }
  if ($Scope) { $body.scope = $Scope }
  (Invoke-RestMethod -Method Post -Uri "http://localhost:8080/realms/demo/protocol/openid-connect/token" -Body $body).access_token
}
function Decode-Jwt([string]$Jwt) {
  $p = $Jwt.Split('.')[1].Replace('-', '+').Replace('_', '/')
  switch ($p.Length % 4) { 2 { $p += '==' } 3 { $p += '=' } }
  [Text.Encoding]::UTF8.GetString([Convert]::FromBase64String($p)) | ConvertFrom-Json | ConvertTo-Json -Depth 5
}

(d) Kết quả mong đợi — 6 kịch bản

Kịch bản 1 — Không gửi token → 401
curl -i $API/orders
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer
Content-Length: 0

Không có error= vì đây không phải token sai mà là không có token (RFC 6750 quy định không gửi mã lỗi khi request thiếu thông tin xác thực). Log: AuthenticationScheme: Bearer was challenged.

Kịch bản 2 — Token sai aud → 401

Cách tạo: lấy token worker không xin scope nào → Audience mapper không chạy → aud không chứa demo-api.

TOK=$(worker_token)            # không có scope
jwt_payload "$TOK" | jq .aud   # thường là "account" (hoặc không có aud)
curl -i -H "Authorization: Bearer $TOK" $API/me
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer error="invalid_token", error_description="The audience 'account' is invalid"

warn: Lab.Auth[0] [LAB] Token bị từ chối: IDX10214: Audience validation failed. Audiences: 'account'.
      Did not match: validationParameters.ValidAudience: 'demo-api' or validationParameters.ValidAudiences: 'null'.

Giá trị aud thực tế phụ thuộc cấu hình realm (Keycloak thường thêm account khi token chứa role của client account). Nếu token hoàn toàn không có aud, thông báo sẽ khác (ví dụ IDX10206) nhưng vẫn là 401. Ý nghĩa: chữ ký hợp lệ nhưng token không dành cho API này — phải từ chối (M02).

⚠️ Hiểu lầm hay gặp

Hiểu lầmLỗi audience thì tắt ValidateAudience cho nhanh.Thực tếKhi đó API nhận cả token dành cho API khác (kể cả ID token). Sửa ở IdP (Audience mapper, client xin đúng scope), không tắt kiểm tra.
Hiểu lầmChữ ký hợp lệ nghĩa là token dùng được ở API.Thực tếChữ ký chỉ chứng minh “Keycloak đã phát hành”. Token có aud = account vẫn ký đúng nhưng không dành cho demo-api → 401.
Kịch bản 3 — Token hết hạn → 401

Cách tạo: client worker → tab Advanced → mục Advanced settings → Access Token Lifespan = 1 phút → Save (hoặc đặt ở cấp realm: Realm settings → Tokens → Access Token Lifespan, mặc định 5 phút). Lấy token, chờ > 1 phút + 30 giây ClockSkew, rồi gọi.

TOK=$(worker_token orders.read)
sleep 100
curl -i -H "Authorization: Bearer $TOK" $API/me
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer error="invalid_token", error_description="The token expired at '11/10/2026 08:15:42'"

warn: Lab.Auth[0] [LAB] Token bị từ chối: IDX10223: Lifetime validation failed. The token is expired.
      ValidTo (UTC): '11/10/2026 08:15:42', Current time (UTC): '11/10/2026 08:16:20'.
⚠️ Bẫy ClockSkewNếu không giảm ClockSkew, token hết hạn vẫn được chấp nhận thêm 5 phút — nhiều người tưởng “API không kiểm tra exp”. Nhớ đặt lại Access Token Lifespan về mặc định sau kịch bản này.

⚠️ Hiểu lầm hay gặp

Hiểu lầmLỗi “token expired” (IDX10223) chỉ xảy ra khi token đã cũ.Thực tếAPI so exp với đồng hồ của máy API. Nếu máy API chạy nhanh hơn Keycloak quá ClockSkew, token vừa cấp cũng có thể bị báo hết hạn. Đồng bộ giờ (NTP) trước khi nghi ngờ code.
Kịch bản 4 — Token hợp lệ nhưng thiếu scope orders.read → 403

Cách tạo: xin orders.write thay vì orders.read → aud vẫn có demo-api (vì orders.write cũng có Audience mapper) nhưng scope không chứa orders.read.

TOK=$(worker_token orders.write)
curl -i -H "Authorization: Bearer $TOK" $API/me       # 200 - token hợp lệ
curl -i -H "Authorization: Bearer $TOK" $API/orders   # 403 - thiếu quyền
HTTP/1.1 403 Forbidden
Content-Length: 0
(KHÔNG có header WWW-Authenticate kèm error)

info: Microsoft.AspNetCore.Authorization.DefaultAuthorizationService[2]
      Authorization failed. These requirements were not met:
      AssertionRequirement: Handler assertion should evaluate to true.
info: ...JwtBearerHandler[13] AuthenticationScheme: Bearer was forbidden.

Đây là ranh giới quan trọng nhất: authentication thành công (đã biết caller là ai) nhưng authorization thất bại → 403, không phải 401.

⚠️ Hiểu lầm hay gặp

Hiểu lầmToken hợp lệ nhưng thiếu quyền thì trả 401.Thực tế401 = không xác thực được. Thiếu scope/quyền là 403, và response 403 không có error="invalid_token".
Kịch bản 5 — Gửi ID token thay access token → 401

Cách tạo: chạy DemoClient ở Lab 3, lấy giá trị id_token (được lưu ra file tokens/id_token.txt).

IDT=$(cat ../DemoClient/tokens/id_token.txt)
jwt_payload "$IDT" | jq '{aud, azp, typ, nonce}'
curl -i -H "Authorization: Bearer $IDT" $API/me
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer error="invalid_token", error_description="The audience 'demo-client' is invalid"

Lý do quan sát được: ID token có chữ ký hợp lệ, đúng issuer, còn hạn — nhưng aud = demo-client (ID token dành cho client, không dành cho API). Keycloak còn đặt claim riêng "typ": "ID" (access token là "Bearer"), nhưng JwtBearer mặc định không kiểm tra claim này — chính kiểm tra aud đã chặn. Xem M03 — ID token vs access token.

Kịch bản 6 — Bỏ MapInboundClaims = false → claim bị đổi tên
dotnet run -- --Lab:MapInboundClaims=true
# terminal khác:
TOK=$(worker_token orders.read)
curl -s -H "Authorization: Bearer $TOK" $API/me | jq '.[] | select(.type | test("sub|nameidentifier|scope"))'
curl -i -H "Authorization: Bearer $TOK" $API/profile
curl -i -H "Authorization: Bearer $TOK" $API/orders
{ "type": "http://schemas.xmlsoap.org/ws/2005/05/identity/claims/nameidentifier", "value": "5b1c...-service-account-id" }
{ "type": "scope", "value": "orders.read profile email" }

/profile  -> HTTP/1.1 403 Forbidden   (policy has-sub tìm claim "sub" nhưng nó đã thành ...nameidentifier)
/orders   -> HTTP/1.1 200 OK          (claim "scope" KHÔNG bị đổi tên)
ℹ️ Điểm hay bị hiểu sai (đã kiểm tra mã nguồn Microsoft.IdentityModel) Bảng ánh xạ mặc định (JsonWebTokenHandler.DefaultInboundClaimTypeMap) đổi sub → ClaimTypes.NameIdentifier, email → ClaimTypes.Email, scp → http://schemas.microsoft.com/identity/claims/scope… nhưng không đổi claim tên scope. Vì vậy với Keycloak (dùng scope), policy orders.read vẫn chạy; thứ hỏng là mọi chỗ đọc sub. Với Entra ID (dùng scp), policy kiểm tra scp cũng sẽ hỏng → 403. Bài học: tắt mapping (MapInboundClaims = false) để tên claim trong code giống hệt trong token.

Nhớ chạy lại API không có tham số sau kịch bản này.

⚠️ Hiểu lầm hay gặp

Hiểu lầmBật MapInboundClaims thì mọi policy đều hỏng, kể cả policy orders.read.Thực tếBảng ánh xạ đổi sub, email, scp… nhưng không đổi claim tên scope. Với Keycloak, /orders vẫn 200, chỉ /profile (đọc sub) bị 403. Với Entra ID (claim scp) thì policy scope mới hỏng.

Ví dụ: cùng một token xin orders.write: /me → 200 (chỉ cần token hợp lệ), /orders → 403. Token không đổi, chỉ yêu cầu của endpoint khác nhau — bằng chứng 403 là chuyện quyền, không phải chuyện token.

401 = “bạn là ai?” · 403 = “tôi biết bạn, nhưng không.” Gặp 401 hãy nhìn token; gặp 403 hãy nhìn policy và quyền.

(f) Câu hỏi tự kiểm tra

Vì sao kịch bản 1 không có error="invalid_token" còn kịch bản 2 có?

Kịch bản 1 không có token nào để đánh giá — handler chỉ “challenge” yêu cầu xác thực. Kịch bản 2 có token nhưng token không qua được validation → handler đặt error="invalid_token" và mô tả lý do (vì IncludeErrorDetails = true).

Ở production có nên trả error_description chi tiết không?

Thông tin như “audience invalid” giúp client debug và thường không quá nhạy cảm, nhưng nhiều tổ chức chọn tắt (IncludeErrorDetails = false) để không lộ cấu hình. Dù chọn gì, log phía server phải đủ chi tiết; nhưng không bật ShowPII ở production.

API có gọi Keycloak cho mỗi request không?

Không. API tải discovery + JWKS rồi cache (ConfigurationManager tự làm mới định kỳ hoặc khi gặp kid lạ). Mỗi token được xác minh cục bộ bằng khóa công khai — đó cũng là lý do token đã thu hồi vẫn được chấp nhận đến khi hết hạn (xem Lab 4).
