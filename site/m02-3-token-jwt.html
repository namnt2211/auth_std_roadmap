Bài 2.3 — Token & JWT

Token là “vé” chứng minh bạn đã đăng nhập hoặc được cấp quyền. Bài này giúp bạn phân biệt 3 loại token (access / ID / refresh), hiểu token dạng chuỗi ngẫu nhiên (opaque) khác JWT thế nào, đọc được một JWT, và biết API phải kiểm tra những gì trước khi tin nó.

D. Token concepts Must

📖 Thuật ngữ trong bài
Authorization Server (AS)
Máy chủ đăng nhập và phát token, trong ví dụ là Keycloak realm kaopiz.
Resource Server (RS) / API
Nơi giữ dữ liệu, nhận token và quyết định cho truy cập hay không, vd. hr-api.
Client
Ứng dụng xin token thay mặt người dùng, vd. hr-web.
Access token
“Vé” client đưa cho API để được gọi API; sống ngắn (vài phút).
ID token
“Biên nhận đăng nhập” AS đưa cho client để client biết ai vừa đăng nhập.
Refresh token
“Giấy hẹn đổi vé” — client đem tới AS để lấy access token mới mà không bắt đăng nhập lại.
Opaque token
Token là chuỗi ngẫu nhiên, không đọc được gì bên trong; phải hỏi AS mới biết nó là gì.
JWT
Token dạng JSON có chữ ký, tự mang thông tin (claims) bên trong.
Claim
Một mẩu thông tin trong token, dạng "tên": giá trị, vd. "sub": "8f2c…".
JWKS / kid
Danh sách public key AS công bố / mã số cho biết token được ký bằng key nào trong danh sách đó.
Nói đơn giản Access token giống thẻ ra vào tòa nhà có hạn dùng: quẹt ở cửa (API) là vào, ai nhặt được cũng quẹt được, nên hạn dùng ngắn. Refresh token giống giấy hẹn đổi thẻ mới ở quầy lễ tân (Authorization Server) — không quẹt được ở cửa. ID token giống biên nhận “đã kiểm tra căn cước” lễ tân đưa cho công ty mời bạn đến (client) — chứ không phải đưa cho bảo vệ ở cửa.
  • Token: một chuỗi ký tự đại diện cho thông tin/quyền. Có 2 kiểu: token tự mang thông tin bên trong (JWT), hoặc chỉ là số tham chiếu tới thông tin lưu ở server (opaque token).
  • Access Token: dùng để gọi Resource Server/API. Người nhận (audience) là API.
  • ID Token: thuộc OIDC (OpenID Connect — lớp “đăng nhập” xây trên OAuth, học ở M03). Nó cho client biết ai vừa đăng nhập, lúc nào, bằng cách nào. Người nhận là client (còn gọi là RP — Relying Party). Luôn là JWT.
  • Refresh Token: dùng để xin access token mới từ Authorization Server. Chỉ gửi tới AS, không dùng gọi API.

Ví dụ: An đăng nhập hr-web qua Keycloak và nhận về cả 3 token.

  1. hr-web đọc ID token để hiện “Xin chào, An” và biết sub của An — rồi giữ nó lại, không gửi đi đâu.
  2. hr-web gửi access token trong Authorization: Bearer … khi gọi GET https://hr-api/payroll/57.
  3. 5 phút sau access token hết hạn → hr-web gửi refresh token tới token endpoint của Keycloak để lấy access token mới. An không phải nhập lại mật khẩu.

Nếu hr-web gửi nhầm ID token cho hr-api, hr-api phải từ chối (sai aud, sai loại token). Nếu gửi refresh token cho hr-api thì vừa sai, vừa làm lộ token quan trọng nhất.

Access → API · ID → client · Refresh → AS. Hỏi “token này gửi cho ai?” là phân biệt được.

Ví dụ: ID token của An do Keycloak ký thật, nhưng aud là hr-web → hr-api phải từ chối. Hỏi “token này gửi cho ai?” để phân biệt.
Hiểu lầmRefresh token là “access token sống lâu”, dùng gọi API cho đỡ phải refresh.Thực tếRefresh token không được gửi tới API — API không chấp nhận nó, và gửi đi khắp nơi chỉ làm tăng nguy cơ lộ token quan trọng nhất. Nó chỉ đi tới token endpoint của AS.

Opaque token vs JWT

Access token có thể ở một trong hai dạng. Điểm khác cốt lõi: thông tin nằm ở đâu — trong chính token (JWT) hay ở server của AS (opaque).

Ví dụ: hr-api nhận JWT từ Keycloak và tự verify — rất nhanh, không phải gọi mạng. Giả sử có thêm một API duyệt chi lương rất nhạy cảm, cần khóa user là có hiệu lực ngay: API đó nên dùng opaque token (hoặc introspect cả JWT) để mỗi request đều hỏi AS “token này còn hiệu lực không?”.

Opaque = “số vé, phải tra sổ”; JWT = “vé in sẵn thông tin, có tem chống giả”.

⚠️ Hiểu lầm hay gặp

Hiểu lầmAccess token thì luôn là JWT.Thực tếOAuth không quy định định dạng access token. Nhiều AS phát opaque token (chuỗi ngẫu nhiên không có dấu chấm). Gặp token không decode được thì đó có thể là opaque token — API phải dùng introspection, không phải token “hỏng”.

JWT, JWS và JWE Should (JWE)

Ba cái tên này hay bị dùng lẫn. Thực ra JWT là định dạng nội dung, còn JWS và JWE là hai cách đóng gói nó: ký hoặc mã hóa.

Phân biệt dễ nhầm: JWT vs JWS vs JWE
Tiêu chíJWT (RFC 7519)JWS (RFC 7515)JWE (RFC 7516)
Là gìĐịnh dạng để biểu diễn claims (các cặp thông tin JSON)Cách ký nội dungCách mã hóa nội dung
Bảo vệ điều gìTự nó không bảo vệ gì — cần JWS hoặc JWEToàn vẹn + nguồn gốc: không sửa được, biết ai phát hànhBí mật: người ngoài không đọc được

Đọc được payload?—✅ Ai cầm cũng đọc được❌ Chỉ người giữ key giải mã

Ví dụ: khi người ta nói “access token của Keycloak là JWT”, ý thực sự là “một JWT được ký theo JWS” — nên bạn đếm thấy đúng 3 phần. Nếu bạn đếm được 5 phần, đó là JWE.

JWT = nội dung; JWS = có tem (3 phần); JWE = bỏ phong bì kín (5 phần).
🚫 JWT ký ≠ payload bí mật Payload của JWS chỉ được Base64url-encode — ai cầm token cũng đọc được (thử với widget bên dưới). Đừng bao giờ đặt mật khẩu, số CMND, lương… vào payload của JWT ký. Cần giấu → dùng JWE, hoặc dùng opaque token.

⚠️ Hiểu lầm hay gặp

Hiểu lầmJWT đã ký nên nội dung bí mật.Thực tếChữ ký chỉ chống sửa đổi, không chống đọc. Payload JWS chỉ là Base64url — ai cầm token cũng đọc được (dán vào widget bên dưới là thấy preferred_username, scope…). Cần bí mật → JWE hoặc opaque token.

E.1. JWT validation — checklist cho access token Must

Nói đơn giản Bảo vệ ở cửa tòa nhà kiểm tra thẻ theo thứ tự: tem chống giả thật không (chữ ký) → do đúng công ty phát hành không (iss) → thẻ dành cho tòa nhà này không (aud) → còn hạn không (exp/nbf) → đúng loại thẻ ra vào không, không phải biên nhận (token type) → có quyền vào tầng này không (scope/role).

Deliverable 5. Checklist cho API khi nhận access token JWT. Thực tế bạn không tự code từng bước — thư viện (JwtBearer) làm giúp. Nhưng bạn cần hiểu checklist để cấu hình đúng và đọc được lỗi 401. M03 sẽ bổ sung phần validation ID token (nonce, aud = client_id…).

  • Định dạng: đúng 3 phần (JWS); token lấy từ header Authorization: Bearer, không từ query string.
  • Thuật toán: alg nằm trong allowlist do API cấu hình (vd. chỉ RS256). Từ chối none (token không ký); không để token tự chọn thuật toán. Lý do: tấn công “alg confusion” — kẻ gian đổi alg từ RS256 sang HS256 và ký bằng chính public key (vốn công khai); API lỏng lẻo sẽ dùng public key làm secret HMAC và chấp nhận.
  • Chữ ký: verify bằng key đáng tin cậy — public key lấy từ JWKS của issuer đã cấu hình (qua HTTPS), chọn theo kid. Không lấy key từ chính token (vd. header jku/jwk do token tự khai).
  • iss khớp chính xác issuer mong đợi (kể cả dấu / cuối).
  • aud chứa định danh của chính API này (vd. hr-api).
  • Thời hạn: exp chưa qua, nbf (nếu có) đã tới; clock skew nhỏ (vài chục giây đến vài phút).
  • Đúng loại token/ngữ cảnh: là access token, không phải ID token hay refresh token (kiểm tra typ header nếu IdP dùng at+jwt, hoặc claim/audience đặc trưng).
  • Quyền: có scope/role cần thiết cho endpoint (thiếu → 403 + insufficient_scope), sau đó còn kiểm tra quyền trên dữ liệu cụ thể (An chỉ xem payroll của An — M06).
  • Tùy yêu cầu: kiểm tra thu hồi (introspection/denylist jti), ràng buộc sender (DPoP/mTLS), client được phép (azp/client_id).
  • Không tự viết: dùng thư viện đã kiểm chứng (Microsoft.IdentityModel / JwtBearer); log lý do từ chối ở server, không lộ chi tiết cho client.

Lỗi xác thực token → 401; token hợp lệ nhưng thiếu quyền → 403 (nhắc lại M01).
🧪 Ví dụ: 4 request tới hr-api, 4 kết quả
  • Token mẫu của An, gọi GET /payroll/57 (payroll của An) lúc 09:03 → mọi bước qua → 200.
  • Cùng token đó gọi lúc 09:07 → exp đã qua → 401 invalid_token. hr-web cần refresh.
  • Token có aud: report-api → sai audience → 401 invalid_token.
  • Token hợp lệ của An gọi PUT /payroll/57 cần hr.write → thiếu scope → 403 insufficient_scope.
Nhớ: 401 = “tôi không tin token này”; 403 = “tôi tin token, nhưng bạn không được làm việc này”.

Đoạn code dưới cho thấy checklist trên được “bật” trong ASP.NET Core như thế nào. Điều cần rút ra: chỉ cần khai báo Authority (issuer) và Audience, thư viện tự tải JWKS, chọn key theo kid và kiểm tra chữ ký, iss, aud, exp.

using Microsoft.AspNetCore.Authentication.JwtBearer;
using Microsoft.IdentityModel.Tokens;

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(o =>
    {
        // Authority → tự tải discovery document + JWKS (và làm mới khi key rotation)
        o.Authority = "https://sso.kaopiz.local/realms/kaopiz";
        o.Audience  = "hr-api";
        // Mặc định (true) đổi tên claim: sub → ClaimTypes.NameIdentifier,
        // scp → ".../identity/claims/scope" (claim "scope" của Keycloak thì KHÔNG bị đổi)
        o.MapInboundClaims = false;            // giữ nguyên tên claim gốc: sub, scope...
        o.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true,
            ValidateAudience = true,
            ValidateLifetime = true,
            ValidateIssuerSigningKey = true,
            ValidAlgorithms = new[] { SecurityAlgorithms.RsaSha256 },
            ClockSkew = TimeSpan.FromSeconds(30) // mặc định là 5 phút
        };
    });

builder.Services.AddAuthorization(o =>
    o.AddPolicy("hr.read", p => p.RequireAssertion(ctx =>
        ctx.User.FindFirst("scope")?.Value.Split(' ').Contains("hr.read") == true)));
⚠️ Đừng tắt validation để “cho chạy được” Gặp lỗi audience? Đừng đặt ValidateAudience = false — sửa cấu hình để token có đúng aud. Các cách troubleshooting lỗi 401 xem Lab — bảng lỗi và M07.
