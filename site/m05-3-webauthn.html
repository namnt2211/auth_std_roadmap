Bài 5.3 — WebAuthn: thành phần, đăng ký, đăng nhập

Đăng nhập không cần mật khẩu hoạt động thế nào? Bài này giới thiệu các “mảnh ghép” FIDO2, WebAuthn, CTAP, rồi đi qua hai bước chính: đăng ký (thiết bị tạo cặp khóa, gửi public key cho website) và đăng nhập (thiết bị ký câu đố, website kiểm chữ ký).

A. Các thành phần Must

Nói đơn giản Thay vì một mật khẩu (bí mật mà cả bạn và server cùng biết), bạn có một cặp chìa khóa: chìa riêng (private key) nằm trong điện thoại/security key và không bao giờ rời khỏi đó; ổ khóa (public key) gửi cho website. Mỗi lần đăng nhập, website đưa một câu đố mới, thiết bị dùng chìa riêng “ký” câu đố, website dùng ổ khóa kiểm tra. Server bị hack cũng chỉ lộ ổ khóa — vô dụng với kẻ trộm.

Sơ đồ dưới cho thấy ai nói chuyện với ai: website chỉ nói chuyện với trình duyệt (qua WebAuthn); trình duyệt/hệ điều hành mới là bên nói chuyện với authenticator (qua CTAP nếu authenticator nằm ngoài máy).

B. Đăng ký (Registration)

Nói đơn giản Như làm chìa khóa mới cho một ổ khóa: website đưa “mã đơn hàng” (challenge) để chống làm giả; thiết bị của bạn đúc một cặp chìa–ổ riêng cho website này, giữ chìa, gửi ổ khóa cho website cất.

Đăng ký xảy ra một lần cho mỗi thiết bị/passkey, thường khi An đã đăng nhập bằng cách cũ và vào trang “Bảo mật → Tạo passkey”. Điều cần rút ra từ sơ đồ: private key sinh ra và ở lại trong authenticator; thứ đi về server chỉ là public key + credential ID (+ attestation nếu có).

Registration: private key được sinh và giữ trong authenticator; RP chỉ nhận public key.

Code JS phía trình duyệt khá ngắn: lấy options từ server → gọi navigator.credentials.create() → gửi kết quả về server. Phần khó (kiểm tra) nằm ở server. Hai trường đáng chú ý trong options: user.id là user handle (mã ngẫu nhiên đại diện cho An, không chứa email); residentKey: "required" yêu cầu tạo credential discoverable (authenticator tự nhớ tài khoản, nên lúc đăng nhập không cần gõ username).

// Server trả về options (các trường nhị phân ở dạng base64url).
// WebAuthn L3 có helper chuyển JSON -> options:
const serverJson = await (await fetch("/passkeys/register/options", { method: "POST" })).json();
const publicKey = PublicKeyCredential.parseCreationOptionsFromJSON(serverJson);

// Nội dung tương đương (PublicKeyCredentialCreationOptions):
// {
//   challenge: <ArrayBuffer 32 byte ngẫu nhiên từ server>,
//   rp:   { id: "hr.company.com", name: "Kaopiz HR" },
//   user: { id: <user handle: byte ngẫu nhiên, KHÔNG phải email>,
//           name: "an.nv@company.com", displayName: "Nguyễn Văn An" },
//   pubKeyCredParams: [ { type: "public-key", alg: -7 },     // ES256
//                       { type: "public-key", alg: -257 } ], // RS256
//   authenticatorSelection: { residentKey: "required", userVerification: "preferred" },
//   attestation: "none",
//   excludeCredentials: [ /* credential đã đăng ký, tránh tạo trùng */ ],
//   timeout: 60000
// }

const credential = await navigator.credentials.create({ publicKey });
await fetch("/passkeys/register", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify(credential.toJSON())   // clientDataJSON + attestationObject (base64url)
});

Kết quả gửi về server gồm hai “gói” chính. Bạn cần nhớ: clientDataJSON do trình duyệt viết (chứa challenge và origin thật); authenticatorData do authenticator viết (chứa hash của RP ID và các cờ). Server kiểm cả hai.

clientDataJSON (do browser tạo)

{
  "type": "webauthn.create",
  "challenge": "q4vT8xP2...base64url",
  "origin": "https://hr.company.com",
  "crossOrigin": false
}

Browser tự điền origin thật của trang — JS của trang không thể giả mạo. Khi đăng nhập, type là webauthn.get.

authenticatorData (do authenticator tạo)

TrườngKích thướcÝ nghĩa
rpIdHash32 byteSHA-256 của RP ID
flags1 byteBit 0 UP, bit 2 UV, bit 3 BE, bit 4 BS, bit 6 AT, bit 7 ED
signCount4 byteBộ đếm chữ ký (có thể luôn = 0)

Flags: UP = User Present; UV = User Verified; BE = Backup Eligible (có thể sao lưu/đồng bộ); BS = Backup State (đang được sao lưu); AT = có attested credential data; ED = có extension data.

ℹ️ Attestation là gì? Attestation là “giấy chứng nhận xuất xưởng” của authenticator: chứng minh credential được tạo bởi loại thiết bị nào (qua AAGUID và chữ ký của nhà sản xuất). Giá trị attestation: "none" (mặc định, phù hợp hầu hết website công khai), "indirect", "direct", "enterprise". Doanh nghiệp chỉ cho phép security key được cấp phát mới cần yêu cầu và kiểm attestation (thường đối chiếu FIDO Metadata Service).

Ví dụ: khi An tạo passkey trên YubiKey, server HR có thể nhận attestation cho biết “đây là YubiKey 5 thật” (qua AAGUID — mã định danh model authenticator). Mỗi lần An đăng nhập sau đó, server nhận assertion gồm chữ ký trên challenge mới. Không có XML, không có IdP nào ở đây — khác hẳn SAML Assertion.

Attestation = giấy xuất xưởng (lúc đăng ký). Assertion = chữ ký đăng nhập (mỗi lần login). Trùng chữ “assertion” với SAML nhưng khác hoàn toàn.

Hiểu lầm“Assertion” trong WebAuthn giống SAML Assertion.Thực tếWebAuthn assertion là chữ ký của authenticator trên challenge khi đăng nhập, kiểm bằng public key RP đã lưu; SAML Assertion là tài liệu XML do IdP ký. Chỉ trùng tên. Xem so sánh.
Hiểu lầmWebsite nào cũng nên yêu cầu attestation "direct" cho chắc.Thực tếWebsite công khai thường để "none": attestation chỉ cho biết loại thiết bị, không chứng minh người dùng là ai, và đòi hỏi nhiều sẽ chặn nhầm nhiều passkey hợp lệ. Chỉ doanh nghiệp cần giới hạn loại authenticator mới yêu cầu và kiểm attestation.
Hiểu lầmLộ public key hoặc credential ID của An là nguy hiểm như lộ mật khẩu.Thực tếCả hai đều không bí mật; không có private key thì không ký được challenge. Đó là lý do lộ bảng passkeys không cho kẻ tấn công đăng nhập.

C. Đăng nhập (Authentication)

Nói đơn giản Website đưa một câu đố mới tinh. Thiết bị hỏi bạn vân tay/PIN để “mở két”, rồi dùng chìa riêng ký câu đố kèm theo tên website đang hiện trên thanh địa chỉ. Website kiểm: đúng câu đố mình vừa đưa, đúng tên mình, chữ ký khớp ổ khóa đã cất.

Luồng đăng nhập có hình dạng giống đăng ký, nhưng lần này không tạo khóa mới: authenticator dùng private key đã có để ký. allowCredentials: [] (rỗng) nghĩa là “bất kỳ passkey nào của site này” — authenticator tự đưa danh sách tài khoản cho An chọn, nhờ đó An không cần gõ username.

RP phải kiểm tra gì? Must

#Kiểm traVì sao
1clientDataJSON.type = webauthn.create / webauthn.getKhông dùng lẫn dữ liệu đăng ký và đăng nhập.
2challenge = challenge server vừa phát, chưa dùng, còn hạnChống replay (gửi lại một phản hồi cũ đã bắt được). Challenge phải mới, ngẫu nhiên, dùng một lần.
3origin nằm trong danh sách origin được phép (vd. https://hr.company.com)Chống phishing: trang giả có origin khác.
4rpIdHash = SHA-256(RP ID mong đợi)Credential thuộc đúng website.
5Flag UP bật; UV bật nếu policy yêu cầuCó người thật thao tác; người đó đã được xác minh (PIN/sinh trắc).
6Chữ ký hợp lệ với public key đã lưu của credential ID nàyChứng minh sở hữu private key.
7Credential thuộc đúng user (userHandle khớp), chưa bị thu hồiXác định subject.
8signCount: nếu giá trị mới hoặc giá trị đã lưu khác 0, mà giá trị mới không lớn hơn giá trị đã lưu → nghi ngờ nhân bảnTín hiệu rủi ro (passkey đồng bộ thường luôn trả 0).
9(Đăng ký) thuật toán được phép, attestation theo policy, credential ID chưa tồn tạiĐảm bảo chất lượng credential.
