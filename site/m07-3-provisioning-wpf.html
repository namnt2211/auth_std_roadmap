Bài 7.3 — Provisioning & ví dụ WPF + API

Vòng đời tài khoản (provisioning/offboarding) và ví dụ tổng hợp WPF + ASP.NET Core Web API.

⏱ ~15 phút 📘 Module 07 · Architecture & Practical Cases

C. Provisioning, deprovisioning và offboarding Should

Nói đơn giản Provisioning = làm thẻ cho nhân viên mới ở từng phòng ban. JIT giống “ai đến cửa lần đầu thì làm thẻ ngay tại chỗ” — nhanh, nhưng không ai báo khi người đó nghỉ việc. SCIM giống phòng nhân sự gửi danh sách cho mọi phòng ban: ai vào, ai đổi vị trí, ai nghỉ — cập nhật ngay. Và khóa tài khoản ở cổng chính chưa đủ: thẻ đang cầm trên tay (session, refresh token) phải bị thu hồi.
📖 Thuật ngữ trong bài
Provisioning
Tạo (và cập nhật) tài khoản cho người dùng trong từng ứng dụng.
Deprovisioning
Vô hiệu hóa hoặc xóa tài khoản trong ứng dụng.
Offboarding
Toàn bộ quy trình khi nhân viên nghỉ việc: khóa tài khoản, thu hồi phiên/token, thiết bị, key…
JIT provisioning
App tự tạo tài khoản ngay lần đầu người dùng đăng nhập SSO.
SCIM
Chuẩn REST API để IdP chủ động báo cho app: tạo, sửa, khóa user/group.
Revoke
Thu hồi một token/phiên trước khi nó tự hết hạn.
CAE
Continuous Access Evaluation: IdP báo cho API “user này vừa bị khóa” để API từ chối token sớm.
DPAPI
API của Windows mã hóa dữ liệu bằng khóa gắn với tài khoản Windows của người dùng.

Ví dụ: An chuyển công ty. Deprovisioning là việc Kaopiz HR khóa account của An. Offboarding là cả danh sách: khóa An ở Entra ID/Keycloak, khóa account ở Kaopiz HR và các app khác, thu hồi refresh token trên app mobile, thu hồi laptop, xóa passkey, đổi mật khẩu Wi-Fi khách mà An biết.

Deprovisioning là một bước; offboarding là cả quy trình.

Có hai cách để app nhận được thông tin tài khoản từ IdP — JIT và SCIM. Khác biệt quan trọng nhất là app có biết khi user nghỉ việc hay không:

Phân biệt dễ nhầm: JIT provisioning vs SCIM
JIT (Just-in-Time) provisioningSCIM 2.0 (RFC 7643 / 7644)
Cách hoạt độngApp tạo account khi user đăng nhập SSO lần đầu, dựa trên claims/attributes trong token/assertion.IdP chủ động đẩy thao tác tạo, cập nhật, vô hiệu hóa user/group sang app qua REST API chuẩn.
Ưu điểmĐơn giản, không cần API riêng.Offboarding gần như tức thời; đồng bộ group; tạo account trước khi user đăng nhập.
Nhược điểmApp không biết khi nào user nghỉ việc/đổi phòng; thuộc tính chỉ cập nhật khi user đăng nhập lại.App phải triển khai endpoint SCIM; xử lý lỗi đồng bộ.
ChuẩnKhông có chuẩn riêng (dựa trên OIDC/SAML).RFC 7643 (schema: User, Group, thuộc tính active…), RFC 7644 (protocol: /Users, /Groups, PATCH…).

Ví dụ: Kaopiz HR dùng JIT. Lần đầu An đăng nhập, hr-web đọc sub, email, name trong ID token và tạo account. Khi An nghỉ việc, An bị khóa ở IdP — nhưng account trong Kaopiz HR vẫn “active”, và báo cáo “nhân viên đang làm việc” của HR vẫn đếm An. Với SCIM, IdP gửi ngay PATCH active=false (request mẫu bên dưới) tới Kaopiz HR.

JIT = app biết khi bạn đến. SCIM = app biết cả khi bạn đi.

Đây là request IdP gửi khi khóa một user qua SCIM — chỉ đổi một thuộc tính active thành false:

PATCH /scim/v2/Users/2819c223-7f76-453a-919d-413861904646 HTTP/1.1
Host: orders.example.com
Authorization: Bearer eyJ...   (token của IdP để gọi SCIM endpoint)
Content-Type: application/scim+json

{
  "schemas": ["urn:ietf:params:scim:api:messages:2.0:PatchOp"],
  "Operations": [
    { "op": "replace", "path": "active", "value": false }
  ]
}
⚠️ Vô hiệu hóa ở IdP chưa phải là offboarding Khóa tài khoản ở IdP chỉ chặn đăng nhập mới. Những thứ đã cấp trước đó vẫn sống:
  • Session cookie của các app và refresh token đã cấp vẫn còn hiệu lực.
  • Access token JWT vẫn dùng được đến khi hết hạn, vì API tự kiểm tra chữ ký chứ không hỏi lại IdP.
Cần thêm:
  • Revoke session/refresh token; access token ngắn hạn.
  • SCIM để app vô hiệu hóa account.
  • Cơ chế đánh giá liên tục nếu IdP hỗ trợ — ví dụ Continuous Access Evaluation (CAE) của Microsoft Entra ID (resource provider được báo sự kiện như vô hiệu hóa user, đổi mật khẩu và từ chối token sớm), hoặc chuẩn OpenID Shared Signals Framework / CAEP.

Offboarding đầy đủ: IdP + app (SCIM) + token (revoke, lifetime ngắn, CAE).

⚠️ Hiểu lầm hay gặp

Hiểu lầmKhóa tài khoản ở IdP là nhân viên mất quyền ngay.Thực tếKhóa ở IdP chỉ chặn đăng nhập mới. Session cookie của app và token đã cấp vẫn sống; cần revoke, access token ngắn hạn, SCIM, CAE.
Hiểu lầmDùng JIT provisioning thì nhân viên nghỉ việc cũng tự bị khóa trong app.Thực tếJIT chỉ tạo account khi đăng nhập lần đầu; app không được báo khi user nghỉ. Cần SCIM hoặc quy trình deprovisioning riêng.
Hiểu lầmRevoke refresh token là access token JWT đã cấp hết hiệu lực ngay.Thực tếAPI kiểm tra JWT bằng chữ ký (JWKS), không hỏi lại IdP, nên access token cũ vẫn được chấp nhận đến exp. Revoke chỉ chặn việc xin token mới. Muốn chặn sớm hơn: lifetime ngắn (5–15 phút), introspection, hoặc CAE.

D. Ví dụ tổng hợp: WPF + ASP.NET Core Web API Must

Nói đơn giản App WPF là khách, IdP là quầy cấp thẻ, Web API là cửa kho. Khách ra quầy (qua trình duyệt thật) lấy thẻ; cửa kho tự kiểm tra thẻ thật/giả, còn hạn, đúng kho, rồi xem nội quy (policy) để quyết định cho lấy món hàng nào. Kho không bao giờ tin câu “tôi là quản lý” do khách tự nói.

Phần này ghép mọi thứ đã học thành một hệ thống hoàn chỉnh: app desktop WPF cho nhân viên xem đơn hàng, gọi Order API viết bằng ASP.NET Core. Khi đọc sơ đồ, để ý hai điều: token đi qua trust boundary ở đâu, và ai quyết định quyền (luôn là API).

Order API kiểm tra: iss đúng realm, aud là chính nó (orders-api), exp chưa qua, chữ ký khớp JWKS. Sau đó mới xét quyền: có scope orders.read? đơn hàng này có thuộc người dùng sub không? Trường azp cho biết token được cấp cho client nào (ở đây là app WPF).

D.3. Code tham khảo phía WPF

Hai đoạn code dưới làm cùng một việc cho hai IdP khác nhau: mở system browser, nhận code qua loopback, đổi lấy token (PKCE tự động), rồi cất token đã mã hóa. Bạn không cần nhớ từng dòng — chỉ cần thấy không có client secret và không có WebView.

Với Keycloak (như Lab 3): thư viện Duende.IdentityModel.OidcClient (trước đây là IdentityModel.OidcClient). Lớp SystemBrowser dưới đây không có sẵn trong thư viện — lấy từ sample của dự án (mở browser + HttpListener trên loopback).

using Duende.IdentityModel.OidcClient;
using System.Security.Cryptography;

public sealed class LoginService
{
    private readonly OidcClient _client;

    public LoginService()
    {
        var port = GetFreeTcpPort();
        _client = new OidcClient(new OidcClientOptions
        {
            Authority   = "http://localhost:8080/realms/demo",
            ClientId    = "wpf-client",                       // public client, KHÔNG có secret
            Scope       = "openid profile orders.read offline_access",
            RedirectUri = $"http://127.0.0.1:{port}/",
            Browser     = new SystemBrowser(port)             // từ sample: mở system browser + loopback
        });
    }

    public async Task<LoginResult> LoginAsync()
    {
        var result = await _client.LoginAsync(new LoginRequest());   // PKCE, state, nonce tự động
        if (result.IsError) throw new InvalidOperationException(result.Error);

        // Lưu refresh token đã mã hóa theo user Windows (DPAPI)
        var protectedBytes = ProtectedData.Protect(
            System.Text.Encoding.UTF8.GetBytes(result.RefreshToken),
            optionalEntropy: null,
            scope: DataProtectionScope.CurrentUser);
        await File.WriteAllBytesAsync(TokenFilePath, protectedBytes);

        return result;   // result.AccessToken dùng để gọi API; result.IdentityToken cho client
    }
    // GetFreeTcpPort(), TokenFilePath ... bỏ qua cho gọn
}

Với Microsoft Entra ID: dùng MSAL.NET + cache đa nền tảng (theo Microsoft Learn — token cache serialization):

var pca = PublicClientApplicationBuilder.Create(clientId)
    .WithAuthority($"https://login.microsoftonline.com/{tenantId}")
    .WithRedirectUri("http://localhost")          // MSAL tự chọn port, mở system browser
    .Build();

var storage = new StorageCreationPropertiesBuilder("msal.cache", cacheDir).Build();
var cacheHelper = await MsalCacheHelper.CreateAsync(storage);   // Windows: mã hóa bằng DPAPI
cacheHelper.RegisterCache(pca.UserTokenCache);

string[] scopes = { "api://orders-api/orders.read" };
AuthenticationResult result;
try
{
    var account = (await pca.GetAccountsAsync()).FirstOrDefault();
    result = await pca.AcquireTokenSilent(scopes, account).ExecuteAsync();   // cache / refresh
}
catch (MsalUiRequiredException)
{
    result = await pca.AcquireTokenInteractive(scopes)
        .WithUseEmbeddedWebView(false)            // system browser
        .ExecuteAsync();
}
httpClient.DefaultRequestHeaders.Authorization =
    new AuthenticationHeaderValue("Bearer", result.AccessToken);
