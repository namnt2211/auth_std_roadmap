Bài 6.3 — CSRF, XSS & session fixation

Bài này mở đầu bằng “bản đồ” các tấn công phổ biến, rồi đi sâu vào ba tấn công web kinh điển nhắm vào cookie và session: CSRF (mượn tay trình duyệt gửi request), XSS (chèn script vào trang) và session fixation (cài sẵn phiên cho nạn nhân) — cơ chế của từng cái và cách chặn.

C. Threats và rủi ro phổ biến Must

Mục tiêu là nhận diện rủi ro và thiết kế phòng vệ, không phải thực hành tấn công.

📖 Thuật ngữ trong bài
Origin / site
Origin = scheme + host + port (https://hr.kaopiz.com). Site rộng hơn: chỉ xét scheme + tên miền đăng ký (kaopiz.com), nên a.kaopiz.com và b.kaopiz.com là cùng site.
CSRF
Trang độc dụ trình duyệt của bạn gửi request tới app bạn đang đăng nhập, cookie tự đi kèm.
XSS
Script của kẻ gian lọt vào và chạy bên trong trang của app bạn.
SameSite
Thuộc tính cookie quyết định cookie có được gửi kèm request xuất phát từ site khác hay không.
CSP
Content Security Policy: header HTTP khai báo trình duyệt được chạy script từ đâu.
Session fixation / hijacking
Cài sẵn session ID cho nạn nhân trước khi họ login / lấy trộm session ID sau khi họ login.
MITM / AiTM
Kẻ đứng giữa nghe lén đường truyền / trang phishing đứng giữa người dùng và trang login thật.
Rate limit / throttling
Giới hạn số request trong một khoảng thời gian.
Sender-constrained token
Token gắn với khóa của client (DPoP — RFC 9449, hoặc mTLS — RFC 8705): bị lấy cắp cũng không dùng được nếu thiếu khóa.
SIM swap
Kẻ gian thuyết phục nhà mạng chuyển số điện thoại của nạn nhân sang SIM mới của chúng.

Bảng dưới là bản đồ tổng quan: mỗi dòng một kiểu tấn công, kẻ gian muốn gì, dấu hiệu nhận biết và cách chặn chính. Lần đầu chỉ cần đọc lướt cột “Mục tiêu”; các tấn công quan trọng nhất có link “chi tiết” sang phần giải thích riêng.

C.1. CSRF — Cross-Site Request Forgery

Nói đơn giản CSRF (giả mạo request liên trang) giống việc kẻ gian gửi một lá thư đã điền sẵn “chuyển 10 triệu cho X” vào hộp thư công ty bạn, và nhân viên bưu điện tự động đóng dấu của bạn lên mọi thư gửi tới ngân hàng của bạn. Kẻ gian không cần biết con dấu (cookie) trông thế nào — chỉ cần lợi dụng việc nó được đóng tự động.

Browser tự động gửi cookie của site A khi có request tới site A — kể cả khi request đó được khởi tạo từ trang của kẻ tấn công. Nếu app chỉ dựa vào cookie để xác thực, kẻ tấn công có thể khiến nạn nhân thực hiện hành động mà không biết.

sequenceDiagram
  participant V as Nạn nhân (Browser)
  participant Bank as bank.example (đã đăng nhập)
  participant Evil as evil.example
  V->>Bank: Đăng nhập, nhận cookie session=abc
  Note over V: Vẫn đang đăng nhập, mở tab khác
  V->>Evil: Mở trang evil.example
  Evil-->>V: HTML có form ẩn tự submit
  V->>Bank: POST /transfer to=hacker, 10tr
  Note over V,Bank: Browser tự gắn Cookie session=abc
  Note over Bank: Cookie hợp lệ → server tưởng nạn nhân tự chuyển tiền
  Bank-->>V: 200 OK ❌
CSRF: kẻ tấn công không đọc được cookie, chỉ “mượn” việc browser tự gửi cookie.
<form action="https://bank.example/transfer" method="POST" id="f">
  <input type="hidden" name="to" value="hacker">
  <input type="hidden" name="amount" value="10000000">
</form>
<script>document.getElementById("f").submit();</script>
Giá trị SameSiteCookie được gửi trong request cross-site?Ghi chú
StrictKhông gửi trong mọi request cross-site (kể cả bấm link từ site khác).An toàn nhất nhưng user bấm link từ email sẽ thấy như “chưa đăng nhập”.
LaxChỉ gửi khi điều hướng top-level bằng method an toàn (GET bấm link); không gửi với POST form, fetch, iframe cross-site.Cân bằng tốt. Trình duyệt Chromium mặc định coi cookie không khai báo SameSite là Lax; đừng dựa vào mặc định — khai báo rõ.

⚠️ SameSite không phải là tất cả “Site” = scheme + registrable domain (vd example.com). evil.example.com (subdomain bị chiếm) là same-site với app.example.com → SameSite không chặn. Vì vậy vẫn nên kết hợp anti-CSRF token hoặc kiểm tra Origin, đặc biệt cho request thay đổi trạng thái. Và GET không được thay đổi trạng thái.

Phòng vệ nhiều lớp — dùng kết hợp, không chọn một:

  1. Cookie SameSite=Lax hoặc Strict.
  2. Anti-forgery token (mã chống giả mạo): một giá trị ngẫu nhiên app nhúng vào form/header (kiểu synchronizer token hoặc double-submit). Trang của kẻ tấn công không đọc được giá trị này nên không gửi kèm được.
  3. Kiểm tra header Origin/Referer: request thay đổi dữ liệu mà đến từ origin lạ → từ chối.
  4. Với SPA/BFF: yêu cầu một custom header (vd X-CSRF: 1). Trình duyệt không cho trang cross-site gửi custom header nếu không qua CORS preflight (bước trình duyệt hỏi server “có cho phép không?” trước khi gửi).

Đoạn code dưới cấu hình cookie an toàn và bật kiểm tra anti-forgery cho mọi request thay đổi dữ liệu (POST/PUT/PATCH/DELETE):

builder.Services.AddAntiforgery(o => o.HeaderName = "X-XSRF-TOKEN");

builder.Services.AddAuthentication().AddCookie(o =>
{
    o.Cookie.Name = "__Host-app";                        // __Host-: Secure, Path=/, không Domain
    o.Cookie.HttpOnly = true;
    o.Cookie.SecurePolicy = CookieSecurePolicy.Always;
    o.Cookie.SameSite = SameSiteMode.Lax;
});

var app = builder.Build();
app.UseAuthentication();
app.UseAntiforgery();   // .NET 8+: tự kiểm tra endpoint nhận form

// Với JSON API, gọi kiểm tra tường minh cho các method thay đổi trạng thái:
app.Use(async (ctx, next) =>
{
    if (HttpMethods.IsPost(ctx.Request.Method) || HttpMethods.IsPut(ctx.Request.Method)
        || HttpMethods.IsDelete(ctx.Request.Method) || HttpMethods.IsPatch(ctx.Request.Method))
    {
        var af = ctx.RequestServices.GetRequiredService<IAntiforgery>();
        await af.ValidateRequestAsync(ctx);   // ném AntiforgeryValidationException nếu sai
    }
    await next();
});
ℹ️ API chỉ dùng Bearer token có bị CSRF không? Không theo cách cổ điển: browser không tự gắn header Authorization; JavaScript của bạn phải gắn. CSRF là vấn đề của credential tự động gửi (cookie, Basic auth đã lưu, Windows Integrated Auth). Đổi lại, token mà JS đọc được lại nhạy cảm với XSS — xem token storage.

⚠️ Hiểu lầm hay gặp

Hiểu lầmĐã đặt SameSite=Lax thì không cần biện pháp chống CSRF nào khác.Thực tếSameSite không chặn subdomain bị chiếm (cùng site); Lax vẫn gửi cookie khi bấm link GET — nên GET thay đổi trạng thái vẫn bị lợi dụng; cookie SameSite=None cho SSO/embed thì không được bảo vệ. Kết hợp anti-CSRF token hoặc kiểm tra Origin.

C.2. XSS — Cross-Site Scripting

Nói đơn giản XSS (chèn script liên trang) giống việc kẻ gian trà trộn vào làm nhân viên bên trong công ty bạn: hắn đọc được mọi giấy tờ trên bàn (localStorage), dùng điện thoại nội bộ gọi đi như người nhà (gọi API). Khóa két (HttpOnly) giúp hắn không mang được chìa đi, nhưng khi còn ở trong tòa nhà, hắn vẫn sai khiến được nhiều thứ.

XSS xảy ra khi dữ liệu không tin cậy được chèn vào trang mà không encode, khiến script của kẻ tấn công chạy trong origin của app, với toàn bộ quyền của app: đọc DOM, đọc localStorage, gọi API.

sequenceDiagram
  participant H as Kẻ tấn công
  participant App as SPA (app.example)
  participant V as Browser nạn nhân
  participant X as attacker.example
  H->>App: Gửi bình luận chứa thẻ img onerror=script
  V->>App: Mở trang có bình luận
  App-->>V: HTML render bình luận KHÔNG encode
  Note over V: Script chạy trong origin app.example
  V->>V: Đọc token trong localStorage

Token trong localStorage bị lấy đi và dùng lâu dài (đặc biệt nguy hiểm nếu là refresh token).

Sơ đồ trên là stored XSS. Script độc có thể lọt vào trang theo ba đường khác nhau:

Ví dụ (Kaopiz HR): An đặt “Ghi chú nghỉ phép” là <img src=x onerror=...>; khi Bình mở trang duyệt, script chạy trong trình duyệt Bình → stored. Trang tìm kiếm /search?q=... in thẳng q ra HTML → reflected. Trang hr-web đọc location.hash rồi gán vào innerHTML để hiện lời chào → DOM-based.

Stored: nằm chờ trong DB. Reflected: dội lại từ URL qua server. DOM: JS phía client tự gây ra. Cả ba cùng một hậu quả — script chạy trong origin của bạn.
✅ Ngăn XSS từ gốc
  • Output encoding theo ngữ cảnh (Razor, React mặc định encode).
  • Tránh innerHTML, dangerouslySetInnerHTML, @Html.Raw với dữ liệu người dùng; nếu bắt buộc → sanitize bằng thư viện chuẩn.
  • Content-Security-Policy chặn inline script và domain lạ.
  • Kiểm soát thư viện bên thứ ba (supply chain, Subresource Integrity).
❌ Sai lầm thường gặp
  • Nghĩ “dùng cookie HttpOnly là hết lo XSS” — script vẫn gọi API từ chính browser nạn nhân.
  • Lưu refresh token dài hạn trong localStorage.
  • Tự viết regex để lọc thẻ <script>.

Quan hệXSS phá được mọi chống CSRF (script đọc được anti-CSRF token). Chống CSRF không giúp gì với XSS.

Ví dụ: Với CSRF, Bình đang đăng nhập hr-web rồi mở evil.example; trang đó gửi một form “duyệt nghỉ phép” sang hr-web, nhưng không đọc được kết quả trả về. Với XSS, script nằm ngay trong trang hr-web: nó tự đọc anti-CSRF token trên trang, gọi API duyệt, rồi đọc luôn bảng lương gửi ra ngoài.

CSRF: kẻ gian ở ngoài “mượn tay” trình duyệt. XSS: kẻ gian đã ở trong nhà. Chặn XSS trước, vì XSS làm vô hiệu chống CSRF.

C.3. Session fixation

Nói đơn giản Kẻ gian đưa sẵn cho bạn một tấm thẻ phòng khách sạn mà hắn giữ bản sao, rồi dụ bạn ra lễ tân “kích hoạt” thẻ đó. Nếu lễ tân kích hoạt luôn tấm cũ thay vì phát thẻ mới, hắn cũng mở được phòng bạn.

Kẻ tấn công khiến nạn nhân dùng một session ID do kẻ tấn công biết trước. Nếu sau khi nạn nhân đăng nhập, server vẫn giữ nguyên ID đó và gắn danh tính vào → kẻ tấn công dùng cùng ID là vào được tài khoản.

sequenceDiagram
  participant H as Kẻ tấn công
  participant V as Nạn nhân
  participant S as Web app
  H->>S: Mở trang, nhận SESSIONID=X (chưa đăng nhập)
  H->>V: Gửi link chứa SESSIONID=X
  Note over H,V: Hoặc cài cookie qua subdomain bị chiếm
  V->>S: Đăng nhập với SESSIONID=X
  alt App lỗi: giữ nguyên ID
    S-->>V: OK, session X giờ là của nạn nhân
    H->>S: Dùng SESSIONID=X → vào tài khoản ❌
  else App đúng: cấp ID mới sau login
    S-->>V: Set-Cookie SESSIONID=Y (X bị hủy)
    H->>S: Request với SESSIONID=X → chưa đăng nhập ✅
  end

Phòng vệ: luôn cấp session ID mới sau login và khi thay đổi đặc quyền (vd vào chế độ admin), không chấp nhận session ID qua URL, dùng tiền tố cookie __Host- để subdomain không ghi đè cookie. Với ASP.NET Core cookie authentication, SignInAsync phát hành cookie xác thực mới; nhưng nếu bạn dùng thêm ISession để lưu dữ liệu nhạy cảm, hãy tự xóa/đổi session sau đăng nhập (xem session management).

Phân biệt dễ nhầm: Session fixation vs Session hijacking
Tiêu chíSession fixationSession hijacking
Kẻ gian có session ID từ khi nàoTrước khi nạn nhân đăng nhập — chính hắn tạo ra và “cài” cho nạn nhânSau khi nạn nhân đăng nhập — lấy trộm ID đang dùng
Cách lấyLink chứa session ID, cookie ghi đè từ subdomain bị chiếmXSS đọc cookie (nếu thiếu HttpOnly), nghe lén khi không có TLS, malware, AiTM proxy, log
Lỗi của appKhông đổi session ID sau loginCookie thiếu Secure/HttpOnly, có XSS, session sống quá lâu
Chặn chínhCấp session ID mới sau login và khi tăng đặc quyềnHttpOnly + Secure + TLS, chống XSS, timeout, ràng buộc session với thiết bị

Ví dụ: Kẻ gian gửi cho An link hr.kaopiz.com/login?sid=X, An đăng nhập và app giữ nguyên X → fixation. An đăng nhập bình thường, nhận sid=Y, rồi một script XSS đọc được Y do cookie thiếu HttpOnly → hijacking. Cả hai kết thúc giống nhau: kẻ gian dùng session của An.

Fixation: “đưa chìa cho nạn nhân rồi chờ”. Hijacking: “giật chìa của nạn nhân”.

⚠️ Hiểu lầm hay gặp

Hiểu lầmSession fixation chỉ xảy ra khi app nhận session ID qua URL.Thực tếSubdomain bị chiếm có thể ghi cookie cho cả domain cha (Domain=kaopiz.com) để cài sẵn session ID. Vì vậy dùng tiền tố __Host- và luôn cấp ID mới sau login.
Hiểu lầmSession ID đủ dài và ngẫu nhiên thì không bị fixation.Thực tếKẻ gian không cần đoán ID — chính hắn tạo ra nó. Độ dài chỉ chống dò ID; chỉ việc đổi ID sau login mới chặn được fixation.
✅ Tự kiểm tra nhanh
  • API chỉ nhận Authorization: Bearer (không dùng cookie) có cần anti-CSRF token không? Vì sao?
  • Cookie đã HttpOnly. Kẻ tấn công XSS còn làm được gì?
  • Sau khi user đăng nhập, app nên làm gì với session ID cũ?
