Bài 7.1 — Quy trình thiết kế, Web, SPA & BFF

Trước khi chọn giao thức, hãy trả lời 10 câu hỏi thiết kế. Sau đó xem ba kiến trúc web phổ biến — server-side web, SPA và SPA + BFF — khác nhau ở đâu: token nằm ở đâu và ai giữ bí mật.

⏱ ~25 phút 📘 Module 07 · Architecture & Practical Cases

A. Quy trình thiết kế: 10 câu hỏi Must

Nói đơn giản Trước khi mua khóa, hỏi: ai cần vào (nhân viên, khách, xe giao hàng)? Vào bằng cửa nào? Cửa đó bảo vệ cái gì? Có cần dùng chung thẻ với tòa nhà bên cạnh không? Mất thẻ thì sao? Trả lời đủ các câu đó, việc chọn khóa gần như tự hiện ra.
📖 Thuật ngữ trong bài
Subject
“Ai” cần được xác thực: một người, một service, một thiết bị.
Workload identity
Danh tính do nền tảng (cloud, Kubernetes) cấp cho một service đang chạy, không cần secret do người quản lý.
Public / confidential client
App không giữ được bí mật (chạy trên máy người dùng) / app giữ được bí mật (chạy trên server).
Delegated access
App gọi API thay mặt người dùng, chỉ trong phạm vi (scope) người dùng cho phép.
Server-side web app
Web mà HTML được tạo ở server (ASP.NET MVC, Razor Pages…); browser chỉ hiển thị.
SPA
Single-Page Application: web viết bằng JavaScript (React, Angular…) chạy hoàn toàn trong browser, tự gọi API.
BFF
Backend for Frontend: backend nhỏ đi kèm SPA, giữ token thay SPA; browser chỉ cầm cookie.
CORS
Luật của browser cho phép trang ở domain A đọc response từ domain B. Không phải cơ chế bảo mật của server.

Bảng dưới là 10 câu hỏi theo thứ tự nên hỏi. Cột cuối là câu trả lời mẫu cho ví dụ WPF + Order API — bạn thử tự trả lời cho hệ thống của team mình.

B. Kiến trúc theo loại ứng dụng

Cả ba kiến trúc web dưới đây đều dùng Authorization Code flow để đăng nhập. Điều làm chúng khác nhau là: sau khi đăng nhập, token nằm ở đâu và ai giữ client secret. Đọc bảng này trước, rồi đi vào từng kiến trúc.

Ví dụ: kẻ tấn công chèn được script độc (XSS) vào trang HR. Với SPA thuần, script đọc được access token trong memory và gửi về máy kẻ tấn công — dùng tiếp được từ bất kỳ đâu đến khi token hết hạn. Với server-side web hoặc BFF, script không đọc được token (không có trong browser) và cookie HttpOnly cũng không đọc được bằng JavaScript; nó chỉ có thể gửi request từ chính tab đó khi nạn nhân còn mở trang.

Token ở server + browser cầm cookie = server-side web hoặc BFF. Token ở browser = SPA thuần.

B.1. Server-side Web Application Should

Nói đơn giản Web server giống quầy lễ tân có két sắt: lễ tân (backend) tự đi đổi “phiếu” (authorization code) lấy “chìa khóa” (token) ở IdP và cất trong két. Khách (browser) chỉ nhận một vé gửi đồ (session cookie) — không bao giờ cầm chìa thật.
  • Dùng OIDC Authorization Code Flow; backend đổi code lấy token, giữ client secret ở server (confidential client). Vẫn nên bật PKCE — OAuth 2.1 và RFC 9700 khuyến nghị PKCE cho cả confidential client.
  • Backend tạo application session (phiên đăng nhập riêng của app, tách khỏi phiên ở IdP) và bảo vệ bằng cookie (HttpOnly, Secure, SameSite).
  • Cần CSRF protection (chống trang lạ lợi dụng cookie của bạn để gửi request), cookie settings và session lifecycle (idle/absolute timeout, logout) — xem M06 — CSRF, M02 — session management.
  • Nếu gọi API downstream, dùng access token riêng cho API đó (đúng aud), không chuyển tiếp ID token.

🧪 Ví dụ: hr-web của Kaopiz HR là server-side web
  1. An mở https://hr.kaopiz.local/payroll. hr-web thấy chưa có cookie → chuyển An tới Keycloak (https://sso.kaopiz.local/realms/kaopiz).
  2. An đăng nhập. Keycloak trả code về /signin-oidc của hr-web.
  3. hr-web (backend) đổi code + client secret lấy token, cất token ở server, gửi cho browser một cookie phiên.
  4. Khi An xem bảng lương, hr-web tự gắn access token gọi hr-api rồi trả HTML. Browser của An không bao giờ thấy access token.

Đoạn code dưới cấu hình đúng luồng trên trong ASP.NET Core: cookie giữ phiên của app, OpenIdConnect lo việc chuyển hướng tới IdP và đổi code. Chú ý các dòng có comment.

using Microsoft.AspNetCore.Authentication.Cookies;
using Microsoft.AspNetCore.Authentication.OpenIdConnect;
using Microsoft.IdentityModel.Protocols.OpenIdConnect;

builder.Services
    .AddAuthentication(o =>
    {
        o.DefaultScheme = CookieAuthenticationDefaults.AuthenticationScheme;          // đọc session
        o.DefaultChallengeScheme = OpenIdConnectDefaults.AuthenticationScheme;        // chưa login → IdP
    })
    .AddCookie(o =>
    {
        o.Cookie.Name = "__Host-orders";
        o.Cookie.HttpOnly = true;
        o.Cookie.SecurePolicy = CookieSecurePolicy.Always;
        o.Cookie.SameSite = SameSiteMode.Lax;
        o.ExpireTimeSpan = TimeSpan.FromHours(8);
        o.SlidingExpiration = true;
    })
    .AddOpenIdConnect(o =>
    {
        o.Authority = "https://idp.example.com/realms/demo";
        o.ClientId = "orders-web";
        o.ClientSecret = builder.Configuration["Oidc:ClientSecret"];   // từ secret store, KHÔNG commit
        o.ResponseType = OpenIdConnectResponseType.Code;               // Authorization Code flow
        o.UsePkce = true;
        o.SaveTokens = true;              // lưu token vào authentication ticket (cookie đã mã hóa)
        o.MapInboundClaims = false;
        o.GetClaimsFromUserInfoEndpoint = true;
        o.Scope.Add("orders.read");
        o.TokenValidationParameters.NameClaimType = "preferred_username";
    });

builder.Services.AddAuthorization(o =>
    o.FallbackPolicy = new Microsoft.AspNetCore.Authorization.AuthorizationPolicyBuilder()
        .RequireAuthenticatedUser().Build());
ℹ️ Lưu ý về SaveTokens SaveTokens = true lưu token trong authentication ticket — mặc định nằm trong cookie (được Data Protection mã hóa). Cookie sẽ to ra; khi có nhiều token hoặc nhiều claim, cân nhắc lưu ticket phía server (ITicketStore) hoặc token cache phân tán. Nếu chạy nhiều instance, cấu hình Data Protection key ring dùng chung.

Checklist server-side web

  • Code flow (+ PKCE), client secret/khóa trong secret store.
  • Cookie __Host-, HttpOnly, Secure, SameSite; idle + absolute timeout.
  • Antiforgery cho form/POST; GET không đổi trạng thái.
  • Callback path (/signin-oidc) đăng ký đúng redirect URI.
  • Logout: xóa cookie app + RP-initiated logout ở IdP (M03).
  • Data Protection key ring dùng chung khi scale-out.

B.2. SPA (Single-Page Application) Must

Nói đơn giản SPA là JavaScript chạy hoàn toàn trong browser — giống một quầy hàng đặt ngoài vỉa hè: ai đi qua cũng nhìn thấy mọi thứ trên quầy. Không thể giấu “mật khẩu của ứng dụng” (client secret) ở đó. Vì vậy SPA hoặc dùng PKCE và giữ token thật cẩn thận, hoặc gửi chìa khóa vào trong cửa hàng (BFF) và chỉ cầm vé.
  • Authorization Code + PKCE (M03). Không có client secret nào giữ bí mật được.
  • Cân nhắc BFF để token không vào browser, browser chỉ có cookie phiên.
  • Nếu SPA gọi API trực tiếp: phải thiết kế cẩn thận token storage (cất token ở đâu trong browser) (M06), CORS, chống XSS, và refresh token policy (rotation, lifetime ngắn).
  • CORS không phải cơ chế authentication hay authorization (xem bên dưới).

RFC 10017 — OAuth 2.0 for Browser-Based Applications (BCP 212, phát hành 8/2026, trước đây là draft-ietf-oauth-browser-based-apps) mô tả ba pattern, xếp theo mức an toàn giảm dần. Điểm cần rút ra: càng ít token nằm trong browser càng an toàn.

B.3. BFF — Backend for Frontend

Nói đơn giản BFF giống quầy gửi đồ của siêu thị: chìa khóa thật (token) nằm trong tủ của quầy, bạn (browser) chỉ cầm phiếu gửi đồ (session cookie). Mất phiếu ở ngoài thì kẻ gian khó dùng lâu dài — nhưng nếu kẻ gian đứng ngay cạnh bạn (XSS), hắn vẫn có thể bắt bạn đưa phiếu ra quầy lấy đồ hộ.

BFF là một backend nhỏ, đi cùng SPA (thường cùng domain), đóng vai confidential client. Nó làm bốn việc:

  1. Thực hiện OIDC code flow thay cho SPA.
  2. Giữ access/refresh token ở server.
  3. Cấp cho browser một session cookie.
  4. Proxy (chuyển tiếp hộ) các lời gọi API: nhận request từ SPA kèm cookie, gắn access token vào rồi gửi tới API.

👍 Được gì

XSS không đánh cắp được token để dùng lâu dài; refresh token an toàn ở server; có thể dùng client secret/khóa; logout và revoke tập trung.

Dữ liệu nhạy cảm → để token ở BFF. Thấy Bearer đi ra từ browser = SPA thuần.

Cách dựng BFF trong .NET: tự dựng (ASP.NET Core + AddOpenIdConnect + reverse proxy như YARP) hoặc dùng thư viện chuyên dụng (vd Duende BFF — kiểm tra điều khoản license).

Yêu cầu cookie theo RFC 10017:

  • Phải có HttpOnly + Secure.
  • Nên dùng tiền tố __Host-Http- (báo hiệu cookie chỉ được đặt qua HTTP và không chia sẻ với subdomain); trình duyệt/framework chưa hỗ trợ thì tối thiểu dùng __Host-.
  • Nên đặt SameSite=Strict.
  • BFF phải có biện pháp chống CSRF, vd yêu cầu custom header để buộc browser gửi CORS preflight (request OPTIONS hỏi trước xem có được phép không).

Còn XSS: script độc không lấy được token, nhưng vẫn gọi được /bff/api/... từ chính tab đó khi nạn nhân đang mở trang. BFF giảm thiệt hại, không thay CSP và việc chống XSS.

CORS không phải authentication/authorization

Nói đơn giản CORS (Cross-Origin Resource Sharing) là luật của trình duyệt: “trang web A có được đọc câu trả lời từ server B không?”. Nó giống người gác cổng của browser, không phải bảo vệ của server. curl, Postman, một server khác… chẳng hề quan tâm CORS.
  • CORS nới lỏng Same-Origin Policy (luật mặc định: trang ở origin này không đọc được response của origin khác) cho browser; nó không xác minh người gọi là ai.
  • Request “đơn giản” (form POST) vẫn được gửi tới server kể cả khi CORS chặn đọc response → CORS không chống được CSRF một mình.
  • Access-Control-Allow-Origin: * kết hợp credentials là cấu hình sai (browser không cho phép); phản chiếu mọi Origin kèm Allow-Credentials: true là lỗ hổng.
  • API vẫn phải xác minh token và phân quyền cho mọi request, bất kể CORS.
🧪 Ví dụ: CORS chặn browser, không chặn curl hr-api chỉ cho phép origin https://hr.kaopiz.local. Một trang lạ gọi fetch("https://hr-api.kaopiz.local/payroll") → browser chặn đọc response. Nhưng ai đó chạy curl https://hr-api.kaopiz.local/payroll từ terminal thì request đi thẳng tới server, không có CORS nào can thiệp. Thứ duy nhất chặn được curl là hr-api kiểm tra access token và trả 401.

⚠️ Hiểu lầm hay gặp

Hiểu lầmBật CORS đúng là API đã được bảo vệ.Thực tếCORS là luật của browser về việc đọc response; nó không xác thực, không phân quyền. curl, Postman hay một server khác gọi thẳng API mà không hề bị CORS cản.
Hiểu lầmConsole báo “blocked by CORS policy” nghĩa là server chưa nhận request.Thực tếVới request “đơn giản” (không cần preflight, vd form POST), request đã tới server và có thể đã được xử lý; browser chỉ không cho JavaScript đọc response. Chỉ request cần preflight mới bị chặn trước khi gửi. Vì vậy endpoint đổi dữ liệu không được trông chờ CORS để chống CSRF.

Checklist SPA / BFF

  • Code + PKCE (S256); không client secret trong bundle JS.
  • Dữ liệu nhạy cảm → BFF; nếu không, access token trong memory, refresh token rotation + lifetime ngắn.
  • Không lưu refresh token trong localStorage.
  • CSP chặt; không innerHTML với dữ liệu người dùng.
  • CORS allowlist origin cụ thể; không coi CORS là bảo mật.
  • BFF: cookie __Host- HttpOnly Secure SameSite + chống CSRF (custom header/antiforgery).

  • Bật CORS chỉ cho một origin có ngăn được kẻ tấn công gọi API bằng curl không? Vậy cái gì ngăn?
