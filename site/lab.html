Lab — Hands-on OAuth/OIDC với ASP.NET Core

Biến các flow đã vẽ ở Module 03 thành hệ thống chạy được trên máy bạn: Keycloak làm IdP, một Web API ASP.NET Core xác minh JWT, một console app đăng nhập bằng Authorization Code + PKCE, và một “worker” dùng Client Credentials. Bạn sẽ đọc request, response và token thật — rồi cố tình làm hỏng để hiểu từng lỗi 401/403.

⏱ Full 2 giờ · Core 1.5 giờ (Lab 1–3) 📥 Input: hoàn thành M01–M03 🧰 .NET 10 LTS · Docker · Keycloak 26.x ➡️ Tiếp theo: Module 04
Sau bài này bạn sẽ
  • Tự dựng một IdP (Keycloak) với realm, user, client public/confidential, client scope và audience — biết vì sao từng cấu hình tồn tại.
  • Viết một ASP.NET Core Web API xác minh access token (JWT) và tái hiện được ít nhất 6 lỗi 401/403, đọc được header WWW-Authenticate và log IDX10xxx.
  • Viết một console app .NET đăng nhập bằng Authorization Code + PKCE qua system browser và loopback redirect, tự bắt được code_challenge, state, nonce.
  • Phân biệt ID token và access token bằng dữ liệu thật (aud, azp, nonce, scope).
  • Dùng Client Credentials, quan sát refresh token rotation, gọi introspection và revocation endpoint.
  • (Nice) Đọc một SAML Response thật bằng SAML-tracer.

Thuật ngữ dùng xuyên suốt (định nghĩa đầy đủ ở M03):

  • IdP (Identity Provider — nhà cung cấp danh tính): hệ thống xác thực người dùng và phát hành token. Ở đây là Keycloak.
  • Realm (Keycloak): một “không gian” độc lập chứa user, client, cấu hình. Mỗi realm có issuer riêng, ví dụ http://localhost:8080/realms/demo.
  • Client: ứng dụng xin token. Public client không thể giữ bí mật (app desktop/mobile/SPA). Confidential client chạy trên server, giữ được client_secret.
  • Access token: “thẻ” để gọi API. ID token: “biên nhận đăng nhập” gửi cho client, cho biết ai vừa đăng nhập (so sánh).
  • Scope: phạm vi quyền client xin (ví dụ orders.read). Audience (aud): token này dành cho ai (API nào được phép nhận).
  • JWKS (JSON Web Key Set): danh sách khóa công khai của IdP để kiểm tra chữ ký JWT. kid (key ID): mã khóa ghi trong header JWT để biết dùng khóa nào.

Lab 1 — Cấu hình IdP (Keycloak)

Must⏱ 20 phút

(a) Mục tiêu

Có một IdP chạy local với đủ “nhân vật” cho các lab sau: realm demo, user alice, client public demo-client (Auth Code + PKCE S256), API demo-api được dùng làm audience, client scope orders.read/orders.write, và client confidential worker (Client Credentials). Biết đọc discovery document và JWKS.

(b) Yêu cầu / đề bài

  1. Keycloak 26.x chạy ở http://localhost:8080, đăng nhập được admin console.
  2. Realm demo có user alice đăng nhập được (mật khẩu không bị bắt đổi).
  3. Client demo-client: public, chỉ bật Standard flow, PKCE method S256, redirect URI đúng http://127.0.0.1:7890/.
  4. Client scope orders.read và orders.write, mỗi scope có Audience mapper thêm demo-api vào aud của access token.
  5. Client worker: confidential, bật Service accounts roles, được gán 2 scope trên.
  6. Nộp: một bảng ghi lại issuer, authorization_endpoint, token_endpoint, jwks_uri, introspection_endpoint, revocation_endpoint và kid của khóa ký RS256; ảnh chụp tab “Evaluate” cho thấy access token chứa "aud": "demo-api" khi xin scope orders.read.

(c) Hướng dẫn từng bước

ℹ️ Tên menu Keycloak Hướng dẫn viết theo admin console Keycloak 26.x (tài liệu Server Administration Guide). Giao diện thay đổi nhẹ giữa các bản minor (ví dụ vị trí chọn realm, vị trí PKCE). Nếu không thấy đúng tên, tìm trường có ý nghĩa tương đương.
  1. Chạy Keycloak bằng Docker. 
    docker run --name kc -p 8080:8080 -e KC_BOOTSTRAP_ADMIN_USERNAME=admin -e KC_BOOTSTRAP_ADMIN_PASSWORD=admin quay.io/keycloak/keycloak:26.8.2 start-dev
    • Vì sao: start-dev chạy chế độ phát triển (HTTP, DB nhúng, không cần cấu hình hostname). Biến KC_BOOTSTRAP_ADMIN_* tạo admin tạm thời lần đầu. Phiên bản Keycloak cũ (trước 26) dùng KEYCLOAK_ADMIN/KEYCLOAK_ADMIN_PASSWORD. Ghim tag phiên bản (26.8.2, bản mới tại thời điểm viết) để lab lặp lại được; dùng tag 26.8 hoặc bản 26.x mới hơn cũng được.
    • Kiểm tra: log có dòng tương tự Running the server in development mode. DO NOT use this configuration in production.; mở http://localhost:8080 thấy trang đăng nhập admin.
    • Lưu ý: dữ liệu nằm trong container. docker stop kc / docker start kc giữ nguyên cấu hình; docker rm kc là mất hết realm (lúc đó API sẽ gặp lỗi kid không tìm thấy vì khóa ký đã đổi).
  2. Đăng nhập admin console bằng admin/admin.
    • Kiểm tra: có thể thấy banner cảnh báo đây là temporary admin — bình thường với lab.
  3. Tạo realm demo. Mở danh sách realm (dropdown góc trên-trái, hoặc mục Manage realms ở menu trái tùy phiên bản) → Create realm → Realm name: demo → Create.
    • Vì sao: không làm việc trong realm master (realm quản trị). Realm demo sẽ có issuer riêng.
    • Kiểm tra: mở http://localhost:8080/realms/demo/.well-known/openid-configuration — trả JSON.
  4. Tạo user test alice. Menu Users → Create new user (hoặc Add user) → Username alice, Email alice@example.com, First name Alice, Last name Nguyen, bật Email verified → Create. Sang tab Credentials → Set password → nhập mật khẩu (ví dụ Alice@123) → tắt Temporary → Save.
    • Vì sao: nếu để Temporary = On, lần đăng nhập đầu Keycloak bắt đổi mật khẩu — làm rối luồng lab. Điền đủ email/họ tên để Keycloak không hiện màn hình “Update account information” (user profile mặc định yêu cầu các trường này).
    • Kiểm tra: mở http://localhost:8080/realms/demo/account (Account Console) bằng cửa sổ ẩn danh, đăng nhập alice thành công ngay.
  5. Tạo client demo-api (đại diện cho Web API). Clients → Create client → Client type OpenID Connect, Client ID demo-api → Next → Capability config: Client authentication Off, bỏ chọn Standard flow và Direct access grants → Next → Save.
    • Vì sao: API không đăng nhập ai cả; ta chỉ cần một client tên demo-api để Audience mapper tham chiếu. Tài liệu Keycloak ghi rõ mapper không thêm audience nếu client được tham chiếu bị disable hoặc không tồn tại.
    • Kiểm tra: demo-api xuất hiện trong danh sách Clients. (Nếu UI không cho lưu khi bỏ hết flow, để Standard flow bật nhưng không khai báo redirect URI — không ai đăng nhập qua client này được.)
  6. Tạo client scope orders.read có Audience mapper.
    1. Menu Client scopes → Create client scope → Name orders.read, Type None, Protocol OpenID Connect, Include in token scope On → Save.
    2. Tab Mappers → Configure a new mapper (hoặc Add mapper → By configuration) → chọn Audience → Name aud-demo-api, Included Client Audience = demo-api, Add to access token On, Add to ID token Off → Save.
    3. Lặp lại cho orders.write (cùng mapper aud-demo-api).
    • Vì sao Audience mapper: mặc định, access token của Keycloak thường có aud = account (client nội bộ của Keycloak) hoặc không chứa API của bạn. API của ta kiểm tra aud == demo-api → phải dạy Keycloak thêm giá trị này. Gắn mapper vào scope nghĩa là: “client nào xin orders.read thì token dành cho demo-api”.
    • Vì sao Type None: ta sẽ gán scope cho từng client ở bước sau, không gán tự động cho mọi client trong realm.
    • Vì sao Include in token scope: để chuỗi orders.read xuất hiện trong claim scope của access token — policy của API dựa vào đó.
    • Vì sao có thêm orders.write: để Lab 2 tạo được token đúng audience nhưng thiếu scope orders.read (kịch bản 403).
  7. Tạo client public demo-client. Clients → Create client:
    1. General settings: Client type OpenID Connect, Client ID demo-client → Next.
    2. Capability config: Client authentication Off (= public client), Authorization Off, Authentication flow: chỉ chọn Standard flow; bỏ Direct access grants, Implicit flow. PKCE Method = S256 → Next.
    3. Login settings: Valid redirect URIs = http://127.0.0.1:7890/ (có dấu / cuối), Valid post logout redirect URIs = http://127.0.0.1:7890/, Web origins để trống → Save.
    4. Tab Client scopes của demo-client → Add client scope → chọn orders.read, orders.write → Add ▾ → Optional.
    ⚠️ Vị trí cài đặt PKCE thay đổi theo phiên bản Tài liệu Keycloak hiện hành đặt PKCE Method (giá trị: trống / S256 / plain) trong Settings → Capability config. Release notes Keycloak 26.3.0 ghi nhận việc chuyển cài đặt này từ tab Advanced sang tab Settings. Nếu bạn dùng bản cũ hơn: tab Advanced → mục Advanced settings → Proof Key for Code Exchange Code Challenge Method = S256. Để trống nghĩa là PKCE chỉ được áp dụng khi client tự gửi tham số — không bắt buộc.
    • Vì sao public: console/WPF app được cài trên máy người dùng — ai cũng có thể dịch ngược lấy secret. PKCE thay thế vai trò “chứng minh tôi là người đã bắt đầu flow” (M03 — PKCE).
    • Vì sao tắt Direct access grants: đó là ROPC (client cầm mật khẩu user) — bị loại khỏi OAuth 2.1 và Security BCP (M03).
    • Vì sao 127.0.0.1: RFC 8252 (OAuth cho native app) khuyến nghị loopback IP literal thay vì localhost. Keycloak so khớp redirect URI chính xác, phân biệt hoa thường → http://127.0.0.1:7890 (thiếu /) hay http://localhost:7890/ đều bị từ chối.
    • Kiểm tra: tab Client scopes → Evaluate (tab con) → chọn user alice, ô Scope parameter chọn thêm orders.read → xem Generated access token: có "aud" chứa demo-api và "scope" chứa orders.read. Bỏ orders.read → demo-api biến mất khỏi aud.
  8. Default hay Optional? — hiểu trước khi chọn.
    Nói đơn giản Default giống món “đi kèm combo”: gọi combo là luôn có, không cần nói. Optional giống món “gọi thêm”: chỉ có khi bạn nói rõ trong order (tham số scope).
    Default client scopeOptional client scope
    Khi nào áp dụngLuôn luôn, bất kể tham số scope client gửi.Chỉ khi client xin nó trong tham số scope.
    Hệ quả với labMọi token của client đều có aud=demo-api + orders.read.Chỉ token xin scope=... orders.read mới có.
    Ưu điểmĐơn giản, client không cần biết tên scope.Đúng tinh thần least privilege: xin quyền nào nhận quyền đó; tái hiện được lỗi “thiếu scope”.
    Dùng trong lab—✅ Chọn Optional cho cả demo-client và worker.
  9. Tạo client confidential worker. Clients → Create client → Client ID worker → Next → Client authentication On, bỏ Standard flow và Direct access grants, chọn Service accounts roles → Next → Save. Tab Credentials → copy Client Secret. Tab Client scopes → Add client scope → orders.read, orders.write → Optional.
    • Vì sao: “Service accounts roles” chính là bật Client Credentials grant cho client này (theo tài liệu Keycloak). Client confidential vì worker chạy trên server, giữ được secret.
    • Kiểm tra: 
      export KC=http://localhost:8080/realms/demo
export WORKER_SECRET='dán-secret-vào-đây'
curl -s -X POST "$KC/protocol/openid-connect/token" \
  -d grant_type=client_credentials -d client_id=worker \
  -d client_secret="$WORKER_SECRET" -d scope=orders.read | jq .
      $KC = "http://localhost:8080/realms/demo"
$env:WORKER_SECRET = "dán-secret-vào-đây"
$t = Invoke-RestMethod -Method Post -Uri "$KC/protocol/openid-connect/token" -Body @{
  grant_type = "client_credentials"; client_id = "worker"
  client_secret = $env:WORKER_SECRET; scope = "orders.read" }
$t | Format-List
      Phải nhận được JSON có access_token, token_type: "Bearer", expires_in: 300 (mặc định 5 phút).
  10. Đọc discovery document và JWKS. 
    curl -s $KC/.well-known/openid-configuration | jq '{issuer, authorization_endpoint, token_endpoint, jwks_uri, userinfo_endpoint, end_session_endpoint, introspection_endpoint, revocation_endpoint, pushed_authorization_request_endpoint, code_challenge_methods_supported}'
curl -s $KC/protocol/openid-connect/certs | jq '.keys[] | {kid, kty, alg, use}'
    • Vì sao: đây chính là thứ AddJwtBearer làm tự động khi bạn đặt Authority: tải discovery → lấy issuer và jwks_uri → tải khóa công khai (M03 — Discovery & JWKS).
    • Kiểm tra: lấy header của access token ở bước 9 (dùng bộ decode) → kid trong header phải trùng với kid của một khóa "use": "sig", "alg": "RS256" trong JWKS.
  11. (Tùy chọn, khuyến nghị) Lưu cấu hình: Realm settings → menu Action (góc trên-phải) → Partial export (bật export clients) → lưu thành keycloak/realm-demo.json trong repo. Secret sẽ bị che trong file export.

(f) Câu hỏi tự kiểm tra

Vì sao demo-client là public còn worker là confidential?

demo-client chạy trên máy người dùng: mọi secret nhúng trong app đều lấy ra được, nên coi như không có secret và dùng PKCE. worker chạy trên server do ta kiểm soát, giữ được secret, nên xác thực client bằng client_secret.

Nếu gắn orders.read là Default cho demo-client, điều gì thay đổi?

Mọi access token của demo-client sẽ luôn có aud=demo-api và scope chứa orders.read, kể cả khi client không xin. Tiện nhưng vi phạm least privilege, và bạn không tái hiện được kịch bản “thiếu scope”.

kid dùng để làm gì?

IdP có thể có nhiều khóa (đang dùng, sắp xoay vòng…). kid trong header JWT cho API biết dùng khóa nào trong JWKS để kiểm tra chữ ký. Khi gặp kid lạ, JwtBearer sẽ tải lại metadata/JWKS.

(f) Câu hỏi tự kiểm tra

Vì sao kịch bản 1 không có error="invalid_token" còn kịch bản 2 có?

Kịch bản 1 không có token nào để đánh giá — handler chỉ “challenge” yêu cầu xác thực. Kịch bản 2 có token nhưng token không qua được validation → handler đặt error="invalid_token" và mô tả lý do (vì IncludeErrorDetails = true).

Ở production có nên trả error_description chi tiết không?

Thông tin như “audience invalid” giúp client debug và thường không quá nhạy cảm, nhưng nhiều tổ chức chọn tắt (IncludeErrorDetails = false) để không lộ cấu hình. Dù chọn gì, log phía server phải đủ chi tiết; nhưng không bật ShowPII ở production.

Giới hạn của phép so sánh: verifier không bị “xé” thật — challenge là hash một chiều của nó.

(f) Câu hỏi tự kiểm tra

Vì sao code_verifier không bao giờ xuất hiện trên URL?

URL đi qua browser, lịch sử, log proxy, có thể bị app khác chặn redirect. Chỉ code_challenge (hash một chiều) đi qua front channel; verifier chỉ đi qua back channel (POST tới token endpoint). Kẻ trộm code không có verifier thì không đổi được token.

state và nonce chống lại điều gì, khác nhau ra sao?

state gắn callback với request đã gửi → chống CSRF/login injection ở redirect (client kiểm tra trước khi đổi code). nonce nằm trong ID token → chống replay ID token, gắn token với phiên đăng nhập của client (kiểm tra sau khi nhận token).

Vì sao không cần client_secret khi đổi code?

demo-client là public client; PKCE đóng vai “bằng chứng” rằng bên đổi code là bên đã khởi tạo flow.

Lab 4 — Client Credentials, refresh, introspection

Should⏱ 20 phút

(a) Mục tiêu

Quan sát token không có người dùng thật (Client Credentials), cơ chế refresh token rotation và phát hiện dùng lại, và hai endpoint quản lý vòng đời token: introspection (RFC 7662) và revocation (RFC 7009). Lý thuyết ở M02 — Token lifecycle và M02 — Introspection & Revocation.

Nói đơn giản Access token giống thẻ ra vào có hạn 5 phút. Refresh token giống giấy hẹn đổi thẻ mới ở quầy lễ tân. Với rotation, mỗi lần đổi, lễ tân thu giấy hẹn cũ và đưa giấy mới — ai cầm giấy cũ quay lại là bị phát hiện. Introspection là gọi điện hỏi lễ tân “thẻ này còn hiệu lực không?”. Revocation là báo lễ tân “hủy thẻ/giấy này”. Giới hạn: đầu đọc thẻ ở cửa (API JWT) không gọi điện hỏi lễ tân — thẻ đã hủy vẫn mở được cửa đến khi hết hạn, trừ khi API dùng introspection.

(a) Mục tiêu

Nhìn tận mắt một SAML AuthnRequest và SAML Response thật, chú giải các trường bảo mật quan trọng. Lý thuyết ở Module 04 (Response vs Assertion, kiểm tra bảo mật SAML).

Nói đơn giản SAML giống một lá thư giới thiệu có đóng dấu (XML ký số). App (SP) viết “phiếu yêu cầu” (AuthnRequest) gửi qua tay người dùng tới IdP; IdP gửi lại lá thư (Response) qua tay người dùng, trong đó có “giấy chứng nhận” (Assertion) ghi: ai (NameID), do ai cấp (Issuer), cho ai đọc (Audience), có hiệu lực tới khi nào (Conditions), trả lời phiếu nào (InResponseTo). Người dùng chỉ là “người đưa thư” — nên app phải kiểm tra con dấu và từng dòng.

(f) Câu hỏi tự kiểm tra

SAML Response và Assertion khác nhau thế nào trong XML vừa bắt?

<samlp:Response> là message bao ngoài (Destination, InResponseTo, Status). <saml:Assertion> nằm bên trong, chứa tuyên bố về subject (NameID, Conditions, AuthnStatement, Attributes). Chữ ký có thể ở Response, ở Assertion, hoặc cả hai.

Vì sao không tự viết code parse XML để kiểm tra chữ ký?

Rủi ro XML Signature Wrapping, XXE, canonicalization sai. Dùng thư viện SAML trưởng thành (M04).

Knowledge Check (tự luận)

Tự trả lời trước, sau đó mở đáp án gợi ý để so sánh.

Vì sao MapInboundClaims = false giúp tránh lỗi policy?

Mặc định handler đổi tên một số claim theo bảng ánh xạ cũ của Microsoft: sub → http://schemas.xmlsoap.org/ws/2005/05/identity/claims/nameidentifier, scp → http://schemas.microsoft.com/identity/claims/scope, email → ClaimTypes.Email… Policy viết theo tên trong token (RequireClaim("sub"), đọc scp) sẽ không tìm thấy claim → 403 dù token đúng. Tắt mapping để tên claim trong ClaimsPrincipal giống hệt trong JWT — điều bạn thấy khi decode là điều code nhận được.

API trả 401 hay 403 khi token hợp lệ nhưng thiếu scope?

403 Forbidden. Authentication đã thành công (biết caller là ai); thất bại ở authorization. Response 403 không mang error="invalid_token". (RFC 6750 có mã insufficient_scope cho trường hợp này; ASP.NET Core mặc định không tự thêm nó vào header — có thể tùy biến nếu muốn.)

API lấy public key để xác minh chữ ký ở đâu, khi nào làm mới?

Từ jwks_uri trong discovery document ({Authority}/.well-known/openid-configuration), ở đây là /realms/demo/protocol/openid-connect/certs. JwtBearer tải lần đầu khi cần, cache lại, làm mới định kỳ (mặc định của ConfigurationManager là theo chu kỳ tính bằng giờ) và làm mới ngay khi gặp token có kid không có trong cache (RefreshOnIssuerKeyNotFound, mặc định bật) — để hỗ trợ xoay vòng khóa.

Vì sao ID token bị API từ chối dù chữ ký hợp lệ?

Vì ID token dành cho client: aud = demo-client, không phải demo-api. Chữ ký chỉ chứng minh “Keycloak đã phát hành token này”, không chứng minh “token này dành cho tôi”. Ngoài ra ID token không mang scope ủy quyền. API phải kiểm tra aud và chỉ nhận access token.
