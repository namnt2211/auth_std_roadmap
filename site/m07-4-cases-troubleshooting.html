Bài 7.4 — Case studies & troubleshooting

Áp dụng kiến thức vào tình huống thật: với từng bài toán thì chọn giải pháp nào và vì sao. Sau đó học cách đọc lỗi — nhiều lỗi trông giống nhau (cùng là 401, cùng là “đăng nhập thất bại”) nhưng nguyên nhân và cách sửa khác hẳn.

Phân tích sâu 3 case

Case 1 — B2C social login: “email trùng thì gộp tài khoản” có ổn không?

Bối cảnh: shop online cho đăng nhập bằng Google, Microsoft và mật khẩu riêng.

  • Lưu bảng ExternalLogins(Issuer, Subject, UserId). Khóa định danh là iss + sub; email chỉ là thuộc tính.
  • Không tự gộp chỉ vì email trùng: một IdP có thể cho phép email chưa xác minh; kẻ tấn công tạo account ở IdP B với email của nạn nhân → chiếm tài khoản (account takeover qua account linking).
  • Gộp chỉ khi user đã đăng nhập bằng phương thức hiện có rồi chủ động “liên kết thêm”, hoặc email đã xác minh và IdP được tin cậy về email đó, kèm xác nhận.
  • Flow: OIDC code + PKCE từ backend (confidential) hoặc BFF; session cookie cho shop.
Case 2 — Đối tác gọi API: API key hay Client Credentials?
  • API key: đơn giản, phù hợp dữ liệu ít nhạy cảm, cần quota/metering. Nhược: thường dài hạn, không có scope chuẩn, không hết hạn tự động, dễ lộ qua log/repo. Bắt buộc: gửi qua header (không query string), hash khi lưu, có rotation và revoke, gắn với một đối tác.
  • Client Credentials: token ngắn hạn, có scope/aud, IdP quản lý vòng đời, có thể nâng cấp lên private_key_jwt/mTLS. Phù hợp khi dữ liệu nhạy cảm hoặc cần phân quyền theo scope.
  • Cả hai đều định danh ứng dụng, không định danh người dùng. Nếu đối tác truy cập dữ liệu thay mặt user của bạn → cần Authorization Code (delegated) thay vì Client Credentials.
Case 3 — Nhân viên nghỉ việc lúc 17:00, phải mất quyền ngay
  1. HR vô hiệu hóa ở nguồn (HRIS/AD) → IdP vô hiệu hóa user và thu hồi refresh token/phiên SSO.
  2. IdP gửi SCIM PATCH active=false tới các app hỗ trợ SCIM → app khóa account, xóa session.
  3. App/API không hỗ trợ SCIM: dựa vào access token ngắn hạn (5–15 phút) và refresh token đã bị thu hồi.
  4. Nếu có CAE/introspection: API từ chối token ngay khi nhận sự kiện.
  5. Thu hồi credential khác: thiết bị (mất thiết bị → wipe), API key cá nhân, SSH key, chứng thư, passkey đăng ký; rotate shared secret mà người đó biết.
  6. Kiểm tra audit log các hoạt động gần thời điểm nghỉ.

⚠️ Hiểu lầm hay gặp

Hiểu lầmĐăng nhập Google mang email trùng với account cũ thì tự gộp vào account đó là tiện và an toàn.Thực tếEmail chỉ là thuộc tính, có IdP còn cho phép email chưa xác minh. Kẻ tấn công tạo account ở IdP khác với email của nạn nhân là chiếm được tài khoản. Khóa định danh là iss + sub; chỉ gộp khi user đã đăng nhập bằng cách cũ rồi chủ động liên kết.
Hiểu lầmĐối tác dùng Client Credentials thì API biết được người dùng nào bên đối tác đang thao tác.Thực tếClient Credentials (và API key) chỉ định danh ứng dụng của đối tác; token không có user. Nếu đối tác truy cập dữ liệu thay mặt user của bạn, cần Authorization Code (delegated access).

Các lỗi trông giống nhau nhưng khác nguyên nhân

Ba lỗi dưới đều là 401 Unauthorized. Nếu chỉ nhìn status code, bạn sẽ đoán mò. Hãy đọc header WWW-Authenticate — ASP.NET Core (JwtBearer) ghi rõ lý do:

Phân biệt dễ nhầm: 401 do hết hạn vs do sai aud vs do sai issuer
Tiêu chíToken hết hạnSai audience (aud)Sai issuer (iss)
error_description thường gặpThe token expired at '…'The audience '…' is invalidThe issuer '…' is invalid
Đặc điểmTrước đó chạy được, sau vài phút thì lỗiLỗi ngay từ request đầu tiênLỗi ngay; thường sau khi đổi môi trường/domain
Nguyên nhân hay gặpClient không refresh; đồng hồ máy lệchXin token cho API khác; gửi nhầm ID token; thiếu audience mapperlocalhost vs hostname thật; http vs https; sai realm/tenant; IdP sau reverse proxy
Cách sửaRefresh token; đồng bộ NTPXin token có aud = API này; không nới ValidAudienceSửa Authority hoặc cấu hình hostname của IdP cho khớp iss

Ví dụ: An gọi hr-api và nhận 401. Decode token (vd bằng công cụ JWT ở M02): "aud": "hr-web" → đây là ID token hoặc token xin cho hr-web, không phải cho hr-api. Nếu thay vào đó "iss": "http://localhost:8080/realms/kaopiz" trong khi hr-api cấu hình https://sso.kaopiz.local/realms/kaopiz → sai issuer: cùng realm nhưng khác URL vẫn là issuer khác.

401 → decode token, so exp, aud, iss với cấu hình API trước khi sửa bất cứ thứ gì.

Lỗi ở bước đăng nhập (trước khi có token) cũng hay bị nhầm:

Phân biệt dễ nhầm: redirect_uri mismatch vs invalid_client
Tiêu chíredirect_uri không khớpinvalid_client
Xảy ra ở bước nào/authorize — trong browser, trước khi người dùng đăng nhập/token — server/app đổi code lấy token (back-channel)
Bạn thấy ở đâuTrang lỗi của IdP (vd Keycloak: “Invalid parameter: redirect_uri”); IdP không redirect về appResponse JSON {"error":"invalid_client"} (thường HTTP 401) trong log của app
Nguyên nhânURI gửi đi khác URI đã đăng ký (scheme, host, port, path, dấu / cuối)Sai client_id/secret, secret hết hạn, sai phương thức xác thực client (vd client là public nhưng app gửi secret, hoặc ngược lại)
Sửa ở đâuDanh sách Redirect URI của client ở IdP, hoặc cấu hình callback của appSecret trong secret store; loại client (public/confidential) ở IdP

Ví dụ: deploy hr-web lên server mới sau reverse proxy. Lỗi “Invalid parameter: redirect_uri” → app đang tạo http://hr.kaopiz.local/signin-oidc (http) trong khi đăng ký https://…. Còn nếu đăng nhập xong, quay về app rồi mới lỗi invalid_client → secret trên server mới chưa được cấu hình hoặc đã rotate.

Lỗi trước khi thấy form đăng nhập → redirect_uri. Lỗi sau khi đăng nhập xong, lúc đổi code → client credentials (hoặc invalid_grant).

⚠️ Hiểu lầm hay gặp

Hiểu lầmGặp 401 “audience is invalid” thì tắt ValidateAudience (hoặc thêm audience lạ vào ValidAudiences) cho chạy.Thực tếLàm vậy là API chấp nhận cả token phát cho API khác và ID token của mọi client. Sửa ở phía xin token: client xin đúng scope/resource, IdP có audience mapper để token mang aud của API này.
Hiểu lầmThấy 401 thì đi sửa policy/role.Thực tế401 là lỗi xác thực (token thiếu, hết hạn, sai aud/iss/chữ ký); policy và role thuộc về 403. Đọc WWW-Authenticate trước khi sửa.

⚠️ Hiểu lầm hay gặp

Hiểu lầmConsole báo “blocked by CORS policy” thì đặt Access-Control-Allow-Origin: * là xong.Thực tếThông báo CORS thường che lỗi thật: preflight OPTIONS bị authentication middleware trả 401 (đặt UseCors sai chỗ), hoặc API lỗi 500 nên response thiếu header CORS. Xem tab Network và log API trước. * cũng không dùng được khi gửi kèm credentials.
